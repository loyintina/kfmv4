# agent 信箱机制研究（文档世界账本 → 代码世界事件面）

> 2026-08-18 立（用户拍板）。主理人：评审会话（Kimi Code）。
> 定位：**元机制公共品**，不属任何产品线（9.0 主线 / 工坊 / NA 收编均不持有），
> 无利益冲突；研究成果喂给 9.0 二阶段契约 3（信箱事件面）。
> 出身：跨线评审信箱（`docs/ledger/agent-inbox/`，2026-08-15 立）实战三天后的
> 复盘——文档世界已证明「多 agent 异步评审协作」可行，本线研究代码世界怎么把
> 它做成真正面向 agent 的机制。

## 研究命题

文档信箱 = **裁决正本（账本）**，只追加、全员可见、git 可回查——这层保留，
不动。代码世界要解的是账本做不到的事：**传输层**——投递、通知、回执、
寻址、停滞检测。两者是「账本 vs 事件面」关系，不是替代关系。

明确非目标：**性能**。文件 IO 在当前规模（日均几封信）不是瓶颈；「更好」
的定义是「不再依赖人肉快递 + 状态不再靠手维护」，不是吞吐。

## 实战痛点清单（每条带事故证据）

1. **人肉快递**：每封信靠用户亲自到各线会话转发通知（2026-08-18 用户原话
   「他们我都通知了」）。全系统最贵的环节是人。
2. **无回执**：发信方无法知道对方看没看、何时看。评审回信后 NA 是否已读，
   只能等它下封信自证。
3. **状态手维护漂移**：2026-08-18 全量审计实证——台账漏登 1 封（且被台账
   自身状态引用，自相矛盾）、批准行状态倒挂 3 行、「33 封信」计数 3 处滞后。
   半数已机检化（check-agent-inbox，当日入链），但「该回信而长期未回」的
   停滞检测仍靠用户抽查。
4. **寻址语义缺失**：现有「主送 + 全员可见」是潜规则；信头没有机读地址段。
   面向 agent 集群时私聊/群聊/广播无从表达。
5. **跨机传输为零**：服务器 ⇄ 手机的 agent 通信靠人工维护的反向隧道
   （kalo，2026-08-17/18 断线事故：僵死会话占坑 → 僵尸隧道误判 → 端到端
   探头才救回）。agent 跨机协作时信箱没有任何传输支持。

## 第一批研究问题

承接挂起的议题 6（`docs/ledger/agent-inbox/kfmv4-inbox-mechanism-response.md`
送审问题 1-5，主开发线 2026-08-15 挂起至今），本线解挂并扩展：

- Q1（原 1）通用化：信箱从「跨线评审」升为通用多 agent 信箱的边界与归属；
- Q2（原 2）停滞检查机械化：阈值、巡查节奏（实战已部分回答——状态一致性
  已机检，活性检测待定）；
- Q3（原 3）机读契约头：provides/depends/status + **地址段**（to/cc/线），
  与 NA 规格书 §8 模板的关系；
- Q4（原 4）回执契约：四类信件谁必须回、回什么、多久内；代码世界可加
  「已读回执」「落库回执」两层；
- Q5（原 5）结晶回路：裁决 → 契约的迁移路径；
- Q6（新）事件面形态：信箱作为文档世界 ctx 的事件面（phase2 契约 3），
  事件 schema、订阅模型、与账本的双写一致性；
- Q7（新）传输探针：watch + 通知的最小实现（先解人肉快递），跨机传输
  复用 SSH 隧道还是独立通道。
