# D3：契约 3 机械件落地设计（信封机读头 + 台账投影生成器）

> 2026-08-18 · 评审会话
> 上游：phase2 契约 3（信箱事件面，定稿）——本稿是其「待落地机械件」
> （归属行扫描器 / 代际戳）+ 「事件/落盘分离」条款的实现设计。
> 关联：Q3（机读契约头）、check-agent-inbox（现查手写台账，落地后转型）。

## 问题

README 台账是手写投影：2026-08-18 审计实锤漂移三型（漏登/状态倒挂/计数
滞后），且是并发竞写热点（D2 险情 1/4）。契约 3 已定方向——「信件文件 =
日志，README 状态列 = 从信件推导的投影」——本稿把这个方向落成机制：
**活源头是信件机读头，台账是生成物**（与 experiments 清单、code-inventory
同模式：手写必漂移，生成不漂移）。

## 信封机读头 schema（对齐契约 3 四字段，不多造）

每封信件文首引用块内落四个机读字段（单行 `key: value`，人读即机读）：

```
> 致: kfm-na            # 寻址（契约 3 字段 1）；全线 = all
> 流型: 链条            # 链条/征集/汇总/线程（契约 3 字段 2）
> 预期表态方: 评审,NA    # 征集/汇总必填（字段 3）；链条可省（=致）
> 收敛判据: 评审回信到达  # 字段 4
> 状态: 待回信           # 投影源——状态列从这来，不再手维护
> 回: <文件名或—>        # 台账「回哪条」列来源
> 日期/线/类型          # 从文件名与头部已有信息解析，不重复写字段
```

存量信件的「> 类型 / > 发信 / > 回」头注已有雏形，本 schema 是补齐不是
推翻（四字段契约 3 定稿文字原样，机读格式本稿新立）。

## 机械件三件套

1. **gen-agent-inbox.mjs**（生成器）：扫信件机读头 → 拼 README 信件清单表
   （日期/信件链接/回哪条/状态四列）→ 回写 gen 标记区段；`--check-only`
   进检查链（漂移即红）。手写区只留规则与说明，表格整体入 gen 段。
2. **归属行扫描器**（契约 3 点名第一机械件）：从机读头「致 + 状态」直接
   输出「某线当前欠什么」——`--for=kfm-na` 列待办。降生链第 5 步依赖它；
   也是阅信纪律 D1「启动自查」的机读入口（agent 不用读全表，查自己的
   归属行即可）。
3. **代际戳**：状态翻转在信件侧留下「更新者+日期」（生成器在投影行尾
   注 last-touch），过期回执覆盖新状态时 check 判红——防 D2 险情 2
   （旧会话内存覆盖新状态）的机械兜底。

## check-agent-inbox 转型

落地后其四查改为：信封头 schema 校验（字段齐/流型合法/状态词表）+
生成器 --check-only（台账漂移）+ 命名规范（沿用）+ 决策索引覆盖（沿用，
信号源从手写状态列换成机读头）。计数咬合自动消失（生成物天然一致）。

## 过渡方案

1. 存量 42 封：评审一次性回填机读头（机械解析现有头注 + 人工补四字段，
   逐封核对流型判据——这是一次小判卷）；
2. 新信纪律：送信即带头（写进 README 送信方义务，与阅信纪律并列）；
3. 回填完成前生成器双读（有机读头用头，无则回退文件名/台账行解析），
   回填毕双读退役。
4. 落地顺序：schema 定稿（本稿评审/用户过）→ 回填 + 生成器 → 扫描器 →
   代际戳。git 卫生 commit 检查（契约 3 v0）随生成器同车（脚本比对
   commit 路径清单与本线归属）。

## 风险与不做

- 机读头写错 = 投影错——由 schema 校验 + 回填判卷控制；头注保持人可读，
  不引入 YAML frontmatter 等第二语法（信件既是文档也是数据，单语法）。
- 不做实时 watcher/推送（Q7 另案；契约 3「订阅缓建」立场延续）。
- 台账 README 的规则/活性/阅信纪律等文字区保持手写——生成器只接管表格。
