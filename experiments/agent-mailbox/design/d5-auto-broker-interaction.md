# D5：agent 总线代理交互机制——投递激活 + 空闲指纹 + 自动评审（实战发现）

> 2026-08-22 立（运行时实操中发现，评审会话主理）。
> 归置：agent-mailbox 研究线设计序列（d1 信箱习惯 / d2 并发纪律 / d3 台账生成 /
> d4 代际戳之后的 d5）；研究成果喂 9.0 二阶段契约 3（信箱事件面）+ agent 集群方向。
> 定位：不是替代现有文档信箱（账本）或 d1-d4，而是**账本之上的传输层补充**——
> 解决「信写好了怎么送达、对方何时读完」这两个传输/通知原语。

## 一、由来

评审会话实操中，用户提出「我只跟你对话，你代替我驱动两条线的会话」。经一轮
验证（注入 → 空闲监测 → 自动读回复）后确认可行，形成一套可复用的
**总线代理交互机制**。它把此前「每封信靠用户亲自转发到各线会话」（人肉快递）
和「发信方不知道对方看没看」（无回执）两件事机械化掉了。

## 二、机制五个组件

```
[用户] ──只跟──> [总线代理/评审 agent]
                    │  ① 常读两线 pane（只读，掌握现场）
                    │  ② 通信/裁决落到 durable 信箱（账本）
                    │  ③ 投递激活：向目标线 live 会话 send-keys 一句
                    │     「你有一封信，请读 <file>」（文本激活原语）
                    │  ④ 空闲指纹监测：子代理轮询 pane，判「回复结束」
                    │  ⑤ 空闲即评：抓回复原文 → 继续评审 → 下一条
```

1. **总线代理（broker）**：用户唯一接口，持全量多线上下文；角色=调度 + 评审。
2. **durable 信箱（账本）**：所有真实通信落成信（可复核、可回查），不因会话
   压缩/死亡丢失——这是传输层的「固定底座」。
3. **投递激活原语**：向目标 agent 的 live 会话注入一句短通知（引用真实信件
   文件）。替代人肉快递；因为引用的是账本里的信，激活只是「送达」，不新增内容。
4. **空闲指纹原语（done 信号）**：kimi CLI 会话结束回复的可判指纹 = 底部空
   `>` 输入框 + 旋转 Tip 行（"Tip:…"/"Try /dance"）+ 连续 N 次取样内容稳定
   （跨 ~15s）。作为「这条回复做完了」的机器可判信号。
5. **子代理监视原语**：把轮询空闲指纹外包给后台子代理（每会话一个），空出
   主代理上下文；子代理空闲即上报，主代理自动续评。

## 三、实战证据（本会话，全部可复核）

- **送达 + 对方真读**：向 dsh 注入「评审已定夺…请读 <verdict>」，dsh 面板出现
  `Used Read (.../kfmv4-9.0-nz-882-3bc-verdict.md)` ——激活 → 真读，闭环。
- **空闲指纹可靠**：注入后每会话约 5-15s 回到「空 `>` + Tip + 稳定」，子代理
  以此判定 IDLE，抓回全文（含 Todo 更新、结论要点）。dsh/kfm-na 两例均成功。
- **自动评审接续**：子代理回报 → 主代理读回函 → 定夺 → 写裁决信 → 再次注入。
  整条链路（来信→回函→裁决→再送）不依赖用户切窗口。
- **意外收获（并发教训）**：两线同刻各自 commit 更新计数，与评审线补格式撞车，
  靠 git 串行 + 全员 `git add` 白名单习惯化解，无冲突残留；也印证了 d2 并发
  纪律的必要性。

## 四、它解决了哪些痛点（对 index.md 痛点表）

| 痛点 | 解决 |
|---|---|
| 1 人肉快递（用户亲转每封信） | ✅ 投递激活原语替代 |
| 2 无回执（不知对方看没看） | ✅ 空闲指纹 + Read 痕迹可判「已读/已完」 |

## 五、边界与局限（诚实记录）

1. **物理/设备动作替不了**：只有通信/处理类请求可代驱动；手机上实测 IME、
   真连服务器这类物理动作仍需用户本人（激活原语只能推文本，不能替人按键盘）。
2. **注入时机风险**：只能在空闲指纹出现时注入；正在生成的会话注入 Enter 会
   打断/截断其输出。诚实做法 = 先判空闲再注入（本机制的空闲指纹正是为此）。
3. **单机局限**：tmux send-keys / capture-pane 只在同机可行；跨机（服务器 ⇄
   手机）仍需反向隧道（kalo）承载，跨机激活原语是下一步缺口（对应痛点 5）。
4. **角色混杂**：总线代理同时是「调度者」+「评审者」，有自我审查风险。缓解：
   裁决内容始终以账本信件为准（激活只是送达，不注入新判断），保持逻辑分离。

## 六、对 9.0 的方向建议（喂契约 3 / agent 集群）

把上述三原语正式化为 agent 集群的传输层能力，写入 9.0 二阶段契约 3 的
信箱事件面设计：

1. **投递激活原语**：`deliver(msgRef, targetSession)` —— 把「有信」推到目标
   agent 的会话，而非等人肉/靠它抽查信箱。
2. **会话空闲原语**：`idle(session) -> bool`（同款指纹）—— 作为「该 agent
   这轮做完了」的机器可判 done 信号，是自动编排的基石。
3. **子代理监视原语**：把「等一个 agent 空闲」作为一等可等待任务（异步监视），
   主代理不在等待上占上下文。
4. **角色区分**：`broker(调度)` + `reviewer(评审)` 若同体，至少在数据层保持
   「裁决=账本信、激活=纯送达」的分离，防自我审查偏置。
