# D1：阅信纪律——文档侧递送的过渡方案（拉模式）

> 2026-08-18 · 评审会话（用户动议：观察到各线 agent 有时会自查信箱，
> 把流程写成文让习惯固化）
> 落地：agent-inbox README 规则区「阅信纪律」条目（同日落笔）。

## 判断

传输层（Q7 push）落地前，信箱递送的最优文档侧形态是**拉**：收信方在
会话启动的自然检查点主动查台账。零基建、今天可用。证据：用户观察
（2026-08-18）——部分 agent 已自发出现该行为，说明检查点选择符合
agent 工作节律，不是反自然的要求。

## 设计要点

- **检查点选「会话启动/接新任务」**：agent 此时本就处于「读取上下文」
  心态，读台账边际成本最低；且与 README 活性条款的「会话启动时发现」
  半成文惯例接续。
- **回执的文档形态 = 状态翻转**：「读后即翻」让 Q4（回执契约）在代码
  世界之前先有一个可执行的雏形——已读 = 状态离开「待回信」。机检
  （check-agent-inbox 停滞检测方向）因此有了可判信号。
- **阈值暂用 7 天**（送审问题 2 草案），Q2 定稿时回收。
- **用户转发降级为补充手段**：明确「不是任何一方的义务」，把人肉快递
  从隐性关键路径上撤下来。

## 边界（诚实声明）

- 拉模式依赖各线 agent 真的读入口文档并执行——**可靠性非 100%**，
  不替代 Q7 推送探针；推送落地后，启动自查仍保留为兜底习惯。
- 对「从不启动新会话」的长驻 agent 无效——这类靠停滞检测（Q2）覆盖。

## 推广位（各线入口文档挂载点）

规则本体在 agent-inbox README；各线入口应加一行路由，把启动自查挂进
各自的开场流程：

- kfmv4：`CLAUDE.md`（本体线茉莉执行）
- kfm-na：`AGENTS.md`（NA 线执行）
- 其余 agent 宿主（dsh 等）：各自的 system prompt / 角色卡

建议行文：「会话启动先读 `docs/ledger/agent-inbox/README.md` 台账，
处理指向本线的待回封信件（阅信纪律 D1）。」
