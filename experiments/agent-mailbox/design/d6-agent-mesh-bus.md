# D6：agent 网格总线——从「以评审为心的星型」到「N×N 通用互发」

> 2026-08-23 立（评审会话主理）。agent-mailbox 研究线设计序列，D5（总线代理交互机制）
> 的泛化。起因：用户指出 D5 的「worker → notify 文件 → 评审 watch」是**以评审为中心的
> 星型拓扑**，无法推广到所有 agent；未来 agent 自动聊天（agent↔agent 直接对话）需要的
> 是**「塞对话」这个动作本身成为通用原语**，不是每个 agent 都向一个 hub 汇报。

## 一、现状的局限（D5 是星型，不够）

D5 实际形态：worker 干完 → 写 `/tmp/kfm-note/notify.log` → **评审**的守望子代理读 →
评审行动。所有"完成信号"都汇到评审这一个点。**缺点：**

- 信息流是星型、单向（都朝评审），agent 之间不能直接互发；
- 谁要看谁的状态都要经评审中转，评审成瓶颈；
- 无法表达"任意两个 agent 互相塞话"——这恰恰是未来 agent 自动聊天最核心的动作。

## 二、目标：N×N 网格

把「塞对话」做成**任意 agent 可调用的通用原语**，任意 agent A 能向任意 agent B 的会话
窗口注入一条消息并唤醒它。三层分工，各司其职、不分家：

| 层 | 载体 | 干什么 |
|---|---|---|
| **内容层** | agent-inbox 信箱（durable） | 消息正本，留痕、可回查、全员可见 |
| **时序层** | `agent-send.sh`（塞）+ `agent-notify.sh`（完成信号） | 投递/唤醒/通知，只管"此刻该动一下" |
| **寻址层** | 会话注册表（README 会话注册表节） | session ↔ agent/线 映射，可寻址 |

## 三、两个原语（已在仓，自测通过）

1. **`agent-send.sh <target-session> <message>`** —— 塞对话原语：向任意会话窗口注入消息
   （tmux send-keys + C-m），拒不存在会话。**任何 agent 都能调**，不依赖评审。这是
   D5 里"评审替用户通知各线"那一步的泛化——现在谁都能做。
2. **`agent-notify.sh <session> <status>`** —— 对方干完后写完成信号到 `/tmp/kfm-note/notify.log`；
   任意 watch 方读该文件即知（不必是评审）。

## 四、怎么构成 agent 自动聊天

一个 agent 想跟另一个对话，两步：
```
A:  写内容到信箱（或直接）→ agent-send.sh <B的窗口> "我有一信，见 <信文件>，请回"
B:  读信 → 回函 → agent-notify.sh <B> done
A（或共同 watch）: 见 <B> done 即知 B 回完，接续
```
任意 A↔B 可用，不需要中心。这正是"agent 自动聊天"的最小自足回路。

## 五、开放问题（记下，不定论）

- **防止误注入活跃会话**：send-keys 可能打断正在回复的 agent。需要"目标空闲才注入"的
  守卫（读 pane 判断，或目标自己声明 busy）。当前 agent-send.sh 靠调用方自觉，未机械
  守卫——是已知弱点。
- **信箱还是 send 做正本**：建议内容正本永远进信箱（durable），send 只放"去看看信"
  这类唤醒短句，避免把多字内容刷进窗口污染 agent 上下文。
- **是否给每 agent 配独立 inbox**（每会话一个专属文件，代替全局 notify.log）：可扩展，
  N×N 更大规模时更干净；当前小规模全局 notify.log 够用。
