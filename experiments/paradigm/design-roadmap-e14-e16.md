## e14 组合挂载（H3 验证）

- **问题**：范式包可组合吗？组合效应 = 叠加 / 协同 / 互相稀释？
- **矩阵**：{无， behavior-discipline， metacognition(8.1k)， bd+meta} × 2 任务
  × 4 模型（35B / 27B / V3 / M2.5，硅基）× 8 臂 = **256 臂**（4×2×4×8；
  初稿误写 128，2026-08-06 晚订正——预算量级 ≈1.3×e13，点火前报预算）。
- **任务**：1 个 e13 陷阱任务（行为类，bd 包的主场）+ 1 个 e11 无提示任务
  （元认知类，meta 包的主场）——组合包在两类任务上分别测，能读出
  「包 × 任务类型」匹配效应（顺带触变量 6）。
- **组合方式**：两包顺序拼接进首条 user（bd 在前 meta 在后，固定顺序；
  顺序本身是变量但本轮固定，记为已知局限）。
- **依赖**：无基建改动（batch-run 现状即可，paradigms 参数加一个拼接产物
  `e14-bd-meta.md`，构建脚本一次性生成并落档拼接规则）。
- **判卷**：e13 陷阱任务走 judge-e13-script.mjs 零成本通道 + judge-llm 语义项；
  e11 任务走 judge-llm rubric v2。两任务各用各的尺，不混。

## e15 注入位置（变量 7）

- **问题**：同一个包放 system / 首条 user（现状默认）/ 任务前一条 user，
  同化效果差多少？（产品含义：挂载点选哪；缓存友好性——system 位置破坏
  缓存最大，用户已指出包必须在 user 侧。）
- **矩阵**：metacognition-8.1k × 3 位置 × 1 任务（e11 无提示任务）
  × 4 模型（同 e14）× 8 臂 = **96 臂**（无包对照复用 e11 已有 A 格，不重跑）。
- **依赖（基建改动）**：session-runner 加 `--position` 参数（first-user 默认 /
  system / pre-task-user）。**等 e13 收工后改**——e13 循环每轮重新 import
  session-runner，跑数期间不动它。
  **【2026-08-06 晚已落地】**session-runner/batch-run/exp-driver 三件套已通
  （batch-run 显式 --position 时折进臂哈希防撞名；冒烟测试 7 项全绿）。
  实施时发现并解决：消息层 role==='system' 被 chat.ts:209 过滤必丢——
  system 档改走服务端既有 extraSystem 通道（chat.ts:234 静态 system 段），
  零服务端改动。
- **风险**：硅基系部分模型对 system 段敏感度不一（extraSystem 与全局预设同段，
  不存在「不收 system」问题，但权重感知可能不同）——跑前先 1 臂探针
  验证 4 模型 × system 位置输出非空。
