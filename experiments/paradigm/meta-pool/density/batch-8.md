## 我的补充

### 1. 流程应该是闭环，不是直线

```
你说的：任务发布者 → 构建者 → 审查者 → 史官

实际应该是：
┌──────────────────────────────────────────┐
│                                          │
│  ┌──────┐    ┌──────┐    ┌──────┐       │
│  │发布者 │───→│构建者 │───→│审查者 │──┐    │
│  └──┬───┘    └──────┘    └──────┘  │    │
│     ↑                              │    │
│     │  通过                        ↓    │
│     │                         ┌──────┐  │
│     └─────────────────────────│ 史官 │──┘
│           下一个任务           └──────┘
│                               写完就回到发布者
└──────────────────────────────────────────┘
```

审查不通过时呢？回到构建者，但需要**带上审查者的具体问题**——这就是信号机制（SOP §12）的用处。

### 2. 每个角色只需要知道两件事

```
1. 我是谁（角色名）
2. 前一个角色留下了什么（交接物）
```

具体来说：

| 角色 | 接收什么 | 产出什么 | 需要的能力 |
|:-----|:---------|:---------|:-----------|
| **发布者** | 你脑子里的想法 | 任务描述 + 验收标准 | 理解需求 |
| **构建者** | 任务描述 + 验收标准 | 代码 + 构建产物 | 强推理 |
| **审查者** | 构建者的产出 + 验收标准 | 通过/不通过 + 具体问题 | 多模态（看截图） |
| **史官** | 全过程的记录素材 | LOG.md / SOP.md / STATE.md 更新 | 轻量即可 |

### 3. 交接物应该在文档里，不在聊天记录里

现在的问题是——**角色之间的信息传递依赖聊天上下文**。如果上下文压缩了，下一个角色就丢了前一个角色的产出。

解法：每个角色的产出应该**写入固定位置的文档**，而不是只留在对话里。

```
发布者的产出 → TASKBOARD.md（任务描述、验收标准）
构建者的产出 → 代码文件 + git commit
审查者的产出 → 某个固定文件（比如 REVIEW.md？）
史官的产出 → LOG.md + STATE.md + SOP.md
```

这样，任何 AI 进入任何角色时，只需要：

```
1. 读 ENTRANCE.md（知道世界规则）
2. 读自己角色的说明（知道要做什么）
3. 读前一个角色的产出文档（知道从哪继续）
```

### 4. 缺一个东西——角色手册

现在 ENTRANCE.md 有世界规则，SOP.md 有操作流程，但**没有一个地方告诉 AI "你现在是构建者，你要做这些事"**。

我建议加一个 `ROLES.md`：

```markdown
# 角色手册

> 你当前的角色由人类协作者指定。请找到你的角色，按说明操作。

## 构建者 (Builder)

### 你的职责
根据 TASKBOARD.md 中的任务描述，写代码、构建、部署。

### 你的工作流程
1. 读 TASKBOARD.md → 找到当前任务
2. 读相关参考文档（任务描述中会指明）
3. 写代码 → 构建 → 部署
4. 验证（按 SOP §8 三级验证）
5. 输出信号块（SOP §12）
6. git commit + push

### 你不做的事
✗ 不判断效果是否达标（那是审查者的事）
✗ 不更新 LOG.md（那是史官的事）
✗ 不决定下一步做什么（那是发布者的事）

### 完成标志
📋 阶段完成：...
📎 下一步：需要审查者验证
⚙️ 建议模型：多模态
```

类似地给审查者、史官、发布者各写一段。

---

### 5. 你说的"任何 AI 担任任何角色"

这个思路比固定角色分配更灵活。因为：

```
有时候 GLM 当构建者很好用
有时候同一个 GLM 也可以当史官
有时候你想让 Kimi K2 当审查者
有时候你想自己当发布者 + 审查者
```

角色和模型解耦——**角色是职能，模型是能力，你按需组合**。
