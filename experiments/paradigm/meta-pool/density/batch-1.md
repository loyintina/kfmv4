## 但有几个实际问题需要解决

### 1. Tester 的"笨"怎么弥补？

多模态模型虽然能看图，但可能：
- 不理解"三层 glow"是什么意思
- 把蓝色和紫色搞混
- 无法精确判断 opacity 值

**解法**：给 Tester 一份**对照标准**，而不是让它自由判断。

```
Tester 的 prompt 模板：
"这是一张 KFM v3 页面截图。请检查以下清单：
 □ 6个区域是否都有深色背景的卡片？
 □ 每个卡片左侧是否有彩色竖线（宽度约3px）？
 □ 第1行第1列是否有渐变色（紫→粉→黄）的发光效果？
 □ 第2行第2列是否有两个并排的盒子？
 □ 第3行第2列是否有5张堆叠的卡片？
 
 对于每个 ✗ 的项目，请描述你实际看到了什么。"
```

清单越具体，Tester 就越不需要"聪明"。

### 2. 两个模型的上下文怎么传递？

Builder 和 Tester 看到的是完全不同的东西：
- Builder 看到：源码、构建日志、像素扫描数据
- Tester 看到：截图、预期效果描述

**解法**：中间格式统一。测试报告是一份结构化的文本，Builder 只需要读懂这份文本。

### 3. 循环次数怎么控制？

Builder 修 code → Tester 测 → Builder 再修 → ... 无限循环？

**解法**：设定硬性上限（比如 3 轮），并且 Tester 的报告要有**通过/失败阈值**。超过 3 轮还没过就停下来，让人类介入。
