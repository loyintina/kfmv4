### 根因分析

**直接原因**：omp 被外部 `SIGTERM` 信号终止，不是 crash。

SIGTERM 最可能的来源有几种：

**A. SSH 断开 → sshd 杀会话（高概率）**
你通过 SSH 连到 ECS，在 tmux 里跑 omp。虽然 tmux 理论上保护子进程不受 SIGHUP 影响，但阿里云 ECS 的 sshd 配置可能使用了 `ClientAliveInterval` + `ClientAliveCountMax`，SSH 断开后会终止用户会话中的所有进程——包括 tmux server 自身。tmux server 被杀 → 所有 pane 子进程收到信号。

**B. 阿里云会话回收（中等概率）**
部分 ECS 实例配置了闲置会话自动回收策略。`loginctl` 显示 `IdleAction=ignore`（当前未启用），但不排除有云平台级别的进程管理。

**C. UI 事件循环阻塞加剧 SSH 超时（辅助因素）**
日志显示的 536ms 事件循环阻塞虽然不长，但如果频繁发生，会导致 omp 无法及时响应 SSH keepalive，加速 SSH 判定连接死亡。

### 建议的缓解措施

1. **立刻见效** — 用 `nohup` 或 `setsid` 启动 tmux，让它彻底脱离 SSH 会话：

```bash
# 不要直接 tmux new -s omp，改为：
setsid tmux new -s omp
# 或者先 tmux detach 再 attach，而不是直接 tmux new
```

2. **如果你是 SSH 进来的**，在 `~/.ssh/config` 或 `/etc/ssh/sshd_config` 加：

```
ServerAliveInterval 60
ServerAliveCountMax 5
```

3. **在 tmux 内部启动 omp 时加一层保护** — 用 `trap` 忽略终端断开信号：

```bash
trap '' SIGHUP
omp
```

4. **排查云平台** — 检查阿里云控制台是否有「会话闲置回收」或「自动释放」策略。

## 结论：omp 的 bash 工具在后台任务管理中有一个 bug

### 铁证

两次 SIGTERM 事件中，最后一个工具调用 **100% 相同模式**：

| 事件 | 时间 | 最后的工具 | 命令 |
|------|------|-----------|------|
| #1 | 07:59:47 | `bash` | `npm run start 2>&1 &` |
| #2 | 08:17:42 | `bash` | `fuser -k 8021/tcp ... ; node dist/server ... &` |

两次都在 bash 命令发出后 **86–274ms** 内收到 SIGTERM。

### 排除的外部原因

- **`fuser -k` 发的是 SIGKILL，不是 SIGTERM**（已验证：测试进程收到 signal 9，exit code 137）
- kfmv4 服务器（端口 8021）和 omp 在不同 session、不同进程组，完全隔离
- 无 OOM、无 cron/systemd timer 杀进程
- 不是 SSH 断开（tmux daemon 脱离 SSH 运行，PPID=1）

### 最可能的根因

**omp 自身的 bash 工具后台任务管理器有 bug**：当 `npm run start`（内部调用 `fuser -k`）作为后台任务（`&`）启动后，`fuser -k` 杀死了一批进程，导致进程树发生变化。omp 的任务管理代码在追踪/清理子进程时，**错误地将 SIGTERM 发给了自己**（比如 `process.kill(0, 'SIGTERM')` 或 PID 跟踪错误）。

证据：
- SIGTERM 是 omp 主动发出的（omp 捕获并记录了 `"reason":"sigterm"`）
- 两次都在 `fuser -k` 执行的时间窗口内触发
- 同一 session 中其他 51 个 bash 调用（`npm run build`、`npm test`、`curl` 等）完全正常

### 立即可用的 workaround

**在 kfmv4 的 `package.json` 里把 `start` 脚本的 `fuser -k` 改成温和方式**：
