## 关键结论

`fuser -k` → `kill $(lsof ...)` 这个修复**没有解决根本问题**。证据：

- 96c8 的 start 脚本已经改成了 `kill $(lsof -t -i:8021)`（SIGTERM，不是 SIGKILL）
- omp 确实**能**捕获 SIGTERM 并写入了 `session_exit`（这是改进）
- 但 omp **仍然收到了 SIGTERM**，在 `npm run start` 启动后 238ms

这说明 **SIGTERM 不是来自 `fuser -k`，也不是来自 `kill $(lsof ...)`**——这两个命令针对的是 8021 端口上的进程（kfmv4 node 服务器 PID 60000），不会命中 omp 自身。

## 真正的嫌疑方向

omp 的 bash 工具通过 native Rust 的 `Shell.run()` 执行命令。`npm run start` 启动后不到 300ms 就收到 SIGTERM——这太快了，不像是 `node dist/server/index.js` 启动完成后才发信号的。更可能是：

1. **omp native shell executor 的 bug**：启动子进程时的进程组/信号处理有问题，子进程的终止信号传播到了 omp
2. **bash 工具 timeout 机制的 bug**：10s timeout 可能在清理子进程时误发了信号给 omp 自身
3. **npm 自身的进程管理**：npm 在 spawn node 子进程时可能触发了某种信号传播

这三种和 `fuser -k` 无关——所以你之前手动启动 `npm run start` 不会触发 omp 崩溃，但 omp 通过自己的 bash 工具调用时就会触发。
