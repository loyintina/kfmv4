### 1. 我们的 build 本身吃资源吗？

会的，主要是 `tsc --noEmit`。它把整个项目 22 个 `.ts` 文件全部加载到内存里做类型检查。每次跑大约：

| 阶段 | CPU | 内存 | 耗时 |
|------|-----|------|------|
| `check-anim.mjs` | 很低 | 忽略 | <0.5s |
| `tsc --noEmit` | 一个核跑满 | ~500MB-1GB | 8-15s |
| `node build.mjs` (esbuild) | 中 | ~200MB | <2s |

所以构建时 CPU 和内存飙升是**正常的**，但问题在于超时的 tsc 进程没有被杀掉——上一个卡住了，下一个又启动，积少成多把资源吃光。

### 2. 那个第三方 serve 进程是什么？

```
npm exec serve public -l 8021 --no-clipboard
```

`serve` 是一个 npm 包（`npx serve`），零配置静态文件服务器。有人在 kfmv4 目录下跑过 `npx serve public` 或 `npm exec serve public`——它的作用是把 `public/` 目录挂在 8021 端口上当静态网站。它跟我们 Express 服务的区别：

| | Express 服务 (dist/server/index.js) | serve 进程 |
|--|-----------------------------------|-----------|
| 来源 | `npm run start` / `npm run dev` | 误输入的 `npx serve public` |
| 能力 | 文件 API + 静态页面 | **只有** 静态页面 |
| 后果 | 正常 | API 请求返回 HTML（因为找不到路由就返回 index.html） |

### 3. 理论上 8021 确实全是 KFM 的

你说得对——8021 就是 KFM 的端口。这个 `serve` 进程要么是你自己不小心跑过的，要么是之前某个 AI 调试时跑起来忘关的。它不是系统进程，不是恶意软件，只是个意外。

### 我的建议

两件事：

**① `build.mjs` 开头加一行杀掉旧 tsc 进程**：

```js
// build.mjs 第一行
import { execSync } from 'child_process';
execSync('pkill -f "tsc --noEmit" 2>/dev/null || true');
```

这样之前的卡死 tsc 不会堆积。

**② `package.json` 的 `start` 脚本加端口清理**：

```json
"start": "fuser -k 8021/tcp 2>/dev/null; node dist/server/index.js"
```

启动时自动释放端口，不会被误开的 serve 阻塞。
