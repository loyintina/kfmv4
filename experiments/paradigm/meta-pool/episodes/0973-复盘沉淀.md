## UI Registry：文档-代码偏差与心法违反审计

### 发现1 — `KFMState.subscribe()` 订阅违反三大约束

**位置**：`ui-registry.ts:306`

**文档**：
- §S.0：`它不产生任何运行时开销。不监听事件、不订阅状态、不启动 rAF。它是被动索引。`
- §2.1：`Registry 是一个被动索引。它不监听任何事件、不订阅任何状态变化、不拦截任何操作。`
- 文件头注释第一句：`被动索引（黄页），不存储业务状态、不监听事件、不启动 rAF。`

**代码**：
```typescript
KFMState.subscribe(() => Registry.notifyStateChange());
```
这行代码：
1. **订阅了状态**（`KFMState.subscribe()` → 从页面加载到卸载保持活跃）
2. **产生了运行时开销**（每次 `KFMState.notify()` 都触发一次链式调用 → `onChange` → `ws-channel` 的防抖推送）
3. **创建了跨模块依赖**（`ui-registry.ts` 现在 `import` 了 `state.ts`）

**心法违反**：
- **心法 3（不要跨模块依赖）** — `ui-registry.ts` 现在是 `state.ts` 的依赖方。§S.0 明确定义 Registry 是"被动索引"，不需要知道任何业务模块的存在。这条 `import` 打破了它。
- **心法 2（从源头简化）** — 这条订阅是为了解决 `notifyStateChange()` 散布问题（DOC_CODE_ALIGNMENT 已识别）。但解决方案是在 Registry 本身引入了一个它明令禁止的机制。根解应该是让各模块在操作 KFMState 后自行调用 `notifyStateChange()`，而不是让 Registry 变成半个 KFMState 订阅者。

**严重性：高。** 文档承诺和代码行为直接矛盾，且导入了本不应存在的依赖方向。

### 发现2 — `KFMState.sidebarOpen` 死字段，双状态源

**位置**：`state.ts:31,62,120-123` → `ui.ts:14-28`

**文档**：
- §1.5：`snapshot 必须是页面当前状态的精确投影`

**代码**：
- `state.ts` 定义了 `sidebarOpen: boolean` 字段 + `setSidebarOpen()` 方法
- `ui.ts` 的 `openSidebar()`/`closeSidebar()` **完全不使用** `KFMState.setSidebarOpen()`
- 侧栏实际状态只存在于 `DOM.sidebar.classList.contains('open')`
- 因此 `KFMState.sidebarOpen` 永远为 `false`（初始值），从不更新

**实际影响**：
- Registry 的 sidebar state getter 读的是 DOM classList（正确），所以 `snapshot()` 不受直接影响
- 但 `KFMState.subscribe()`（发现1的回调）在 `KFMState.notify()` 触发时**不包含侧栏变化**，因为侧栏操作没有改 KFMState 的任何字段，只是改了 DOM
- 也就是说：发现1的订阅作为"安全网"遇到了盲区——侧栏切换不会触发它

**心法违反**：
- **心法 2（从源头简化）** — 侧栏开合有**两个**状态源（`KFMState.sidebarOpen` + `DOM.classList`），且一个永远过时。DOC_CODE_ALIGNMENT 笔记已识别此问题（P2），但未修复。
- **心法 12（发现补丁立即根除）** — 这属于已识别但未修复的技术债，且因为发现1的"安全网"订阅而变得更隐蔽（开发者以为安全网覆盖了所有 KFMState 驱动变更，但侧栏不在内）。

**严重性：中。** 目前不影响 snapshot 正确性，但是一个潜在的错误来源——任何依赖 `KFMState.sidebarOpen` 的代码都会得到错误的状态。

### 发现3 — `close-sidebar-btn` state 使用非常规语义

**位置**：`app.ts:124-133`

**代码**：
```typescript
state: 'enabled',  // 初始注册值
getter: () => DOM.sidebar?.classList.contains('open') ? 'enabled' : 'hidden'
```

`UIElementState` 类型包含 `'visible'` / `'hidden'` 对和 `'enabled'` / 其他状态。这里用了 `'enabled'` 来表示"侧栏开着时关闭按钮可见"——但 `'enabled'` 通常在按钮上下文中表示"可点击"，而不是"可见"。当侧栏关闭时返回 `'hidden'` 是正确的。

**心法违反**：
- **心法 2（从源头简化）** — 状态值应该精确映射真实 UI 状态。`'enabled'` 对关闭按钮来说是"侧栏开着所以按钮显示"，但语义上更清晰的表达应该是 `'visible'`（对应 `'hidden'`）。

**严重性：低。** 语义问题，不影响功能。

### 发现4 — `operation-toast` 标记为 `enabled: true` 但不可交互

## 根因分析：不是懒惰，是三种不同的认知模式

三个 agent 在三次检入中分别做了三件不同的事。每种"遗漏"的根因不同：

### Agent A（25a295e）— 基础设施推动者

**做了**：Registry 类、ws-channel、ai-tools、capability-executor、三层 MANIFEST、11 个元素注册。2579 行，24 个文件，单次检入。

**留下的缺口**：
- 没有 `data-registry-id`（ws-channel 的 click 指令不可用）

- 内容是静态的（`registerContent`，不是生成器）

### Agent B（05a886a）— 审计修复者

```
### 14. 替换分散不等于解决根因——一份集中的违规仍是违规

把 N 处散布的临时方案替换成 1 处集中的架构违反，不是重构，是换了一种形式的债务。

判断标准：
- 你要加的新代码**明确违反**了某个已写下的 invariants（Registry 不订阅状态、不跨模块依赖等）
- 你的理由是"这样就不用再在 N 个地方散布同一种模式了"
- 那你做的不是根解，而是"把散兵游勇集中到一个战壕里"。战壕还是不在应有的防线上。

怎么区分"集中的违规"和"真正的重构"：
│ 特征                               │ 集中的违规                    │ 真正的重构
│ 违反已写下的约束                     │ 是                            │ 否
│ 去掉它之后 N 处散布会回来              │ 是（它只是压住了它们）           │ 否（根本不需要那些散布了）
│ 新位置的代码在系统架构中的角色          │ 做了它不该做的事                │ 做了它本应做的事

例子：
- ❌ 在 ui-registry.ts 尾部加 KFMState.subscribe()，说是"安全网"
   → 违反：§S.0 "不订阅状态"。去掉它 → 41 处分散的 notifyStateChange 不会消失
   → 判断：集中 +1 处违规，不是根解
- ✅ 让 KFMState.notify() 直接触达 ws-channel 的推送机制
   → 不违反任何约束。去掉集中化的 subscribe → 41 处散布也不需要存在
   → 判断：重构

例外：如果集中违规是**有计划的阶段性过渡**，必须在提交信息中标注：
  "P3: 此处违反 §S.0，原因是 X。预期在 Y 条件满足时替换为根解。"
  并在同一会话中将跟踪项写入 HANDBOOK.md §3（当前待办）。
```

**心法 13 末段补充**（在"例外"之后追加一个 bullets）：

```
- 你设计了一个跨模块的机制（命令通道、查询属性、注册中心回调），
  但只建了机制、没接上任何消费者就关 commit 了→ 停下来。
  至少为 1 个下游消费者完成从"机制出口到被消费端点"的完整链路，
  证明这个机制确实能用。
  判断标准：如果别人需要通过阅读你的交接笔记才能学会如何使用这个机制，
  那你留的就不是代码，是教材。
```
