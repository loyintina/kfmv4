这就是为什么"修完的代码"在下一次审计时总有新东西。因为**基线变了**。上一次修完时候的代码和下一次审计时候的代码已经不是同一个东西了。

| 心法 | 要求 | 矛盾对象 |

| 心法 12 | 发现补丁立即根除 | notifyStateChange 散布的根解是架构级改造（P3），不可能在同一轮做完 |

| 心法 3 | 不跨模块依赖 | Registry 本身就是一个跨模块索引，它的存在就是轻耦合的妥协 |

**没有一个改动能让所有心法同时满意。** 每次只能选一个方向优化，然后下次审计会发现另一个方向被忽略了。

## 关于振荡模式

根本原因不是 agent 粗心，而是这个循环：

```
审计发现 N 个问题 → 修掉 N 个 → 每个修复改了 M 个文件 → 改文件产生 M' 个新不一致
                                                              ↓
                                             下一轮审计发现 N-M+M' 个问题 → ...
```

每轮修复都引入了新锚点（文档中的数字、新 warn 消息、新参数类型），而这些新锚点在下轮审计之前是"看不见的"——因为当前 agent 刚写了它，认为它是对的。

跳出这个模式的几个可行方向：

**方向 A：在"修完"和"收工"之间插入一个编译时自检步骤。**
当前 `check-registry.mjs` 只验证 MANIFEST 完整性。可以扩展它验证更多可自动可验证的契约——比如在 `snapshot()` 中增加开发时断言：如果某元素有 state getter 但 getter 抛异常 → 构建时报错而非运行时静默。问题 1（state getter 无 try/catch）如果在构建时就能检测到，永远不会存活一轮。

**方向 B：每轮修复只做两件事——修问题 + 把修问题的经验提炼为自动化检测规则。**
不修"人能看出来但机器看不出来"的问题。要么加 check-*.mjs 规则，要么留到下一轮。这样每轮修复都在提高基线，不制造新盲区。

**方向 C：接受这模式，但加一个"收敛阀"。**
定义 Registry 的 complete 状态——当 `npm run check` + 全部已注册元素的 100% 行覆盖测试通过时，宣告暂停。在此之前每一轮都只做 add-check add-test，不做手动修补。

综合来看 **方向 A+B** 最实在：本轮六个新问题中，问题 1（getter 异常）、3（命令覆盖）、4（孤立 getter）、6（click 静默失败）都可以或将来可以转化为 check 规则或测试用例。如果能做到"下轮审计首先跑 check，0 错误 = 没有退步"，那振荡就在收敛。
