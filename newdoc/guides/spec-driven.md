# 第一章 新功能开发 SOP（自 INVARIANTS §七整节迁入，原文未删节）

这个 SOP 的目的是"讨论完→确认→再写代码"。

> **审计流程**：如果需求包含"检查"、"审计"、"对比"、"是否一致"等词，终点是报告，不是代码。输出完整审计报告后，在用户确认之前，禁止进入修改步骤。

### 步骤 1 — 需求提出
用户描述功能。AI 只澄清模糊描述，不问技术细节。

### 步骤 2 — 现状分析
AI 读取相关代码，输出受影响文件列表 + 改动点 + 接口边界。不输出代码，只出结构和位置。

### 步骤 3 — 设计确认（最关键）
AI 用一句话描述最终产物的形态：
- UI：新元素位置/相邻/对齐/尺寸
- 交互：操作路径/手势触发
- 生命周期：创建/销毁/打开/关闭时机

用户确认或纠正。

#### 步骤 3a — 心法回溯
AI 对方案中每个新变量/新分支/新函数，逐条对照 §二 心法表：
- 违反任一 **[LEVEL 1]** 的 → **否决方案**，回到步骤 2
- 违反 **[LEVEL 2]** 的 → 在步骤 4 中写明理由

#### 步骤 3b — 设计讨论 SOP（机制类设计的定稿流程）

涉及匹配/压缩/统计/解析等机制设计时，设计确认按此链条推进，每步不可省：

1. **提议**——给出锋利命题（组 8）：推荐、理由、自认最弱环节
2. **真实数据验证**——拿真实会话/真实输出跑命中率与误报率（心法 25）
3. **质疑**——用压力测试问题库逐条自问；任何一条答不满意就收窄或反转，不要辩护：
   - 反例击穿：那 X 怎么办？（X = 最普通的真实形态，不是理想样例）
   - 流程走查：现有每个 SOP/工作流在新设计里怎么走？
   - 消费追问：谁会读它？读多长？注入哪里？信息污染在哪？
   - 递归上升：这个机制之上还有没有一层？那层成立吗？
   - 信息损耗审计：压缩/模板化/归一会丢什么？需要时谁找得回？
   - 真实数据：命中率/误报率是多少？
   - 成本不对称：错报和漏报各是什么代价？（心法 26）
   - 代理指标：我在优化目标还是目标的代理？（心法 27）
   （问题库源自 2026-07-28 双轨讨论对用户质疑模式的蒸馏，见
   `docs/active/doc-system-redesign.md` §10.3——「用户不在场时的用户式质疑」）
4. **收窄/反转**——把机制收到精确率≈1 的边界内（心法 26），宁可漏报
5. **定稿写入契约**——映射表/注册表/契约文档三者同步（check 脚本机械核对）

### 步骤 4 — 改动计划
AI 输出精确改动清单（含不做的事），精确到行号范围。
用户确认后开始。

### 步骤 5 — 实施
AI 按清单实现，每项标记。不做清单外的优化。

> **关键规则**：每项改动实施前，先说一句："改 X，因为 Y，效果是 Z，验证方式 W。"

### 步骤 6 — 验证
构建 + 测试。用户确认功能符合。不符合 → 回到步骤 1 或 3。

### 步骤 7 — 沉淀五问（元步骤，防灵感流失）

功能/机制定稿后、提交前，逐条自问——答案为「有」就必须落到对应容器：

1. 这轮推翻/收窄了什么初版方案？ → 契约文档错误示例
2. 哪条规则不只属于这个特性？ → 心法候选（版本说明记录来源）
3. 哪条违反了项目就不再是自己？ → 宪法候选（极少，需用户批准）
4. 哪个流程动作值得固化？ → SOP/契约候选
5. 哪条可以机械执行？ → check 脚本候选

# 第二章 规范驱动元工作流（自 SPEC_DRIVEN_WORKFLOW.md 迁入，2026-07-28）

> **面向要做一次「带文档的大改动」的 agent。**
> 这不是某个功能的设计文档，是**做设计文档这件事本身的方法论**——从设计、到分阶段
> 执行、到追加约束、到判断归档。KFM 一直在用（测试基础设施、回归体系都走过这条路），
> 本文把它显式写下来，让后来者照着做，而不是每次重新发明。

## 关联文档

- `doc-maintenance.md` — 文档维护规则（本工作流产出的文档要遵守它）。
- `../constraints/invariants.md` — 心法原则（执行阶段的行为约束）。
- **已跑通的范本**：
  - `docs/archive/design/REGRESSION_TESTING_SYSTEM.md` — **任务型**，8 阶段建成后归档（archive 轮结算后改指）。
  - `../domains/ai-chat/detail-runtime.md` — **参考型**，实现完仍保持活跃（长期契约参考）。

## §1 何时用这套流程

**用**：改动满足以下任一条——
- 跨 3+ 文件，或跨客户端/服务端。
- 分多个阶段、无法一次做完。
- 引入或依赖**隐式契约**（跨文件的时序/协作约定，破坏后症状隐蔽）。
- 用户明确要求先出方案再实施。

**不用**（直接干）：单文件改动、bug 小修、能在几次工具调用内完成的事。给这类改动写设计
文档是过度工程。

**判断标准**：如果你说不清「这个改动分几步、每步验收什么」，就该先写文档理清；如果一句话
能说清怎么做，就别写。

## §2 四个环节

```
① 设计（active/ 草案）
    ↓  §现状 → §方案 → §分阶段实施表 → §开放问题
② 执行（边做边更新状态表）
    ↓  每阶段做完翻状态；发现新决策先更文档再改代码
③ 追加约束（把纪律沉淀成一等公民）
    ↓  一次性纪律→心法 / 实时闸门→AI 规则 / 契约→域 contract / 账本→ledger
④ 判断去向（任务型收尾 / 参考型保持活跃）
```

### ① 设计

在 `active/` 新建文档。结构（照抄范本）：

```
§0 为什么存在（问题陈述 + 核心洞察）
§1 现状分析（当前覆盖/缺陷，带表格）
§2 方案（总体策略 + 关键设计要点）
§3 实施步骤（每步：目标 / 改动范围 / 设计要点 / 验收标准）
§4 实施计划（阶段划分表，含「状态」列：⬜待开始 / 🔄进行中 / ✅已完成）
§5 可复制模板（首个阶段跑通后回填，供后续阶段套用）
§6 开放问题（决策待定项，实施中逐个消解为「结论」）
```

**结尾必写**：`> 本文档与代码同步。实现中发现设计漏洞或新决策，先更新本文再改代码。`

### ② 执行

- **每阶段做完立刻更新 §4 状态表**（⬜→🔄→✅），附一句产出摘要 + 关键 commit。
- **文档先行**：实施中冒出的新决策/踩的坑，先写进文档（§5/§6），再改代码。文档滞后于代码 =
  下一个 agent 踩你踩过的坑。
- **验收先于推进**：每个阶段的「验收标准」逐条勾掉才进下一阶段（心法 23 增量验证）。
- **每个可测点走 revert 验证**：见心法 24——回退修复必须让测试变红，否则测试是假的。
- **提交纪律**：每个可独立运行的改动立即 commit（心法 14）；`check-uncommitted` 会在 >3 文件时
  拦截，别攒。

### ③ 追加约束（关键，最易漏）

改动做完不等于结束——把这次学到的纪律沉淀到对应载体，否则下次还会犯：

| 约束类型 | 沉淀去向 | 例 |
|---|---|---|
| 长期行为纪律 | `../constraints/invariants.md` 心法（编号追加/升级） | 心法 24 回归测试纪律 |
| 改特定代码时的实时提醒 | AI 规则（`src/server/ai/rules/` 下的 md，`condition` 触发） | `kfmv4-regression-discipline` |
| 隐式契约（破坏出隐蔽 bug） | `../domains/{域}/contract.md` #陷阱 | ai-chat 面板渲染生命周期 8 条 |
| 日常速查 | 对应 `guides/` 主题指南 | `testing.md` 回归测试分层 |
| 持续追踪的账本 | `../ledger/bugs.md` | BAR 编号登记表 |

### ④ 判断去向

文档做完后，按**它是什么**决定命运，而非「实现完没完」：

```
这份文档是「一次性任务的计划」吗？
├─ 是 → 任务型：知识按域回家 + ledger/history.md 记一条，原草案删除
│        （见 doc-maintenance.md 文档生命周期节；范本：REGRESSION_TESTING_SYSTEM）
└─ 否，是「长期要查的契约/架构参考」→ 参考型：进 domains/{域}/ detail 或 guides/，
         实现完也不删除。
         （范本：AI_CHAT_RUNTIME —— 改流式对话时仍要查它的隐式契约）
```

**常见错误**：把参考型文档因为「实现完了」就删除 → 后来者改相关代码时找不到契约参考。
**判据**：问「这份文档实现完之后，还有人需要回来查它吗？」需要 → 参考型 → 保留。

## §3 收尾检查清单

一次规范驱动的改动，结束前逐条确认：

- [ ] §4 状态表全部 ✅，每阶段有产出摘要。
- [ ] §5 可复制模板已回填（真实跑通的做法，不是占位）。
- [ ] §6 开放问题全部消解为「结论」。
- [ ] 学到的纪律已按 §2③ 表沉淀到对应载体。
- [ ] 文档去向已判定（任务型收尾 or 参考型保留），引用同步。
- [ ] `npm run check` 绿灯（含 check-docs 引用有效性、check-versions）。
- [ ] 涉及测试的：`npm test` 全量绿 + 关键钉子过 revert 验证。
