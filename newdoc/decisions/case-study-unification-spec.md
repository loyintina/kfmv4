# 案例详注：CARD_SYSTEM_UNIFICATION_SPEC（统一化 SPEC 的失败）

## 它计划了什么

v1.0 SPEC（173 行，2026-06-05）是 adr-002「尝试 2」的实施计划：以 orb.ts 为地基，
将 floating-card.ts 泛化为 config 驱动的通用引擎——「一份引擎，任意浮卡」，
「配置即差异」（尺寸/角光球/内容/z-index/输入栏避让全部参数化），5 步迁移，
最终**彻底删除 orb.ts**。

## 为什么仍然失败

方向反转（v0.2 以 floating-card 为引擎 → v1.0 以 orb 为地基）没有解决问题——
因为问题从来不在方向，在「统一」本身：orb 的 AI 面板是二元展开/收起，
浮卡是多态发射流水线，状态机本质不同（adr-002 理由 1）。SPEC 自己的 §1.4
「彻底删除 orb.ts」正是最大的风险源——把经过 14 commit 迭代的业务逻辑强迁进
泛化引擎，细节必丢（adr-001 理由 1）。

## 元教训（超出 adr-002 的部分）

- **SPEC 写得越完整，越说明该先质疑前提**。这份 SPEC 有产出定义、删除清单、
  5 步验收、已知缺口表——流程上无懈可击，但「两个状态机能否同一引擎」这个
  前提问题从未被当作问题。流程正确 ≠ 方向正确（与 spec-driven 元工作流 §1
  「说不清分几步就该写文档」互补：写得清步骤 ≠ 该做）。
- **方向反转是沉没成本的伪装**。v0.2 失败后反转方向再来一次，感觉像「吸取了
  教训」，实际是同一个错误假设的第二次投胎。两次回退后 adr-002 才承认：
  统一化这个念头本身该放弃。
- **「配置即差异」的失败是过度抽象的典型**：两个模块共享的是概念对称
  （四角光球/拖拽/缩放），不是逻辑共性。概念对称 ≠ 可参数化（adr-001 理由 2：
  共享层解决重复，引擎统一解决不了）。
