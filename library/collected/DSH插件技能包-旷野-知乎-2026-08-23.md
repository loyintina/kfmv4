## 一句话核心

> **DeepSeek Harness 这套 Skills 真正少见的是：从头到尾按"执行者会偷懒、会作弊、会为了让指标变绿而糊弄我"这个前提写。大量的篇幅不在教 Agent 怎么做事，而在堵 Agent 糊弄事的路。**
> 它抬的不是天花板，是地板——但地板比天花板更值钱。

**它不是"自我进化"，DeepSeek 本身也没做这方面。** 但价值极高。

## 三个最锋利的洞察

1. **正向指令写了等于没写**：绝大多数人写 Skill/Rules 都是正向的——"你应该检查空指针、补测试、保持函数简短"，这些模型本来就会。**真正难的、也真正值钱的是反向的：什么情况下应该否决/降级一个判断。**（如 `dsh-find-simplifications` 整节 "Reject or downgrade a candidate when"，四条否决条件：想法对但太小→只加 TODO 不写 Agent Note；删掉引发一堆无关改动而公开 API 其实没减……）

2. **把 API 设计品味写成可执行判据**：`dsh-code-review`（1500+ 字，无一废话角色扮演）要求追踪每个改动接口的**两侧**，确认实现与 PR 描述/Agent Note 一致，含**错误/取消/所有权/销毁**四维；甚至规定"通用服务上新增的 public 方法若唯一调用者是内部消费者，就是不必要的 API 膨胀，应改成构造时交给该消费者的私有能力闭包"。

3. **下限 vs 上限**：堆模型能力抬的是**上限**（能不能想出新东西）；Skills 抬的是**下限**（能不能稳定地不犯上次那个错）。一个天花板 90 分但每次 40–90 随机跳的 Agent 工程上没法用；一个天花板 70 分但稳定 65 的能进生产。**对今天真用 Agent 干活的人，下限比上限要紧得多。**

## 真正的宝藏：`.agents/notes/`

> **`.agents/notes/` 目录才是真正的宝藏——那个团队工程决策的完整化石层，带状态、带否决理由、带备选方案、带封印，日期从六月排到八月。** Skills 只是它面向模型的那个查询接口而已。想学，从那里翻起。

（这也印证了 kfmv4 的判据：**skill 是"原子事实"，文档世界是"仍然为真的事实 + 状态"**——`.agents/notes/` 就是文档世界，Skill 只是查询接口。呼应 `library/notes/skill-本质与kfmv4文档世界-2026-08-21.md`。）

## 与 kfmv4 / 我们讨论的呼应

- **"堵糊弄事的路" > "教做事"** ≈ kfmv4 心法 / check 门（机械执法防退化）——正是"反向/否决项"的纪律化
- **"被 knip 假阳性坑过的人才写得出'knip 不能当结论'"** = 心法从撞墙中来（kfmv4 纪律原则 5）
- **Skills 抬下限** ≈ 我们讨论的"prompt 资产化 + 渐进披露"，模型不变、纪律注入
- **`.agents/notes/` 化石层** = kfmv4 文档世界（知识+纪律+状态），Skill = 查询接口 —— 这是两套体系的同构验证

Agent 真要能靠 Skills 成长，瓶颈从来不在生成新 Skill。让模型写一百个 Skill 出来是今天就能做的事，而且它会写得很起劲。瓶颈在于第 101 个 Skill 和第 3 个 Skill 冲突的时候怎么办，在于某个 Skill 因为 GitHub 改了行为已经过期了但没人知道，在于两个 Skill 在讲同一件事的不同版本。 一个只会积累不会淘汰的技能库，膨胀到一定规模就会开始互相矛盾，然后 Agent 的表现会 倒退 。DeepSeek 显然想清楚了这件事，所以他们在淘汰上花的笔墨远多于积累。 这是我觉得其他项目最该抄的一条，但可能也是最不会有人抄的一条。因为写规范很爽，删规范很痛。 为什么这套东西现在不是自我进化 好，现在回答核心问题。我在仓库里找到了三条互相印证的证据。 第一条，架构上 Skills 被刻意放在核心之外。 packages/skill/README.md 里有一句非常克制的话。 This capability remains outside the core control spine ，这个能力保持在核心控制脊柱之外。子系统文档里说得更明白。 Skills are optional instructions, not session events ，技能是可选的指令，不是会话事件。 这句话在 dsh 的语境里权重极高。因为 AGENTS.md 里有一条铁律就是Model-visible ⟺ logged，任何到达模型请求的东西都必须能从会话日志里重建，新增一个模型可见的输入就必须新增一个会话事件。而 Skills 明确被排除在这个体系之外，技能目录是以 user 角色消息注入的，文档里说 These catalog messages are session history, not World State，这些目录消息是会话历史，不是世界状态。 所以 dsh 的作者自己不完全信任 Skills。 他们把它放在了可替换，非权威，不进核心状态的位置上。这跟外界把 Skills 吹成 Agent 进化引擎的调门，差得有点远。 第二条，连调用权都没有完全交给模型。 技能有两个独立的开关， modelInvocable 和 userInvocable ，组合出四种状态。其中带 disable-model-invocation 的技能，模型既看不到它在目录里，也没法用 skill 工具加载它。它唯一的入口是人在消息里手打一个 /名字 。 也就是说有一类技能被设计成模型永远不能自主选择，必须人来触发。这是在调用路径上就切了一刀。 第三条，真正的自我修改路径存在，但它是易失的。 仓库根目录的 AGENTS.md 里列了一个包组，叫 self-modification/ ，注释写的是 the agent inspects/mounts its own plugins，Agent 检查并挂载自己的插件。命令列表里还有一行 pnpm run demo:cordis # the agent modifies its own runtime 。 我去翻了，这个目录现在已经改名叫 packages/extensions/ ，README 标题就是 the agent modifies its own runtime。里面四个包： tool-cordis 提供模型可见的运行时检查和动态包工具， cordis-host-runner 提供定义注册表和一个 node:vm 沙箱 ，加上浏览器侧的两个对应实现。能力描述是：检查已加载的插件和服务 API，定义并运行 模型自己写的动态包 ，然后再把它们 撤回 。 看清楚这个组合。DeepSeek 确实给了 Agent 修改自身运行时的能力，模型可以现场写一个插件、挂上去、跑起来。但这个能力是关在 node:vm 沙箱里的，而且是可撤回的、不落盘的、活在内存里的。 于是整个图景就清楚了。dsh 里有两条自我修改的路径： 谁能写 是否持久 门槛 packages/extensions/ 动态插件 Agent 自主 不持久，可撤回，vm 沙箱 无 .agents/skills/ + .agents/notes/ 走 git 持久，版本化，gate 校验 PR review Agent 能自主写的东西是易失的。能持久下来的东西必须过人工 review。 这个缝隙的宽度，正好就是一个人类工程师的身位 ，而这是一个明确的架构决策。因为你只要把这两条路连起来，让 Agent 自主生成的经验直接落盘成 Skill，你立刻得到一个没有人监督的，能自己改自己行为的，还会互相引用的知识库。它第一次写错一条规则，后面所有任务都带着这个错误跑，而且那条错误规则还会被新的 Skill 引用，形成正反馈。 DeepSeek 这套体系里那么多 gate、那么多哈希封印、那么多不要凑数的条款，全部都指向同一个判断： 他们非常清楚这个执行者不可靠。 一个明确知道执行者不可靠的团队，不会把持久化写权限交给它。 所以这套 Skills 的本质不是自我进化，是一个 人类经验的棘轮 。人踩了坑，写成 Agent Note，过 review，固化成 Skill，Agent 下次读到。梯度全部来自人类。棘轮的价值在于它不回滑（这就是那些 gate 和封印的作用），但它不自转。 那如果真想闭环的话会卡在哪 假设我们真想让 Agent 自己生成、验证、淘汰 Skill，把那条线连起来，实际卡点在哪。 我看到三个，从难到易排。 卡点一，验证。这是死结。 注意一个事实就是dsh 里所有能自动检查的东西，已经全都是 gate 了。 doc-sync 、 verify-type-equiv 、 verify-translation-pairing 、 verify-export-jsdoc 、 verify-agent-note-format 、 verify-archived-agent-notes 、 verify-doc-budgets 、 verify-cordis-config 、 test:coverage 的每文件 100% 阈值，长长一串。 那 Skill 还剩下什么？剩下的恰恰是自动检查建立不了的那部分。 dsh-code-review 的第一条阻塞要求里写得明明白白：automated checks do not establish those properties，自动检查建立不了那些性质。它讲的是新增散文必须接受语义审查，覆盖度、准确性、位置、编辑质量，这些得对着代码和行为人工判断。 Skill 的存在本身就是这部分没法自动验证的证明。 那么问题来了，一个 Agent 生成了一条新 Skill，它凭什么判断这条是对的？它没有验证器。它唯一的信号是按这条做了之后任务成功了，而这个信号极其嘈杂，也极容易造假 —— 别忘了这批 Skill 里有一整个类别的条款，就是在防 Agent 伪造成功证据。 你要让 Agent 自己验证 Skill，等于要让它对着一个连人都要吵半天的语义问题做出可靠判断。这不是工程问题，这就是原问题本身。 卡点二，路由。 看下技术细节。技能目录只注入 name 和 description ，完整 body 靠模型主动调 skill 工具按需加载，这叫渐进披露，设计得很干净。但是 catalogDescriptionMaxLength 默认 500 字符。 11 个技能，目录撑死几千 token，无所谓。500 个技能呢？光目录就把上下文吃掉一大块，而且模型要在 500 条一句话摘要里挑对的那个。 这里的瓶颈不是存储，是 description 写得好不好 。它不是简介，它是路由键。你回头看 dsh-find-simplifications 那条 description，长得离谱，密密麻麻堆满了触发条件：dead、duplicated、speculative、over-built、added-then-removed、hand-rolled-where-a-dependency-exists，一口气六个场景关键词。这不是给人读的，这是给检索用的。 技能库要规模化，得先有语义检索，有分层目录，有基于当前任务上下文的动态子集。这些都是能做的工程，但目前 dsh 是全量目录注入， skills/change 事件触发全量替换。这条路走到几十个技能就得改架构。 卡点三，归因。 一个任务失败了。是 Skill 写错了？是模型没遵守 Skill？是环境变了让 Skill 过期了？还是这个任务本来就不该用这个 Skill？ 四种情况的修法完全不同，而且没有归因就没有梯度。你连该改哪儿都不知道，谈什么进化。 我注意到 dsh 在这方面其实有基础设施 —— 那个 append-only 的会话日志，模型看到的一切，系统提示词、思维链、工具调用、子 Agent 调度，全部落盘，支持恢复、分叉、检索和回放。理论上你可以拿一批失败会话去做归因分析。但那是另一套系统了，现在没有。 最后 写这篇的时候我发现了一个挺有意思的小细节。 AGENTS.md 的仓库结构里还写着 self-modification/ the agent inspects/mounts its own plugins ，但实际的 packages/ 下面已经没有这个目录了，它改名叫 extensions/ 。 而这份 AGENTS.md 自己规定 Docs accompany every code change，代码改动必须带上文档 。 dsh-code-review 的阻塞要求第二条说的是 Docs match the code ，配置、默认值、错误、wire 字段、事件和公开行为的改动，必须在同一个 diff 里更新 README 和 JSDoc。 一个把文档纪律写到这个程度的仓库，自己的入口文档里有一行是过期的。 我觉得这是全文最有说服力的一个数据点。 连 DeepSeek 这样一个把规范写到偏执的团队，在人工 review 全程在线的情况下，都没能守住自己定的纪律。 那么让 Agent 自己维护这套知识体系这件事有多难，你大概能有个体感了。 维护成本不会因为执行者换成 AI 就消失，它只会换个地方冒出来。 所以最后回到那个 AGI 的问题。我不觉得这是通向 AGI 的另一条路线，说实话我觉得那个框架有点大了。 堆模型能力抬的是上限，能不能想出新东西； Skills 抬的是下限，能不能稳定地不犯上次那个错。 但对于今天真在用 Agent 干活的人来说，下限比上限要紧得多。一个能力天花板 90 分但每次表现在 40 到 90 之间随机跳的 Agent，工程上没法用。一个天花板 70 分但每次都稳定在 65 的，能进生产。 DeepSeek 这套 Skills 干的是后一件事，它是对的，只是不是我们期待的那个进化。 而且说到底， .agents/notes/ 这个目录才是真正的宝藏。那才是这个团队工程决策的完整化石层，带状态、带否决理由、带备选方案、带封印，日期从六月一直排到八月。Skills 只是它面向模型的那个查询接口而已。 想学的话，我建议从那里开始翻。 发布于2026-08-21 10:04 ・德国 打开知乎查看更多内容 收起 ​ 推荐阅读 查看更多 一个千万流量博主的AI工具清单（总花费：673元）
