## 一句话核心

> **从进程列表看，这是多 Agent。从工程结果看，它只是多个模型同时碰同一份状态。**

多 Agent 的难点不在"能启动",而在——**谁能定义子任务、谁拥有工作区、什么上下文可传递、失败怎样传播、取消后副作用几何、结果凭什么进主分支**。可控的 Sub-agent 需要一条清晰主线：**Task Contract**（固定任务）、**工作区与权限**（限制执行）、**Artifact Envelope**（返回证据）、**独立 Review Gate**（决定是否接收）。

## 七类对象（主线检查表）

| 对象 | 必须回答的问题 |
|------|---------------|
| Task | 要解决的具体问题是什么 |
| Context | 允许依赖哪些事实与代码快照 |
| Capability | 可调用哪些工具/凭证/网络 |
| Workspace | 在哪读写，谁拥有这些写入 |
| Run | 当前执行到哪个状态 |
| Artifact | 返回了什么可检查的结果与证据 |
| Gate | 谁决定接受/重试/拒绝/合并 |

> 缺任何一项，主 Agent 得到的往往只是一句"我完成了"的自然语言，而不是可接管的工作。

## 与 kfmv4 的呼应（本剪藏的价值点）

- **Task Contract / Review Gate ≈ kfmv4 的契约 + check 门**——"结果凭什么进主分支"正是 kfmv4 全绿才提交的纪律
- **Artifact Envelope（返回证据、结论挂证据）** 对应实验契约"结论必须挂臂 id 证据"
- **"冲突不在模型能力，在状态与写权限"** 与 kfmv4 多端分层 "核心层禁碰平台依赖" 同构——都是把状态/权限从模型上下文里拿出来
- 核心主张：**工程应把任务、状态、证据、权限、验收从模型上下文中拿出来**——正是我们 skill 讨论里"context 是运行时资源"的延伸

**01/09 多 Agent 最难的不是启动**
- 副题：并行执行不是多开几个终端。右上橙色块：`MORE PROCESSES ≠ MORE CONTROL`
- 真正困难的是：谁能写、谁能停、结果如何验证，以及迟到结果能不能污染主线。

**02/09 INCIDENT · PARALLEL WRITES — 三个执行者都"完成了"，主线却坏了**
- A 改正文（依赖 revision-17）
- B 重写同一文件（覆盖 revision-18）
- C 返回迟到结果（基于已取消任务）
- 结论：冲突不在模型能力 · 在状态与写权限（CONFLICT FIRST）

**03/09 EVIDENCE 01 · PI README**
- 来源：earendil-works/pi · packages/coding-agent · fixed tag v0.82.1 · checked 2026-08-12
- 原文摘录："No sub-agents. There's many ways to do this. Spawn pi instances via tmux, or build your own with extensions, or install a package that does it your way."
- 解读：证明 Pi 没有内置唯一 Sub-agent 工作流；**不证明**多个进程天然具备调度、恢复与验收能力。（EVID-PI14-01）

**04/09 EVIDENCE 02 · SDK COMPOSITION — SDK 提供组合原语，控制面仍要自己负责**
- Session："The main factory function for a single AgentSession."（Pi 提供）
- Tool："Build custom tools that spawn sub-agents"（Pi 提供）
- Envelope：作者方案——输入、版本、证据、输出与状态
- Gate：作者方案——独立审查后才允许汇入

**08/09 PARALLELISM DECISION — 不是所有任务都值得并行**

| 任务形状 | 只读并行 | 隔离写入 | 持久 DAG |
|---|---|---|---|
| 资料搜集/校对 | 优先 | 不需要 | 不需要 |
| 独立资产生成 | 可用 | 需要 | 按规模 |
| 共享文件重构 | 谨慎 | 强制隔离 | 复杂时需要 |
| 长时任务/重试 | 不足 | 不足 | 优先 |

- 路径：`READ-ONLY → ISOLATED WRITE → DURABLE DAG`，**ESCALATE BY NEED**（按需升级，上一层无法证明收益就不增加并发）

它读取的是哪个代码快照？

结果由谁验收，什么时候才允许合并？
 这条主线背后需要检查七类对象： 对象 需要回答的问题 Task 要解决的具体问题是什么 Context 允许依赖哪些事实与代码快照 Capability 可以调用哪些工具、凭证和网络 Workspace 在哪里读写，谁拥有这些写入 Run 当前执行到了哪个状态 Artifact 返回了什么可检查的结果与证据 Gate 谁决定接受、重试、拒绝或合并 缺少其中任何一项，主 Agent 得到的往往只是一段“我完成了”的自然语言，而不是可接管的工作。 二、Pi 实际提供了什么，又刻意没有提供什么 Pi v0.82.1 README 明确把 Sub-agent 排除在核心默认能力之外，并给出 tmux、Extension 或第三方 Package 等组合方向。到 2026-08-12 检查当前 main ，小核心立场仍然存在。当前 SDK 文档同时把 “构建能启动 Sub-agent 的自定义 Tool”列为程序化用例，Extension 示例目录也提供相关示例。 这组事实应该被准确表述为： Pi core 不内置唯一的 Sub-agent 工作流。
Pi 提供足以构建多会话、多进程与自定义工具的组合原语。
示例与原语不等于生产级调度、隔离、恢复和验收已经成立。
