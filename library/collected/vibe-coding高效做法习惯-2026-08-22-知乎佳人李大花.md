到了 2026 年，Vibe Coding 真正拉开差距的，显然已经不是提示词了……

2026年7月30日，Thoughtworks的一位CTO公布了一个挺有意思的实验。

他用Claude Code和Cursor做了一个大约15万行代码的应用。代码基本都由Agent生成，他平时也很少逐行查看。项目越做越大以后，数据访问层慢慢长成了一个17155行的Rust文件。后来，他按职责把这个文件连续重构，再让全新的Agent用完全相同的提示完成同一项改动。

结果，Agent需要读取的输入token从159564降到了27360，少了 83%。数据访问层的总代码量并没有明显减少，关键变化在于：Agent终于能比较准确地找到自己该看的那几份文件了！

【图 1 · 文字描述】（随剪藏保存的唯一一张内容图）实验中「拆大文件」的效果曲线。横轴 Step 0-14；左纵轴 Lines of Code (LOC)，右纵轴 Tokens。四条线：深蓝 **Data Access Layer (LOC)** 全程近乎水平，稳定在 ~17k（总代码量没变）；青色 **Largest File (LOC)** 起始 ~18k，Step 7 后逐级下降，到 Step 14 塌到 ~3k（最大文件被拆小）；橙线 **Input Tokens** 起始 ~163k，前 11 步高位震荡，Step 12 后陡降，Step 14 达到 ~30k（同一句提示的输入成本骤降 83%）；绿色 **Output Tokens** 贴近 0 全程平坦。水印「知乎 @佳人李大花」。

当然，这只是一个项目上的单项实验，token还是用字符数近似估算的，不能据此认定"拆文件一定省 83%"，但它很能说明这两年Vibe Coding的变化：同一句提示，放进不同的代码库，成本和结果可以差出很远。

早期玩 AI 编程，大家比的是谁更会说话，比如什么要不要先让模型扮演专家，需求分几步写，结尾再加一句"请仔细检查"。这些技巧不能说一点用没有，但到了2026年，它们对于新模型来说，确实是一些废话了……

现在更重要的问题是：Agent 能不能独立启动项目，能不能迅速找到相关代码，能不能自己看见报错，能不能证明改动是对的，以及它做错以后能不能低成本回退。

说白了，过去我们优化的是某一次对话，现在需要优化的则是整个工作环境。

我现在判断一个项目适不适合Vibe Coding，首先不会看它写了多长的AGENTS.md，而是看一个刚进来的 Agent 能不能自己完成几件很简单的事情：安装依赖、启动程序、运行测试、执行 lint 和类型检查、准备一份演示数据，必要时把环境恢复到初始状态。

命令叫什么并不重要。可以是：

```
make setup
make dev
make check
make reset-demo
make smoke
```

关键是，这些命令每次执行都能得到相对稳定的结果，而不是换一台机器就要重新考古半天。

GitHub给Copilot coding agent的建议是预先装好依赖。让Agent自己靠反复试错猜安装方法，不仅慢，而且不稳定，只有当Agent能在自己的环境里完成构建、测试和验证，才更可能给出可以直接合并的改动。

项目要是不能自己跑的话，人和Agent的聊天就会变成这样式的——

> "你先等等，我把报错复制给你。"
> "这个账号没数据，等我手写一条。"
> "按钮点完不是你说的效果，等我截个图。"

看上去像是人在指挥Agent，实际上大半时间都在替Agent搬运信息，提示词写得再漂亮，也省不掉这些人工操作，麻烦得很，而且丢信息几乎是必然的。

OpenAI在一个由Codex生成约百万行代码的内部项目里，给每个worktree单独启动一套应用，还把DOM、截图、浏览器导航、日志、指标和traces直接交给Agent查询。这样Codex就不只是"写完代码并运行测试"，还是能自己复现问题、观察页面、验证修复。

个人项目未必需要照搬这套配置，但道理却是一样的……网页项目应该有固定测试账号、可重置的演示数据、浏览器截图和控制台日志；后端项目至少应该有结构化日志、小规模可重复数据和一条完整检查命令。

这两年还有一个常见误区，就是恨不得把所有项目知识都塞进AGENTS.md或CLAUDE.md里。

目录树要写，架构史要写，代码规范要写，连框架官方文档也复制进去，最后文件越来越长，Agent每次工作都得先交一笔不菲的"阅读费"。

OpenAI那个百万行代码项目早期也试过"一份巨型AGENTS.md"，但后来放弃了……他们现在选择把那份md当目录用：根文件大约100行，只保留最关键的命令、边界和入口，至于详细的架构、设计和执行计划放在结构化文档里，需要时再读取。

2026年2月的一项研究可以算是给这件事补了一组独立证据。研究者在SWE-bench Lite和他们建立的CTXBench上测试多种coding agent。自动生成的上下文文件在多数组合里没有提高任务解决率，却让平均执行成本增加了约20%和23%，开发者亲自维护的文件表现比自动生成的好一些，但也增加了执行步骤和成本。

所以，根目录的指令文件回答四件事通常就够了：**项目怎么运行，哪些架构边界不能碰，有哪些无法从代码里直接发现的约定，以及怎样才算完成**。其他内容放进专门文档，再从这里指过去。

还有一点很重要，就是不要定期让 Agent "重新总结整个项目"，然后不加检查地覆盖原文件。

项目规则不是会议纪要，写得多不代表管理得好，只有那些真正稳定、必要且反复用得到的东西，才值得放进长期上下文里，否则就是浪费token，还可能搞坏项目。

还有现在流行的这个multi-Agent……第一次接触时会感觉这玩意太强了，一个改前端，一个修接口，一个补测试，还有几个在后台研究架构，屏幕上全在跑，很有生产力的样子，然后一周的量几个小时就跑没了……

问题是，最后这些任务都要人来验收。

OpenAI在Symphony项目里记录过这个瓶颈：多数工程师同时管理三到五个Codex会话后，上下文切换就开始明显吃力。人会忘记每个会话正在做什么，也会在几个终端之间来回追进度。Agent 没停，人不行了……

他们后来没有继续研究"怎样同时盯住更多窗口"，而是把管理单位从会话换成了Issue。

每个任务有独立工作区，运行规则写在版本控制内的WORKFLOW.md，任务状态由系统维护。部分内部团队在最初三周里，已合并PR数量增长了500%。

对个人来说，更没必要一上来就搭一套Symphony……把流程固定下来，已经能解决大半问题：

```
Issue/任务文件 → 独立 worktree → 查找相关代码 → 实现
→ 自动检查 → 独立审查 → 人工验收 → 合入
```

查找、实现和审查最好不要全塞在同一个上下文里。负责搜索的 Agent 只需要告诉主任务相关文件、接口和风险；实现 Agent 按边界改代码；审查 Agent 只看需求、测试和 diff，专门找回归与遗漏。

并行任务要分开worktree，否则两个 Agent 同时改一份本地文件，很可能不停地冲突和误覆盖。

Claude Code 与 Codex 现在都直接支持worktree，这已经不算什么高级玩法，算是并行改代码的基本隔离。

我更建议个人先从两个实现任务加一个独立审查开始，只要任务会同时碰同一个核心模块、同一份数据库迁移或同一个公共接口，就继续减，别给自己添麻烦……

最后还是不得不提到提示词……不少提示词看起来很专业，其实是在反复提醒 Agent 做确定性的工作：修改后记得格式化，别碰密钥目录，测试失败只看错误部分，完成前输出变更文件，页面报错时保存截图。

这些要求如果每次都必须执行，就不要指着模型"记得"……能写成普通脚本的写脚本，能放进 CI 的放进 CI，适合在工具调用前后执行的就做成hook。只有那些需要理解代码和作出判断、而且经常重复的流程，才值得做成skill。

Anthropic 的成本指南里有个很朴素的例子：与其把一万行测试日志全部交给 Claude，不如先用 hook 筛出包含 ERROR 的行，再把几百行相关内容送进去。模型没有变聪明，但上下文变得更干净，成本也更低了。

MCP 也是同样的道理，它适合读取经常变化的外部系统，例如 GitHub、Sentry、数据库或设计稿，但不是接得越多越高级。每多一个工具，就多一组权限、失败方式和上下文开销。

先接一两个确实能消灭高频人工操作的服务，后面的根据进展慢慢来。

Vibe Coding很容易制造一种错觉——今天生成了几十个文件、跑了很多个 Agent，效率一定提高了！

但其实代码行数、会话数和token消耗都只是过程，真正该记录的是这个任务花了多少人工时间，结果能不能一次接受，返工了几次，合并后有没有缺陷，出了问题能不能快速回退。

有时候Agent没把活儿干好，跟"咒语"没关系，跟并行跑了多少个Agent也没关系，关键是人要把活儿派清楚，然后别让需要审核的内容超过自己的肉脑子极限……

## 与 kfm 的对照（评审会话 · 2026-08-22 剪藏附注）

1. **「root 指令文件当目录用，别把项目知识全塞 AGENTS.md」——这是 kfm 文档纪律的直接背书**。文章：根文件 ~100 行只留命令/边界/入口，详细架构进结构化文档需要时再读；自动生成的上下文文件让解决率不升反增 20%~23% 成本。kfm 的 `AGENTS.md` 恰恰很薄（入口指示 + 两类维护规则），而 kernel/排障/契约等重内容全在 `docs/` 分目录——正是「当目录用」的形态。证据（2026-02 研究）支持「别让 Agent 付阅读费」，这点值得写进 9.0 的文档维护规则作引用。
2. **「把管理单位从会话换成 Issue」——heavily 印证 kfm 的信箱/评审机制**。文章说 Symphony 从「盯会话」转向「Issue 有独立工作区 + WORKFLOW.md 规则 + 系统维护状态」，合并 PR 增 500%。kfm 的信箱机制（跨线评审信、决策登记、收敛判据、状态机）本质就是「按 Issue/任务管理而非按会话」——且我们已经在多线并行里踩过「会话边界崩了→产线死」（茉莉）。文章给了独立证据：人没法同时盯 3-5 个会话，但可以盯 Issue。
3. **「查找/实现/审查分上下文」= kfm 的评审线独立**。文章：审查 Agent 只看需求、测试、diff，找回归与遗漏。这正是 kfm 把评审会话独立出来、与 NA/9.0 各线分离运行的道理——审查与实现不塞同一上下文，防止自作自受。也解释了为什么「让生成者自查」不可靠（跟「让系统扣的 2.5s 假像」同属观察者/自我验证局限）。
4. **「确定性工作→脚本/CI/hook，判断性重复→skill」——kfm 的链路脚本/门禁已这么干**。文章：能写成脚本的写脚本、能进 CI 的进 CI、工具调用前后做成 hook，只有需理解+判断+常重复的才做 skill。kfm 的 check 链路、gen-* 脚本、git 卫生钩子全是这个分类的落地；反例是信箱计数一度靠手工（gen-agent-inbox 生锈 → 计数滞后被 MECH-FLOW-13 抓住）。这条敲打很及时。
5. **「人工验收是瓶颈，别让审核量超过肉脑极限」——kfm 当前真实短板**。文章：多 Agent 看起来生产力爆炸，最后都要人来验收；Agent 没停，人不行了。这正是 kfm 现状：两条线 + 评审线的产出全压给用户一个肉脑做决策，而这次「读不懂了」的信号就是肉脑到了极限。文章建议把流程固定下来 + 用 Issue 而非会话做单位——kfm 已经走在路上，需要的是把「人工验收」这层也做成可读的文档面（这或许就是 9.0 该补的一格）。
6. **caveat**：所有数据（83% token、500% PR、20%~23% 成本）均为文章转述的单一实验/内部数据，非独立复现；Token 用字符数近似估算（作者自己标注）。当方向性参考，不当精确论据。
