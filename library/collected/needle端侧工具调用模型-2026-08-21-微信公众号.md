## 一、动机：想要 AI，但不想烧 API

博客首页终端打算加个「AI 助手」味道：访客输入自然语言（如「找一下
deepseek 的文章」），终端自己检索、列出结果、附链接。

最省事是调云端 LLM API 做意图识别，但被劝退：①每个访客每次提问都烧
站长额度；②请求要出网，与「纯静态博客」气质不符。目标是**推理发生在
访客自己的浏览器里**。答案：needle（cactus-compute/needle）。

## 二、needle 是什么

Cactus Compute 出的**工具调用（tool-calling）专用小模型**，needle2：

- 45M 参数，量化后整个模型是 14MB 的 `.cact` 文件；
- 一个推理 session 约 28MB RAM；
- 输出被**字节级语法约束**：根据声明的 tools JSON 编译出解码文法，
  模型只能吐出合法的 JSON 调用，结构上不可能写坏；
- 自带 confidence gating：答不了返回空调用，失败模式是**「拒答」而不
  是「乱执行」**。

不做闲聊、不写散文，唯一工作：读 query，从声明的工具里挑一个，填好
参数，吐回来。恰好是「终端命令路由」需要的全部能力。

## 三、架构：三个文件的事

1. **文章索引**：Hugo 构建时生成 `index.json`（标题/标签/摘要/链接），
   终端搜索函数在 JSON 上做关键词匹配——needle 不负责搜，只负责**决定
   搜什么**。
2. **tools JSON**：向 needle 声明博客提供的能力（`search_posts` /
   `list_recent_posts` / `list_posts_by_tag` / `describe_post` 四个工具）。
   官方反复强调「describe your tools well is the whole game」——工具
   描述写得好，路由就准。
3. **Web Worker**：推理在 worker 跑，主线程 UI 不卡，可转等待动画、
   响应 Ctrl+C（销毁 worker 重建）。worker 内部三行核心调用：
   `needle_load` 载权重 → `needle_init` 传 system prompt + tools →
   `needle_complete` 一问一答。
4. **懒加载**：没有一个模型随页面加载。终端启动只拉几十 KB 索引；
   needle2 的 14MB 等访客第一次输入才下载；配合 `Cache-Control:
   immutable` 强缓存，二次访问零流量。真实成本：看文章的人零流量，
   玩 AI 的人花 14MB。

## 四、踩坑实录

### needle1 的「中文友好」是误会
needle1 是 22MB Rust/WASM 版，看似能处理中文——直到翻开词表：8192
词元，**一个 CJK 字符都没有**。它是纯字节级 BPE，所谓中文能力其实是
「把 query 的字节原样抄进参数」，抄回的关键词恰好命中搜索。代价是
偶尔抄坏（`search_posts("縠")`、`search_posts(" DeepSeek 繠")` 这类
乱码）。英文部分字节稳能救回。这不是懂中文，是运气好。

### 一行 locale 救回 decode 失控
needle2 中文输入直接现原形：拒答或 decode 失控烧光 token 预算
（`tool call truncated: token budget exhausted`）。官方只认英文输入
（query 先翻英文），locale 写死 `en-US`——别的值配上英文 query 会让
decoder 说到 token 预算耗尽。中文 query 走 Chrome 端侧 Translator API
先翻英文再喂，不出网不花钱，翻译痕迹打一行提示。

### 模型不够，规则来凑
45M 模型总有边界，体验问题靠薄规则补丁兜底：
- **拒答改写**：空调用 `[]` 改写成「没听懂，试试更具体的说法」；
- **指代消解**：「介绍第一篇」映射到上次搜索结果，不进模型；
- **复合指令**：「找 qemu 文章并介绍第一篇」按连接词拆开顺序执行；
- **搜索重试**：模型提取的关键词搜不到，拿原始输入再搜一次——专治
  字节抄串。

### 语义兜底：sem 命令
关键词匹配有盲区（「降低大模型调用成本」搜不到讲 Prompt Caching 的
文章），加 `sem` 命令：transformers.js 端侧跑 bge-small-zh（24MB 量
化 ONNX）算向量相似度。坑：**hf-mirror 没有 CORS 头**，浏览器 fetch
模型文件直接被拦——模型必须自己托管，运行时镜像兜底这条路不存在。

## 五、这颗模型能跑在什么硬件上

28MB RAM 决定 needle2 甜点区：**手机、树莓派、低配盒子**，以及一切
现代浏览器。官方数据推断移动端 CPU 可数百 tok/s，工具调用一次输出
几十 token，体感秒回。但 MCU 上不了（ESP32-S3 8MB PSRAM 差近 4 倍）。
这类设备的可行架构是 **hub + 执行端**：needle 跑浏览器/主机做路由，
设备经 WebSocket / BLE 接命令干活；只要固定命令（如「亮度调低」），
乐鑫 ESP-Skainet 甚至可片上离线识别。

## 六、成本结构

模型文件合计约 60MB（needle2 14M + needle1 22M + sem 24M），全懒加
载按需拉取，多数访客实际只下 needle2 一个；推理零 API 费用；数据与
query 不出访客浏览器。适合「固定工具集 + 自然语言入口」场景。官方给
了 LoRA 微调，用自己的工具 traces 练一轮路由更准。

**源码位置**：未单独开源，挂在博客静态文件里——主逻辑 `/lib/blog-ai.js`
（<30KB）；演示页 `/html/terminal/`；数据源 `/index.json`；模型文件
来自 cactus-compute/needle 发布 + 自托管 bge-small-zh 于 `/lib/sem/`。

## 与 kfm 的对照（评审会话 · 2026-08-21 剪藏附注）

1. **与 nz 的路线同构**：nz「眼睛/手」将来需要自然语言 → 工具路由；
   needle 的「声明式 tools JSON + 结构约束输出 + 拒答而非乱执行」正是
   kfmv4 fail-closed 纪律的端侧版。**「结构上不可能写坏 JSON」应作为
   工具路由实现的硬目标**，而非靠运行时校验兜底。
2. **工具描述的权重**：「describe your tools well is the whole game」——
   与 nz 的 tools/coords 契约同源：路由质量取决于接口声明的质量，不是
   模型大小。
3. **层级分工的实证**：模型做「决定搜什么」，索引/规则层做执行——
   对应 kfm 的「模型管意图，机械管纪律」。规则补丁（拒答改写/指代消解/
   复合指令拆解/重试）与 nz 的骨架期「规则先立、模型后接」一致。
4. **懒加载 + 强缓存** 的成本观对 kfm 的端侧分发有参考（14MB 按需，
   二次零流量）。
5. **caveat**：needle1 的「伪中文」与 needl2 的 locale 陷阱提醒——端侧
   小模型的「能处理中文」要先查词表/测试才可信，别信文档字面。
