# kfm 即「产品理论换代」的活样本——对照笔记

> 来源对话：2026-08-22 评审会话。素材：知乎 chouheiwa《在 Vibe Coding 时代，
> 有哪些经典的产品理论仍然值得学习？》（剪藏于 `library/collected/vibe-coding时代经典产品理论-2026-08-22-知乎chouheiwa.md`）。
> 起因：用户读完剪藏后问「我们的项目是不是也在不自觉往这个方向走」，
> 评审会话的对照结论，留档备查。

## 结论

不是「不自觉往这个方向走」，而是 kfm 本身就是该理论的一个活样本——
文章作者从产品侧推导，kfm 从工具使用里撞出来，两条路汇到同一结论。

## 四个对照点（文章框架 → kfm 实据）

1. **本质/偶然复杂度分层 → 用户角色迁移**。用户自述「我不知道想要什么，
   只知道哪里不对」= 本质复杂度留在人侧；dsh / 各线 agent 吃掉偶然复杂度。
   用户当前职责已收敛为三件：提问题、做裁决、通知各线——constraint 从
   工程侧挪走后，人的活全部收拢到判断上。
2. **taste is evals → 评审线 + 链路门禁**。文章作者靠 Langfuse +
   LLM-as-judge 获得抓手；kfm 对应物：链路 check、提交门禁、考卷硬门
   （45/45 亲跑复现）、评审信。差异：kfm 的 evals 目前仍是人肉层
   （评审会话 + 用户逐笔过），自动打分层缺位——量一大即成为新瓶颈，
   是 9.0 之后值得认真想的缺口。
3. **Naur 理论构建 → 信箱机制**。茉莉线死于会话压缩 = 理论存在会话里
   的代价；信箱/评审链/决策登记 = 把理论外置成文档，新线 agent 靠文档
   接活而非靠记忆。kfm 是少数真的在还 Naur 那笔账的项目。
4. **Sherlock 测试 → 茉莉线处置**。用户判断「修复不值得，9.0 完成自己
   会复活」= 一次实战 Sherlock 决策：旧躯壳会被下一次版本更新覆盖，
   不救，资源投活路。

## 未对齐处（诚实记录）

- **分发面为零**：kfm 只服务用户一人。当下不是问题（自用生产工具），
  但若信箱机制/评审纪律未来要变成别人可用的东西，这是文章框架里唯一
  缺的一格。
- **evals 自动化缺口**：见对照点 2。各线产出「好不好」的判定目前无法
  脱离人肉，尚无自动判据层。
