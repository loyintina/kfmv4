# Agent 自动化真机测试能力——研究笔记

> 来源：2026-08-22 评审会话。起因：用户提出「我们缺的是让 agent 拥有自动化
> 真机测试的能力」，并点出「已进入默认支持读图的 API 时代，是不是能做更多」。
> 本文在 kfm 现有真机链路（NA 判卷分档 / report 回传通道 / 8022 隧道 / 已配
> 视觉模型）基础上做一次能力盘点与方向研究。

## 一、问题精确化：缺的到底是什么

NA 的判卷分三档（`kfm-na/AGENTS.md` 开发方法论）：

- **A 档考题先行**（纯逻辑：协议/网格/按键/手势/几何）——可自动化，已有
  变异抽检纪律（故意改坏答案看考题抓不抓得住）；
- **B 档答案先行钉住**（胶水/平台：Manifest/wgpu/生命周期）——对错是
  「系统让不让你活」，冒烟钉防退化，可自动化大半；
- **C 档感官判卷**（渲染手感/手势/中文 IME）——**判卷人是眼睛和手指，
  实拍即判卷**，自动化只覆盖可测的边角。

**缺口正是 C 档**：它是「视觉/手感」验收，目前必须真人拿真机跑一遍、
人眼判「对/不对」。同时评审端（本会话）没有真机，只能核代码 + 采信通报
口径，C 档的「实拍 PASS」对评审是黑盒。

所以问题不是「没有自动化测试」，而是：**C 档感官判卷无法脱离人的眼睛和
手指，且其证据（实拍）不可被评审复现/查看**。

## 二、已有基础（很多已经在，缺的是拼起来）

1. **帧缓冲就在 NA 手里**。NA 的 termview/渲染直接把像素画进 buffer，
   探针已经数过「非背景像素个数」（`output 后首帧非背景像素`）。意味着
   **渲染成的画面本身就是可序列化的图像证据**，零新增依赖。
2. **回传通道已存在**。`report.rs` 的 HTTP POST 直报 `127.0.0.1:8021/kfmv4/api/na-report`
   （手机侧 SSH 隧道对接、失败重试、宁重复不丢），加 logcat 双通道。
   目前只回传**文本行**，通道本身可承载图像证据。
3. **真机网络已通**。8022 隧道连手机 Termux；8021 对接 kfmv4。
   服务端 adb 反连不回去（NAT，`report.rs` 注释写死这个前提），所以自动化
   **必须从设备侧主动外送**，不能从服务器拉——这决定了架构。
4. **视觉模型现成**。kimi-code 已配 k3（image_in）+ 刚配
   `opencode-go/deepseek-v4-flash-vision-exp`（image_in）。判卷人可以是 model，
   不必是人类。
5. **手机端截图手段**：确认 `adb screencap` / `termux-screenshot` 未装
   （Android 16, termux 只有 ffmpeg）。但：app 可自dump 帧缓冲（见 1），
   需要系统 UI/IME 覆盖层时再补 `termux-api`（termux-screenshot）或
   `android-tools`（adb connect 自连）。

## 三、方向：让真机自己「看得见」并「评得动」

把 C 档判卷从「人眼实拍」换成「机器眼 + 机器判」的一条闭环：

```
设备侧动作（agent 通过 8022 下发 / 或 app 内驱动）
   → 采集证据（app 自dump 帧缓冲为 PNG；需要系统层再 screencap）
   → 送视觉模型判卷（"画面上是什么 / 是否符合预期状态"）
   → 判定结果 + 原始截图一并 POST 回 report 通道
   → 落盘 field-reports.log / 信箱，评审端跨隧道可查看、可复现
```

这一步做完，三件事同时解决：

- **C 档可自动化**：渲染手感/提示符/光标/IME 候选栏是否出现，可让视觉模型
  读图判定，不必真人盯；
- **评审端不瞎**：截图 + 判定落成文件，我（评审）能真看到「实拍」内容，
  而不只是相信「PASS」三个字——这正是评审盲区的解药；
- **review-prone 证据**：判定可回溯（哪张图、判了什么、对不对），
  踩到误判能查，符合 kfm「判卷要可复核」的基因。

## 四、两条采集路径（按需取）

| 路径 | 用什么 | 覆盖 | 成本 |
|---|---|---|---|
| **app 内自dump 帧缓冲** | NA termview 渲染 buffer → PNG（探针已在数像素，只差序列化） | NA 自己画的画面：提示符/光标/终端网格/拖柄/滚动 | 零新增依赖，确定性最好，**首选** |
| **系统/设备层截图** | `termux-api` 的 termux-screenshot 或 `android-tools` adb screencap（需 `adb connect` 自连） | 软键盘覆盖层、系统菜单、IME 候选栏、多窗口 | 需装小工具 + adb 自连配置 |

自dump 是 kfm-native 的第一优先（帧缓冲本就在、无新依赖、可确定复现）；
系统层截图只在需要看「系统 UI 叠加在 NA 之上」时再补。

## 五、判卷人的选择：视觉模型当「眼睛 + 尺子」

读完图，需要把「这是不是预期」转成可裁决结论。两个层次：

- **阈值判卷**（便宜、确定性）：预设可量化期望（如「光标块占 ≈288px」、
  「非背景像素 > 1000」），视觉模型或像素统计直接给布尔——A 档思路搬到视觉。
- **语义判卷**（贵、泛化）：给视觉模型一句「预期：提示符 xterm 样式 + 光标
  闪动；实拍：____」，让它描述+给结论。这就是 vibe-coding 文里
  「taste is evals 把『好』定义成可复现判据」的视觉版——**把『画面对不对』
  也成了一条判据**。

阈值优先（确定性、省 token、可复核），语义判卷只用于阈值定义不了的手感。

## 六、风险与边界（诚实列举）

1. **视觉模型会幻觉**：判「看起来对」不等于「行为对」。参考 A 档的
   **变异抽检**纪律——故意改坏一处再判卷，看视觉判卷人抓不抓得住。
   这是 C 档自动化的首要纪律，跟 A 档同根。
2. **单帧不足以证时序**：动画/闪烁/IME 伸缩是过程，一帧静图判不了。
   需要多帧/短视频（ffmpeg 已在手机端，可 `screenrecord`）。
3. **token / 成本**：每判一次送一张图，批量判卷会花钱。阈值判卷 + 只对
   疑似/关键帧送视觉模型，能压成本。
4. **证据文件管理**：截图落盘要有命名/路径纪律（跟 field-reports.log 同级），
   否则又变成不可检索的散件——参照「信箱统一目录」的教训。
5. **设备侧自动化的「驱动」仍是难点**：判卷容易，**制造出待判状态**（点
   tap、敲键、滑动手势来触发）才是自动化的另一半。NA 已有「按键注入的手」
   （眼睛与手设计），这条路已在铺。

## 七、下一步（建议，未动工）

1. 先做**最小切片**：NA 加「dump 当前帧为 PNG + 附元数据 POST 回 report
   通道」，验证能拿到图；再在评审会话侧用现成视觉模型读一张，确认闭环通。
2. 再定「帧缓冲 → PNG 序列化」在核心层还是壳层（遵守 multi-end-layering
   分层：渲染归壳，序列化归壳；核心层只出数据）。
3. 判定协议设计（阈值 vs 语义、证据命名、落盘位置）移到
   `experiments/真机测试/` 研究文件夹再展开——本笔记只是能力盘点，不当设计定论。
