# KFM v4 — 全屏卡片设计规范

> **版本**：v0.1
> **状态**：活跃设计提案
>
> 本文档描述 KFM v4 全屏卡片模式的设计。核心理念：全屏卡片是一张放大到全屏的普通浮卡，
> 不改变内容区的渲染逻辑和行为。所有的卡片内容（文件卡预览/编辑、终端卡、对话卡等）在
> 全屏模式下自然继承现有交互。
>
> **背景**：对比 Obsidian 等应用的编辑体验，KFM 当前编辑单文件的成本太高
> （左滑 → 右滑 → 卡片堆 → 确认投放 → 调整大小，共 5-6 步）。
> 全屏卡片模式将单文件编辑路径压缩为：左滑 → 点击文件，共 2 步。
> 两种路径（工作台模式 vs 快速编辑模式）并存，互不冲突。
>

## §0 核心理念

### 0.1 全屏 = 放大到全屏的卡片

全屏卡片不创建新的内容类型。它只是把一张已有浮卡的状态从 `active` 切换到 `fullscreen`：

- 尺寸从默认（155×68）撑满屏幕
- 四角光球隐藏（全屏不需要）
- 内容区自动撑满剩余空间
- 现有预览/编辑切换、输入框、滚动等行为完全不变

这意味着：**卡片的类型（文件卡、终端卡、对话卡）与它是否能进入全屏无关。** 全屏只是一个呈��层级的修饰。

### 0.2 唯一槽位

全局只有一个卡片能处于全屏态。任何新卡片进入全屏时，旧卡必须让位。让位规则：

| 旧卡来源 | 新卡来源 | 旧卡行为 |
|---------|---------|---------|
| 任意来源 | **文件树点击文件** | **完全关闭**（等同于点击浮卡 TR 光球 dismiss） |
| 任意来源 | **其他入口**（浮卡/卡片堆全屏按钮） | **缩回展开态浮卡**，记忆位置恢复 |

一句话：**只有来自文件树的点击操作拥有"替换并关闭旧卡"的特权。**

### 0.3 多文件工作台模式不受影响

全屏卡片不改变现有的浮卡、卡片堆、右滑投放、AI 对话等交互。这些卡片浮动在全屏卡片上方，可正常拖拽、切换焦点、关闭。

## §1 交互流程

### 1.1 文件树 → 全屏（新路径）

```
用户操作                      系统响应
─────────────────────────────────────────────────────
① 左滑呼出侧栏               → 侧栏打开，文件树可见
② 点击文件行                  → 光标移动到该行 + 侧栏关闭
                              → 创建展开态浮卡（不渲染在常规位置）
                              → 直接拉升到全屏
```

- 与现有右滑投放不冲突（点击 vs 右滑，手势路径天然隔离）
- 点击文件夹：光标移动 + 展开/折叠（不触发全屏）

### 1.2 全屏下的操作

| 操作 | 行为 |
|------|------|
| 点击退出按钮（全屏专属） | 退出全屏，回到展开态浮卡，位置沿用记忆的随机投放位置 |
| 左滑呼出侧栏 | 侧栏打开，文件树可见 |
| 侧栏点击另一个文件 | 旧全屏卡完全关闭，新全屏卡出现 |
| 右滑投放浮卡 | 浮卡正常出现在全屏卡片上方 |
| 卡片堆操作 | 卡片堆正常在全屏卡片上方 |
| AI 对话 | 底部输入栏正常操作 |

### 1.3 未来：浮卡/卡片堆全屏入口

为每张浮卡左侧边沿增加一个全屏按钮（光球）。点击后：
- 当前无全屏卡片 → 该浮卡进入全屏态
- 已有全屏卡片 → 旧卡缩回展开态浮卡，新卡顶上

## §2 状态机扩展

现有浮卡状态机：

```
compact → expanding → active ⇄ editing
```

扩展为：

```
compact → expanding → active ⇄ editing
                       ↓（进入全屏：点击文件/全屏按钮）
                     fullscreen
                       ↓（退出全屏：退出按钮）
                     active（记忆位置恢复）
```

### 2.1 FloatingCardItem 新增属性

```typescript
// 新增属性
_fullscreenSaved: { left: number; top: number; width: number; height: number } | null;
// 全屏前的浮卡位置，退出时恢复。不存在则随机生成。
isFullscreen: boolean;
```

### 2.2 全屏态的行为变更

| 属性 | 变化 |
|------|------|
| 尺寸 | 固定为全屏（`window.innerWidth` × `window.innerHeight - 输入栏高度`） |
| 位置 | `left: 0, top: 0` |
| 四角光球 | 隐藏 |
| 退出按钮 | 显示（全屏专属，位于右上角或标题栏） |
| z-index | 固定，不参与焦点竞争 |
| 拖拽 | 禁用（全屏不需要） |
| 缩放 | 禁用 |

## §3 层级策略

### 3.1 z-index 分区

```
10     背景层
20-49  全屏卡片层（固定，不随交互提升）
50+    浮卡/卡片堆/光球（正常 z-index 竞争）
```

全屏卡片固定在一个中间层级：
- 高于背景
- 低于浮卡和交互控件
- 底部输入栏高于全屏卡片

### 3.2 原因

全屏卡片是"可交互背景"角色。如果它被提到 z-index 最高，就会遮盖其他浮卡，
失去多卡片共存的优势。固定层级让它始终作为背景存在。

## §4 文件树交互改造

### 4.1 现状

`tree-swipe.ts` 处理文件行的右滑操作（投放临时卡片堆）。
点击文件行触发 `select-file` 命令，光标移动到对应行。

### 4.2 改造

在点击事件处理器中增加逻辑判断：

```
点击文件行:
  ├─ 执行现有光标移动逻辑（不变）
  └─ 如果目标是文件（非文件夹）:
       ├─ 关闭侧栏
       └─ 触发全屏卡片创建流程
```

手势隔离保证点击和右滑不会打架：
- 点击（pointerdown + pointerup 位移 < 阈值）→ 全屏路径
- 右滑（pointerdown + pointermove 位移 > 阈值）→ 现有卡片堆路径

## §5 实施计划（分阶段推进）

### Phase 1 — 核心链路（最小可验证）

**目标**：从文件树点文件 → 出现全屏卡片 → 退出回到浮卡。

| # | 事项 | 涉及文件 | 验证方式 |
|---|------|---------|---------|
| 1 | 文件树点击文件分支：触发全屏卡片流程 | `tree-swipe.ts` / `tree-render.ts` | 点击文件，侧栏关闭，全屏卡片出现 |
| 2 | 全屏状态常量 + `FloatingCardItem` 属性扩展 | `floating-card.ts` | 编译通过 |
| 3 | 全屏态渲染：尺寸撑满、四角光球隐藏、退出按钮 | `floating-card.ts` | 全屏卡无光球，有退出按钮 |
| 4 | 唯一槽位逻辑：旧全屏卡关闭 + 新全屏卡出现 | `floating-card.ts` | 点文件A → 全屏；点文件B → A关闭，B全屏 |
| 5 | 全屏退出按钮 → 缩回展开态浮卡（记忆位置） | `floating-card.ts` | 点击退出，回到 155×68 浮卡 |

**验收标准**：左滑 → 点文件 → 全屏出现 → 点退出 → 回到浮卡。完整闭环。

### Phase 2 — 交互完善

**目标**：全屏模式下其他卡片协调工作。

| # | 事项 | 涉及文件 |
|---|------|---------|
| 6 | z-index 固定层级（不参与焦点竞争） | `floating-card.ts` |
| 7 | 全屏→侧栏联动（进入时关，左滑可开） | `floating-card.ts` + `tree-render.ts` |
| 8 | 全屏下右滑投放、卡片堆、AI 对话正常 | 验证性，无代码改动 |
| 9 | 底部输入栏保持可见 | CSS |

**验收标准**：全屏打开后，右滑可投放浮卡，卡片堆可呼出，AI 对话可输入。

### Phase 3 — 推广到所有卡片

**目标**：任何浮卡/卡片堆卡片都能进入全屏。

| # | 事项 | 涉及文件 |
|---|------|---------|
| 10 | 浮卡左侧边沿全屏按钮 | `floating-card.ts` |
| 11 | 非文件树来源的全屏替换逻辑（旧卡缩回） | `floating-card.ts` |
| 12 | 卡片堆卡片的全屏入口 | `card-stack.ts` |

**验收标准**：随便一张卡，点全屏按钮进入，点退出回到原位。

## §6 开放问题

### 6.1 全屏卡片的退出按钮位置

当前设计放在右上角或标题栏右端。需要实际渲染后确定视觉位置是否自然，尤其在不同卡片类型下是否遮挡内容。

### 6.2 点击文件 → 全屏之间的视觉过渡

从侧栏关闭到全屏卡片出现的瞬间，是否需要动画过渡（如卡片从文件行位置飞入全屏）？还是直接切？建议 Phase 1 先直接切，Phase 2 再考虑动画。

### 6.3 折叠屏/横屏适配

全屏卡片的尺寸是 `window.innerWidth × window.innerHeight - 输入栏`。旋转屏幕时 ResizeObserver 能否平滑过渡？现有的 `ResizeObserver` + `fit.fit()` 逻辑在终端卡中已验证过，理论上可用。
