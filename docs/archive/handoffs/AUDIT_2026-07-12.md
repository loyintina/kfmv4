# 审计报告 — 2026-07-12

> **背景**：上一个 agent 通过 `/tmp/*.js` 脚本对 `orb.ts`、`routes.ts`、`chat.ts` 进行字符串替换式补丁，
> 新增了会话管理、Provider 类型化、标题生成等功能。审计发现多处结构性问题。

---

## 审计发现

### 🔴 P0 — 必须修复

#### #1 会话选择器双重初始化 + 死代码

**文件**：`src/client/modules/orb.ts`

**症状**：
- `initOrb()`（L870）定义了 `initSessionSelect()` 函数，但**全项目零调用**——纯死代码
- `buildPanelContent()`（L438–477）独立创建了一套会话选择器，挂到同一个 `#orb-session-select-container`
- 两套会话管理的变量互不相通：
  - `initOrb()` 维护 `activeSessionId`、`sessions: Session[]`、`loadSessions()`、`updateSessionSelect()`
  - `buildPanelContent()` 用局部变量独立加载 sessions，不读 `active-config.json`，不更新 `activeSessionId`

**影响**：UI 上的会话选择器（来自 `buildPanelContent()`）切换会话时，`initOrb()` 的 `activeSessionId` 不会同步更新；`saveSession()` 和 `doSend()` 依赖 `activeSessionId`，可能导致保存到错误会话。当前靠 `kfm-session-change` 事件桥接勉强工作，但脆弱。

**修复方向**：删除 `buildPanelContent()` 中的独立会话选择器，让 `initSessionSelect()` 在 `buildPanelContent()` 之后由外部调用；或者反过来，删除 `initOrb()` 中的死代码，让 `buildPanelContent()` 的会话选择器承担全部职责并正确回写 `activeSessionId`。

---

#### #2 `kfm-session-change` 事件监听器重复注册

**文件**：`src/client/modules/orb.ts:911-929`

**症状**：两个几乎相同的 `window.addEventListener('kfm-session-change', ...)` 连续注册：
- L911–916：更新 `activeSessionId` + `updateSessionSelect()`
- L919–929：更新 `activeSessionId` + `updateSessionSelect()` + 保存到 `active-config.json`

注释分别写"监听外部会话变化"和"监听配置卡的会话变化"，但监听的是**同一个事件**。

**影响**：每次会话切换，两个回调都执行——`activeSessionId` 被赋值两次、`updateSessionSelect()` 调用两次、`active-config.json` 被写一次。功能上目前能工作（幂等），但维护者看到两个重复监听器会困惑；如果未来一个回调加了副作用（如重新加载消息），会触发两次。

**修复方向**：合并为一个监听器，保留 L919–929 版本（含 `active-config.json` 写入），删除 L911–916。

---

#### #3 服务端 `/api/proxy/fetch` 是开放代理

**文件**：`src/server/index.ts:248-307`

**症状**：`POST /api/proxy/fetch` 接受 `{ url, method, headers, body }` 后直接转发，无任何 URL 白名单或域名限制。任何人可借此访问内网服务、云元数据端点（`169.254.169.254`）、或作为跳板攻击其他主机。

```typescript
// index.ts:264
const response = await fetch(url, {          // ← 任意 url
  method: method || 'POST',
  headers: { 'Content-Type': 'application/json', ...headers },  // ← 任意 headers
  body: JSON.stringify({ ...reqBody, stream: true }),
});
```

**影响**：SSRF（服务端请求伪造）攻击面。内网其他服务、localhost 端口、AWS/GCP 元数据均可被探测。

**修复方向**：添加 URL 白名单（至少限制为配置的 Provider baseUrl），或移除该端点改为服务端直连（当前 `chat.ts` 已经直连，代理端点可能已无人使用——需确认）。

---

#### #4 `/api/ai/models` 硬编码模型列表

**文件**：`src/server/ai/routes.ts:123-131`

**症状**：
```typescript
router.get('/ai/models', (_req, res) => {
  res.json({
    models: [
      { id: 'deepseek-v4-flash', name: 'DeepSeek V4 Flash', provider: 'opencode-go' },
      { id: 'deepseek-v4-pro', name: 'DeepSeek V4 Pro', provider: 'opencode-go' },
      { id: 'mimo-v2.5-pro', name: 'Mimo V2.5 Pro', provider: 'opencode-go' },
    ]
  });
});
```

不从 `providers.json` 读取。用户在 API 卡新增 Provider 后，模型列表不反映实际配置。

**影响**：API 卡和模型端点数据源不一致。用户困惑"为什么加了新模型但选不到"。

**修复方向**：改为从 `loadProviders()` 读取。

### 🟠 P1 — 应该修复

#### #5 `buildPanelContent()` 中会话选择器不恢复上次选中状态

**文件**：`src/client/modules/orb.ts:438-477`

**症状**：每次展开面板，会话选择器加载全部 sessions 后选中第一个（`sessionSelect.updateItems(sessions, sessions[0]?.value || '')`），不读取 `active-config.json` 恢复上次选中。

**影响**：用户切换会话后关闭面板再打开，选择器重置到第一个会话。但 `activeSessionId`（来自 `initOrb()`）仍然正确，所以发送消息会保存到正确会话——UI 和实际状态不一致。

**修复方向**：加载会话列表后先读 `active-config.json`，选中匹配的 session。

---

#### #6 `routes.ts` imports 结构散乱

**文件**：`src/server/ai/routes.ts:7-48`

**症状**：`add-title-endpoint.js` 脚本用字符串替换插入代码，导致：
- `import { readFileSync } from 'fs'` 和 `import { join } from 'path'` 在 L9-10
- `import type { WsServer }` 在 L48（夹在函数定义之间）

**影响**：可读性差，但编译通过。建议整理为标准 import 块。

---

#### #7 `orb.ts` 中 `Provider` 接口含 `apiKey` 字段

**文件**：`src/client/modules/orb.ts:35-41`

**症状**：客户端 `Provider` 接口定义了 `apiKey: string`，`providers.json` 中的 API 密钥被加载到浏览器端 `providers: Provider[]`。虽然该变量仅用于 Provider 名称/模型列表的 UI 展示（`apiKey` 字段未被客户端使用），但密钥仍在浏览器内存中。

**影响**：XSS 可泄露 API 密钥。攻击面较小（当前 apiKey 字段在客户端未被读取），但违反最小权限原则。

**修复方向**：客户端 `Provider` 接口去掉 `apiKey` 字段，或服务端 `/files/read` 端点在读取 `providers.json` 时剥离敏感字段。

---

### 🟡 P2 — 技术债务

#### #8 大量静默 `catch {}` 块

**文件**：`orb.ts`（多处）、`routes.ts`（L18-20）、`chat.ts`（L43-45）

**症状**：`catch {}` 和 `catch { /* ignore */ }` 遍布代码。网络请求失败、JSON 解析失败、文件读取失败全部静默吞掉。

**影响**：生产环境问题无法排查。建议至少 `log()` 输出错误上下文。

---

#### #9 `buildPanelContent()` sessions 排序不一致

**文件**：`src/client/modules/orb.ts:473`

**症状**：
- `initOrb()` 的 `loadSessions()` 用 `new Date(b.updatedAt).getTime()` 降序排列
- `buildPanelContent()` 的 session 加载用 `a.label.localeCompare(b.label)` 字母序排列

**影响**：两个会话列表排序不一致，不过目前 `buildPanelContent()` 的会话选择器是实际可见的那个。

---

#### #10 `add-session-logic.js` 脚本使用 `(p: any)` 类型

**文件**：`/tmp/add-session-logic.js:12`

**症状**：补丁脚本中 `providers.find((p: any) => p.id === saved.providerId)` 引入了 `any` 类型逃逸。虽然补丁已被后续 `fix-any-types.js` 覆盖修正，但补丁链的存在本身就是技术债务信号（见 INVARIANTS 心法 7）。
