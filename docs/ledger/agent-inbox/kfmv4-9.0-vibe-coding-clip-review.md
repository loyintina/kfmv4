## 建议一：root 指令文件「当目录用」，别把项目知识全塞进 AGENTS.md

- **文章证据**：OpenAI 百万行代码项目早期用「一份巨型 AGENTS.md」后来放弃，
  改为根文件 ~100 行只留命令/边界/入口，详细架构进结构化文档、需要时再读。
  2026-02 研究（SWE-bench Lite + CTXBench）：自动生成的上下文文件在多数组合
  里**没有提高任务解决率，反而让平均执行成本 +20%~23%**。
- **kfm 现状**：`AGENTS.md` 目前很薄（入口指示 + 两条维护规则），重内容在
  `docs/` 分目录——已是「当目录用」形态，且与文章一致。
- **建议**：把「AGENTS.md 只回答四件事（项目怎么运行 / 哪些边界不能碰 /
  无法从代码发现的口头约定 / 怎样才算完成），其余进专门文档并从这里指过去」
  写进 9.0 的文档维护规则作显式说明，防止未来某线把它写成百科全书。附一条
  反模式：不要定期让 Agent「重新总结整个项目」后不检查地覆盖原文件。

## 建议二：管理单位从「会话」换成「Issue/任务」，并正视人工验收瓶颈

- **文章证据**：OpenAI Symphony 项目实测多数工程师同时盯 3-5 个 Codex 会话后
  上下文切换明显吃力；他们放弃「盯更多窗口」，改为**管理单位从会话换成
  Issue**——每任务独立工作区、规则在版本内 WORKFLOW.md、状态由系统维护，
  部分团队三周内合并 PR +500%。文章同时强调：最后都要人工验收，别让需要
  审核的内容超过人的肉脑极限。
- **kfm 现状**：信箱机制（跨线评审信 + 决策登记 + 收敛判据 + 状态机）本质上
  已是「按 Issue 而非按会话」管理；我们也在多线并行中踩过「会话边界崩→产线死」
  （茉莉线死于会话自动压缩）。缺的一格是**人工验收这层还没有文档面**——两条
  线 + 评审线的产出目前全部压给用户一个肉脑做决策（用户已有「读不懂了」的
  信号）。
- **建议**：在 9.0 的评审/信箱设计中，补一条「**人工验收作为一等文档动作**」——
  即把「这封信/这批改动由谁验收、验收什么、验收判据是什么」也在信箱里显式
  记录，让验收不再是无痕的肉脑动作，而是可回溯的一步。具体形态请 9.0 线按
  现有信箱 schema 评估，评审不预判实现。
