## 总评

作为会前酝酿记录，质量显著高于平均水平：用户诉求逐条落地、每个拍板都带依据与代价、
接口细到可外包、遵守修订注纪律。主要不足集中在一处：**离「按论文彻底组件化」的落地

## 做得好的

- **议题 1 分层是成熟判断**：渲染宿主进内核（性能热路径不被间接化）、布局插件化
  （收益最大点）、动画半插件手势内核——收益/代价/对齐三栏俱全，没盲目照搬
  「一切皆插件」。
- **tmux 语义纠正漂亮**：「布局只有'卡片摆放'一种语义，tmux 是一张全屏卡片」——
  用语义分层消解「浮卡/tmux 两种全局模式」的伪需求，是真收敛。
- **池系统「箭头只向下」用数据结构硬约束**（基础池条目没有指向组合的字段）——
  符合「能结构强制的不用纪律」。
- **对话卡「为什么这么薄」论证有力**：多实例免费 / Room 不改卡 / 互相看到浅层化，
  每条都有理由。
- **终端卡三层拆分的复用场景意识**（日志/录像/眼睛系统）与 vision.md 哲学一致。

## 主要问题

### 高 1｜论文机制只抄了形，缺「插拔回滚」与「派发模式」

用户诉求 3 要求「每个插件的入口出口、上下文管线、依赖、提供、**插拔方法**都写清」。
两个组件契约的入口出口表只有 provide/inject/emit/on：

- **没有卸载/回滚语义**：终端卡只写「dispose 渲染器 + 关闭会话」六个字；对话卡只有
  「拔 DOM 留服务」。论文独门功夫是**可逆效果**——apply 注册了什么、unload 逆序
  回滚什么、哪些失败钉死不重试，一个字没提。
- **没有事件派发模式**：`emit terminal/output` 只写事件名。KFM-NA 规格书 §4.3 钉死
  「**派发模式即公开契约**」（Emit/Serial/Bail/Waterfall 是事件契约的一部分）——
  9.0 连这个概念都没出现，事件契约不完整。

### 高 2｜与 KFM-NA 规格书 v1 零交叉引用，后者有现成答案

`../../../experiments/dsh-na/na/plugin-architecture-spec.md`（v1 定稿）就在同工作树，已解决 9.0 缺的东西：
ctx 分层（§4.2）、**获取/发射两分**（§4.1，UI 域恰恰最需要——渲染输出是发射类，
不在回滚承诺内）、**状态存活规则**（§4.1，对应 9.0 议题 3）、**卸载三相 + 失败钉死**
（§4.3/4.4）、**插件设计页模板**（§8：身份/提供/依赖/生命周期语义/配置 schema/
事件派发模式/状态存活/契约测试清单）。9.0 的组件契约格式比该模板**简化过头**，
正好丢掉了生命周期语义与状态存活。两线是同一理论的两个落地点，终局愿景是 NA 接管
kfm——契约语言现在不对齐，以后代价更大。

### 高 3｜termview-wasm 是全文档最重的隐含承诺，零论证

验收清单「三种实现（xterm.js / termview-wasm / headless）过同一套考题」背后是：
把 733 行 Rust 渲染器（`alacritty_terminal + fontdue + softbuffer`）编 wasm 进浏览器。
问题：① termview.rs 渲染后端 softbuffer 是 Android 专属（`target_os = "android"`），
wasm 端没有，「同一个 termview 编 wasm」不成立，等于重写渲染器；② 浏览器事件循环
模型与 winit 完全不同，kfm-na 刚拍板的「同步 unload + 事件循环任务队列」在浏览器里
要重设计。此句至少应升级为待讨论议题，附可行性论证。

### 中 4｜compact「拔 DOM」的接口归属不清

渲染底座分层说「渲染宿主（DOM 容器）在内核」——那「拔 DOM」是内核动作还是卡壳
插件动作？契约 №1 说 compact 语义「写进契约」，但没写清是卡壳调内核 API 还是卡壳
自己的效果。不钉死，布局插件/渲染宿主/卡壳三者的卸载责任会打架。

### 中 5｜session-store 提前回答了议题 3，未标注

契约 №2 把 `session-store` 当 inject 服务用——等于默认它是长寿命内核服务（论文
「状态存活规则」），但议题 3「状态与持久化放哪」还挂着待讨论。契约与议题不同步，
后面讨论议题 3 时会被「契约已经定了」绑架。

### 低 6｜索引结构混乱

「议题」与「组件契约」两套编号并行（议题 2 标题下装着议题 1 下钻 + 三个契约 №），
待讨论列表 2/3/4 与正文推进状态对不上。酝酿期可容忍，转正进 9.0 设计地图前理清。

### 低 7｜需求判断直接记录即可（已按用户反馈修正）

「日志卡几乎没用过」是用户第一手使用事实，是需求输入，无需证据面——本文档直接作为
已拍板需求记录即可。唯一保留的轻量建议：用户诉求 1 说「现在在使用中渐渐清晰」，
这个「渐渐清晰」的过程可以随手记进文档（哪怕一句话一条：哪些常用没入口），
把已知的需求写下来，不是去验证。
