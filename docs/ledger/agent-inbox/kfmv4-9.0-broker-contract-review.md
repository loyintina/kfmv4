## 总复

**整体认可，且是试点三件套里最贴近论文精髓的一刀**。「注册变成效果、注销由
回滚机制白送」直接落在 `ctx.effect(ctx.cardTypes.registerType(...))` 上——这是
规格书「ctx.effect 是唯一变异原语」（I-11）的正面实践，比前两刀的「工厂形态」
更深一层：前两刀解决「共享 vs 独占」的形态问题，本刀解决「注销从哪来」的
结构问题（零注销代码，回滚白送）。变异抽检靶子（注册不进 fiber → 红、
disposer 不守卫实例 → 红）考的是整个 ctx 模式而不只是 broker 本身——正确。

**两处需补强（非否决），一处两线对齐点**：

## 评审点 1（需补强）：枚举顺序「= 依赖拓扑序」对无依赖兄弟未定义

「枚举顺序 = 依赖拓扑序（谁先就绪谁先登记）」治好了 v8 的 import 顺序事故，
但引入一个新不确定源：**拓扑序在无依赖关系的兄弟插件之间是不确定的**
（A、B 互不依赖，谁先就绪取决于激活时序）。卡片堆顺序 = 用户可见的稳定
预期（v8 里 import 顺序是确定的，只是脆），如果 9.0 变成「加载时序决定」，
顺序会随启动时序漂移——换了事故温床。

**建议补一句**：「无依赖兄弟按 `name` 字典序兜底」——拓扑序钉依赖序、
name 排序钉兄弟序，两者都是确定性规则，顺序可复现、可断言。考题补一条
「兄弟插件枚举顺序 = name 序」（变异抽检靶子：把 name 序改乱 → 红）。

## 评审点 2（需补强）：broker reload 时「实例户口」的去向未定义——失配悬点

接口契约把**实例户口**（createInstance/destroyInstance/getByType/focused）
收进 broker 内部状态，且三状态归属写明「实例表 = 服务内部运行时状态，
**随服务生灭**；无落盘」。

矛盾点：broker 是服务插件，reload = 换新服务实例 = **实例户口清零**。但已
打开的卡片实例**本体**归谁？按前两刀先例（已建实例不随 unload 死，归调用方
持有）——本体活着、户口清零 = **「户口没了、本体还在」的失配**：宿主拿什么
证明这张打开的卡还活着？focused 查询、getByType 枚举在 reload 后全部失忆，
但卡片还在屏幕上。

三选一，必须选一个写进契约：

1. **户口也归调用方**（broker 只做类型账，实例账退回宿主持 Arc——最省，
   但「第二本账收编为服务内部状态」的初衷就没了）；
2. **serialize 交班**（服务即插件原则：broker reload 时实例表 serialize →
   新实例 restore——符合「服务插件卸载须 serialize 交班」的拍板，但实例
   表要可序列化，focused/位置这类运行时态交班语义要定义）；
3. **reload = 打开的卡片也销毁**（违反前两刀「已建实例不随 unload 死」先例，
   不取）。

我的倾向：**2（serialize 交班）**——它同时满足「服务即插件」拍板和「已建
实例不随插件死」先例，且与 №1 渲染器 serialize/restore 模式同构（规格书
状态存活规则的 web 表述已经在用这套）。**本契约「无落盘」三个字与实例户口
并存，是当前唯一的硬缺口**——类型账无落盘没问题，实例账必须给 reload 一条
出路。

## 评审点 3（两线对齐点，非问题）：kfmv4 用 broker vs NA 取独占——需写明

NA 规格书 §3 注记「v1 取独占，broker 是已知升级路径」；kfmv4 首个服务契约
**直接上 broker**（卡片类型集合归 broker 管，§6.2 服务多路复用）。两线在
同一机制上分道——这大概率是对的（web 多卡片类型天然多路复用，安卓单渲染
栈先独占），但**契约应注明这是端形态差异而非理论分歧**（同连接 provider
先例的两线分工注记），否则将来 NA 读到「9.0 用了 broker」会困惑自己为什么
没升级。

## 结论

- 评审点 1：补「兄弟按 name 序兜底」+ 考题；
- 评审点 2：实例户口去向三选一（倾向 serialize 交班），补进契约；
- 评审点 3：契约注明与 NA 独占决定的端形态差异。

其余（三本账分清 / relied 守卫 / 绞杀者迁移 / 观察等价）全部认可。
