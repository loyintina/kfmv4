## 二、资源画像(为何冲突)

mutants = 每突变体全量编译+全量测试,连续数十小时 IO 风暴
(rustc+rust-lld 磁盘读写为主,内存 0.6G 级);kimi = 内存大户
(单实例 0.3~0.6G 且随会话时长膨胀)间歇 IO。两者叠加即超

触发 page cache 挤占(用户已定位并移除),是第一轮的放大器。

## 【追记 2026-08-31 00:45】SIGSTOP 半截药教训——冻结必须闭环到 kill

§三 提案执行过程发现新机制,补录:

- **SIGSTOP 不释放内存**。08-28 中午对 mutants 整链 STOP 后,IO 立降
  (止血成功),但 0.6~2.5G 内存被冻结体持续锁死;残留 2 天后,叠加
  存活 kimi 的内存增长,**病灶转化为内存挤兑**(PSI mem full 92%),
  8021 node 二次卡死——与第一轮 IO 卡死不同源;
- **08-31 00:46 清场实录**(用户授权):kill 全部冻结体(dsh kimi 链 /
  mutants 链 / chrome 残骸 / 卡死 node)→ used 4.1G→1.1G(释放 3G),
  mem PSI 92→0,io PSI 21→0.1,负载 5.1→1.3,8021 重启后 8ms;
- **修订后的处置 SOP**:长任务失控时,SIGSTOP 仅作「临时止血」——
  必须在 IO/负载恢复后**立刻评估补 kill**(有价值留档者导出产物后杀,
  无价值直接杀),禁止冻结体过夜滞留。冻结 = 借内存,不是免费暂停;
- 另实录:08-31 凌晨 dsh 会话的浏览器测试链曾「杀后复活」——根因是
  kimi 进程挂在 shell 作业控制下,只杀子进程会被重新拉起;**必须连
  父(kimi/bash)一起停**,见 kfmv4-resource-hygiene-response.md 同轮追记。

——kfmv4(蔚然) · 2026-08-31(追记)
