## 一、探针已验证，但干净路径零漂移

探针 `__kfmNzTermCursor` 已用（baseline col=32, cellW=7.83）。我做了一个长句逐词漂移测试：
14 个词 / 26 个汉字，每词后读 `col`，对照期望 = 32 + 2×累计汉字数：

```
我们 +4/36  今天 +4/40  学习 +4/44  … → 机制 +4/84  全部 drift=0
```

**干净合成路径（compositionend → e.data → bridge.input）的光标列数学 100% 正确，0 漂移。** 网格回显也一字不差。

## 二、结论：真凶在真实 IME 事件序列，headless 抓不到

既然文字正确（20/20）、干净合成 col 零漂移，那真机上的漂移**只可能来自真实小鹤音形 IME 的事件序列**与我合成的不同——很可能是你代码注释里那句"此刻输入框里可能是拼音残影不是汉字"（compositionupdate 的中间态、拼音残渣、compositionend 后补发 input 的顺序），恰好让某一步的 col 累加吃错了长度。

**headless 模拟不出真实 IME 序列，这条在 headless 上到此为止**；要抓到真凶必须拿到 phone 侧的真实事件。

## 三、请加一样（两选一，都不大）

1. **优先·debug 事件流探针**：加一个 `?debug` flag（或环境开关），开的时候把每次
   `compositionstart / compositionupdate / input / compositionend` 的 `e.data` +
   `isComposing` + 时间戳，POST 到服务器落日志。我拿到**真实事件序列**就能在
   headless 原样复现漂移，精确定位是**哪一步的 col 累加错**，并给出"每词偏几格"的
   精确曲线——比你在真机上手测高效得多。
2. **次选·角标加 `col`**：在右下角标 `vp/rz/f/rp` 里追加 `col`。你真机打那段长句时
   直接读角标 col，看它是否从"每 2 列/字"漂开。能现场确认，但给不了精确序列。

## 四、为什么优先 1

抓一次真实序列，headless 即可复现 + 给出逐词漂移曲线 + 定位到行；以后你再也不用
一次次上真机试错。2 只能"确认漂不漂"，定位不了。
