## 裁决清单

### 裁决 1（高 1 · 插拔回滚 + 事件派发模式）——采纳

契约 №1/№2 的入口出口表确实只有 provide/inject/emit/on，丢了论文的独门功夫。
补齐方案，全部对齐规格书：

- **卸载三相**（§4.3）原样引入：停供 → 依赖者排空 → LIFO disposers。
  web 端 disposer 形态 = 各效果注册时返回的退订/注销函数，逆序跑；
- **事件派发模式进契约**：逐事件标注。kfmv4 client 是 JS 单线程同步事件循环，
  与 NA v1.1 同步基座同构——采纳裁决 3 的合并方案：v1 实现 **emit（同步观察）
  / serial+bail 合一（同步顺序短路）/ waterfall（委托链）**，parallel 缓建
  （有真实并发需求再加）；
- **dispose take-once**：web 端无 `FnOnce` 类型级保，用「disposer 置空 + 二次
  调用报错」等效，契约测试强制（忘回滚 → 测试红，同 §5 变异抽检思路）。

### 裁决 2（高 2 · 零交叉引用）——采纳，已补课

已通读规格书 v1.1。9.0 组件契约模板对齐 §8 九字段：身份 / 提供（标注注册表式
vs 有序链）/ 依赖 / 生命周期语义（apply 注册什么、unload 三相各做什么、失败
可见行为）/ 配置 schema（标注变更语义）/ 事件（派发模式）/ 状态存活 / 契约
测试清单 / 实拍判卷点。№1/№2 按此模板补齐，№3 起直接用新模板。

**两线分工的有意差异**（对齐而非照抄，供对账）：

- 执行层（§10 四原则）在 TS 下的映射：「编译期强制」= TS 类型 + 接口形状
  （无过程宏，inject 强制走 registry 路径错误两分 DeclaredButInactive /
  Undeclared + 契约测试）；其余三层同；
- 热插拔承诺边界（§4.1）web 端可略宽：插件 = ES module 可运行时动态 import，
  但 v1 同样只承诺「配置级启停 + 可逆卸载回滚」，不承诺运行中换实现——
  与 NA 对齐，防止「承诺做不到的事」；
- 布局插件化是 9.0 独有增量（NA 渲染底座含覆盖层管理在内核侧）：9.0 把
  「怎么布局」也降级为插件，内核只留渲染宿主（DOM 容器/事件总线/生命周期）。
  两线在「内核 = 基座 + 渲染宿主」上汇合，布局归属不同是端形态差异
  （web 多布局形态 vs 安卓单渲染栈），不是理论分歧。

### 裁决 3（高 3 · termview-wasm 零论证）——采纳，降级为待讨论议题

从契约 №1 验收清单撤下「termview-wasm 过同一套考题」，升级为待讨论议题，
附评审核出的两个硬障碍：① termview.rs 渲染后端 softbuffer 是
`target_os = "android"` 专属，wasm 端不存在，「同一个 termview 编 wasm」
不成立，等于重写渲染后端；② 浏览器事件循环与 winit 模型不同，NA 刚拍板的
「同步 unload + 事件循环任务队列」在浏览器侧要重设计。可行性研究方向：
网格/解析层（alacritty_terminal 纯逻辑部分）编 wasm + Canvas 重写渲染后端的
二分是否成立。议题未决前，契约 №1 的 A 档考题实现集 = {xterm.js, headless}。

### 裁决 4（中 4 · compact 拔 DOM 归属）——采纳，钉死

归属：**DOM 容器归渲染宿主（内核）**，「拔 DOM」= 卡壳调用宿主 API 摘除容器，
不是卡壳私自动作。卸载责任三分：宿主负责容器摘除与屏幕重绘；卡壳负责自身
注册效果（订阅/手势/服务登记）的逆序回滚；布局插件只持有几何状态，不碰
DOM。契约 №1 的 compact 语义按此改写。

### 裁决 5（中 5 · session-store 提前回答议题 3）——采纳，且议题 3 已拍板

程序批评成立。后续发展：议题 3 已在评审后由用户拍板解决，规矩三条——

| 类型 | 例子 | 归谁 | 卸载时 |
|---|---|---|---|
| 登记类（=获取类） | 订阅、手势、服务注册 | 插件挂到基座 | 逆序摘干净 |
| 发射类 | 像素、网络请求 | 扔出去收不回 | 不承诺撤销，摘容器即完 |
| 数据 | 会话、配置、池条目 | 数据管理器（服务） | 与插件无关 |

插件只持私有草稿（滚动位置、在途动画），随卸载蒸发；共享的、活得比插件久的、
要落盘的状态全归服务层——即 §4.1 状态存活规则的 web 表述。配套用户拍板：
**服务即插件**——系统里只有内核 ctx 不可插拔，服务与卡片同为插件，仅
provide 内容不同；服务插件卸载须过 relied 守卫（有依赖者禁卸）+ serialize
交班（热替换，复用契约 №1 渲染器 serialize/restore 模式）或账本在盘（真卸载）。
契约 №2 的 session-store 由此从「工作假设」转为「拍板结论」。

## 反向输入（9.0 侧可供 NA 对账的新结论）

- **池结构**（评审后用户拍板）：agent = 组合 `{prompt × model × 工作区}`，
  L0 基础池（provider/model/prompt/session）彼此不引用；**箭头只向下**，
  由数据结构硬约束（基础池条目无指向组合的字段）；引用即 relied。NA 的
  AI 会话插件（§3 第二批）落地时可对照；
- **池卡/对话卡/池系统三者分离**：管理 UI 与使用 UI 分插件，只通过服务与
  事件总线见面；多实例对话卡（fiber 多次实例化）+ isolate 作用域（§4.3）
  恰好支撑「每对话会话独立服务作用域」，与规格书 isolate 首用途同构；
- **布局插件化 + headless 布局**（同接口不渲染）：AI 无头自测路径，
  与 NA「无头浏览器插件（远期）」是同一需求的两种解法，可互相参照。
