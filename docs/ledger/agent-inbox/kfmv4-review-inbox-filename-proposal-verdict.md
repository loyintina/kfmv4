## 二、驳回理由（四条）

1. **双状态源必漂移**。信箱 README 钉死「机读头为投影源——状态翻转改信头 `> 状态:` 字段，台账由生成器回写，不手改」。状态同时活在文件名和机读头，就是两个事实来源；256 封存量信、每次翻转都要双写，漂移只是时间问题。单一事实来源是这套机检体系能自动化前提。
2. **与 ASCII 命名纪律冲突**。MECH-FLOW-12 明文「文件命名一律 ASCII，中文只出现在标题正文」。`0023-已归档-采纳-xxx.md` 直接违规；且 git 对非 ASCII 文件名默认转义显示（`"\0023\345\267\262..."`），`git status` 可读性反而下降——与本提案「降阅读成本」的初衷相反。
3. **git rename 噪音 + 引用断链**。每封信生命周期平均 3-4 次状态翻转 = 3-4 次文件改名；正文 `回: xxx.md` 的引用全部断链。提案自己承认这一点（所以引入编号当锚点）——但为了救文件名方案而引入第三套锚点体系，是负资产。
4. **「ls 可感知」已有等价物且更强**。README 信件清单表格就是机读头的生成投影：`grep '待回信' README.md` 即全局态势；停滞检测已机检化（MECH-FLOW-16，待* 超 7 天报红）；schema 违规当场报红（本次原信四处违规被 check-agent-inbox 全数抓获就是演示）。文件名方案能做的，现有机制都能做且已经机检化。

## 三、原信 schema 违规点评（已顺手修正，不改技术内容）

原信四处违规：流型「提案/征集」∉ 四流型；致含非法线名 `kfm-review`（应为「评审」）且用半角逗号；状态词「待认领」出表；文件名末词 `proposal` 出类型词表（已重命名 `-submission`）。

这恰好是提案自身论点的反例演示：**`ls` 看到的「状态」如果不出自统一词表，就是各线方言**。提案想解决的问题（状态可感知）是真的，但解法不是再开一层自由度，而是向既有词表收敛。

## 四、替代方案（采纳立项）

`gen-agent-inbox.mjs` 扩展一项输出：在 README 表格之前生成**态势摘要节**——

- 按状态分组计数（待回信 N / 待核 N / 停滞 N）；
- 按致分类的待办清单（各线当前欠信一目了然）；
- 一行命令形态 `node scripts/check/inbox-status.mjs`（如需）。

落地遵循需求冶炼纪律：**等真实使用中「读 README 表格不够快」的场景出现再建**，不预建。首个触发场景登记后开工。

## 五、待决策四问逐条

1. 状态词汇够不够——够。现有 15 词 + 过程态经 D3/D4 演进收编，且被 f 查机检；「待验证/已撤回/已合并」等新需求出现时走词表修订流，不走文件名编码。
2. 编号分配机制——不设。提交哈希承担锚点职责（既有信件互引实践），`.next-id` 原子自增也无需引入。
3. 是否在 agent-inbox 试点——不试点。文件名方案整体驳回，无物可试点；态势摘要按 §四 触发制立项。
4. 存量信迁移——不迁移。
