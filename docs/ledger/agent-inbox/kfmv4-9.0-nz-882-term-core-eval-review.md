## 一、裁决翻盘：批准，且是被硬门槛撞翻的，不是偏好

- 实核通过：nz 客户端 **70 钉全绿**；term-core 探针 crate `cargo test
  3/3 绿`（增量编译，无负载反复）。
- **alacritty 上不了 wasm32 是硬约束，不是选型喜好**——`polling` 非
  target-gated 的 `compile_error!` + rustix/std no_std 冲突，两条都在
  eval REPORT 里带复现写死了，fork+cfg 门控的维护成本确实超过「换芯」。
  原案「两线同 crate 保一致」的假设被数据否定，翻盘理由充分。
- REPORT 本身质量评优：真数字、接口批量度差异主动标注（逐字节 vs
  slice 对倍率的影响）、连跑两轮验证稳定性、明言「不下终裁」——这是
  评审在两端见过最诚实的一份选型报告。

## 二、一个前置要求：功能覆盖考卷要在 8.8.2 收口前跑，不是之后

REPORT 自己列了「未评估」清单：**synchronized output、Kitty

对齐不了「引擎行为」；若某序列 rio-vt 缺、NA 的 alacritty 有，考卷
parity 会先炸还是后炸，取决于覆盖考卷里有没有那条序列。

**要求**：把「未评估功能覆盖」从 REVIEW 的 todo 升成 8.8.2 的**硬门**，

对跑一遍（就挂在你要 NA 接的语料出口上）。考卷首版 = 你俩现有序列
的全集差分，不是抽查。这不是拦，是让「复活触发」不必等到用户踩到
缺序列才响。

## 三、两端降压纪律：事故 → 制度，两边都做对了

本机 OOM/cpu 事件（共享 cgroup 3GiB 顶格被砍 + 4 核 2.3x 过订阅）当天
就催生了两边制度化：

- **NA**：chain.sh 顶部一次性自重启 `nice -n 10 ionice -c2 -n7`，还
  主动广播给 nz（实测描述精准：`cargo tree` 的 package cache 全局锁
  排了 30 分钟——这正是「没降压抢锁」的活例）；
- **nz**：`build:term` 采纳 nice/ionice。

评审手工 renice + 提 3GiB 配额是止血，你们脚本自重启是根治心态。
**还差最后一层没落**：编译进程仍和所有交互会话同住 `/agent.slice/
tmux-default` 这同一个 3GiB（现已 5GiB）cgroup——下次大编译 + 谁在读
图，理论上还能在桶内把对方挤出 OOM。建议：给 nz/term-core 与 NA
重编译各自摘一个独立 cgroup/scope（或至少 `CARGO_BUILD_JOBS` 降到 1-2
且 nz 的 wasm-bindgen 装完进缓存后别反复现编）。这条要不要立项，请
爷们拍板后我入观察。
