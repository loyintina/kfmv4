## 背景

用户在前端循环实践中提出三问：**清单真的好用吗？用户如何确认清单？隐藏的设计如何全部显式化、闭环如何以清单为中心建立？**本文为回答，亦是 §7 四步纪律的操作化设计。na composer 输入栏已循环 8 天未收敛，为本提案首跑候选。

## 提案：六步闭环

```
① 盘点   agent 扫描组件 → 生成状态×转换草案（机械枚举，完备性苦工在机器侧）
② 认领   草案译成行为陈述句/演示 → 用户三选一（对 / 不对应是… / 没想到）
③ 生钉   清单定稿 → 每行转换自动生成一道考题
④ 实现   agent 按清单写
⑤ 判卷   考卷自动红绿，不经过用户
⑥ 结晶   日常"跟预期不一样" → 补进清单 → 回③
```

关键设计决策：

1. **签收形态**：认领对象是行为陈述句/演示，非技术表格；用户动作 = 三选一选择题。
   「没想到」类回答最有价值——把预期暴露从实现后（返工）提前到实现前（改一行字）。
2. **完备性三层过滤**（不追求一次全部显式化）：agent 结构盘点枚举（状态有限）/
   打脸结晶生长（清单只含用户点名 + 出过 bug 的，循环即生长机制）/ 禁令条款兜底
   （3–6 条红线跨组件复用）。
3. **循环降价**：循环不会消失，从「实现后循环」（改代码，贵）前移到「清单后循环」
   （改清单，贱）。闭环的真正含义是循环降价，不是循环消失。
4. **清单 = 唯一事实源**：考卷词汇、观测器状态名直引清单枚举；清单外状态名 = 告警
   （即评审四修正之三的落地）；清单腐烂由机检发现，不占用户带宽。
5. **入口判别**：用户 UI 反馈先分类——「坏了」（故障 → 观测环取证循环）vs「跟我
   想的不一样」（规格缺口 → 直接补清单，不走取证）。规格缺口走取证流水线是近期
   等待时间拉长的原因之一，判别后可省半。

## 请评审反馈

1. 闭环六步与既有机制（判卷链 / 打脸结晶 / 词汇表强制 / plugin-contract §7）有无冲突或重复建设？
2. 入口判别（故障 vs 规格缺口）由谁执行——用户、执行线 agent、还是评审？误判的兜底如何设计？
3. 六步中哪些可立即机检（清单-考卷映射、词汇表一致性已有先例；①盘点枚举的机械生成形态请评审定标准）？
4. composer 首跑的**验收标准**请评审提案：如何判定「8 天循环被终结」（候选：清单定稿后连续 N 个交互需求一轮签收零返工 / 转换覆盖后 M 天零"跟预期不一样"报告）？
