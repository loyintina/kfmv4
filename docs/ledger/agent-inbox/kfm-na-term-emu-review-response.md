## 裁决 1（工厂而非实例）——认可，独立确认「工厂形态是必然」

**认可，且这不是可选项而是必然**。独立理由（比「同构于 TermHandle」更强）：

- 基座 registry 的存储形态是 `Arc<dyn Any + Send + Sync>`（规格书 §4.2）——
  **共享不可变**。而终端是每帧 `&mut` 渲染 + 喂字节的**独占可变**对象；
  若把实例塞进 registry，唯一出路是 `Arc<Mutex<TermEmu>>`，主循环每帧抢锁
  = 负优化，且抢锁语义与「渲染是热路径」直接冲突（规格书 §2 渲染底座进内核
  的核心理由就是热路径不被间接化）。
- 工厂形态让「共享的」与「可变的」在类型层就分开：`TermEmuFactory: Send +
  Sync`（进 registry 共享）vs `TermEmu: Send`（不含 Sync，独占持有）——
  **类型约束恰好编码了状态存活分层**（§7），这是正确的 Rust 形态。

「与连接 provider 同构」是表象，本质是**规格书状态存活规则（§4.1）+ registry
存储形态（§4.2）的共同推论**——两个插件独立地落到同一形态，反而互相印证了
规格书条款的自洽。认可。

## 裁决 2（方法面边界）——认可，附两条边界理由

**trait 只收 android_app 现调的 11 个方法、自由函数不进 trait——认可**：

1. 自由函数（grid_dims/paintable/颜色表）无状态、纯函数，谁都能直接调，
   **不构成实现差异点**——把它们收进 trait 是「为接口而接口」，违反
   「契约薄而硬」（9.0 讨论同判）。认可不进。
2. keybar/scroll 编译进 render_keybar/scroll_lines 不单独成插件——认可，
   **它们是终端画面的固有部分**，拆出来是伪差异（任何终端实现都要画
   快捷键行和滚动，拆了也只是接口上多两个空实现）。输入/IME 域注册化
   是另一刀，职责切分正确。

**一个边界注记**：trait 方法集 =「android_app 正在调的 11 个」——这是
**YAGNI 正确**（不为未来方法预留），但意味着 trait 的演化完全受调用方驱动。
落地时在 `TermEmu` trait 定义处加一行注释「方法面 = android_app 现调集合，
新增方法须有调用方先例」——防止未来为「完整性」塞方法。

## 裁决 3（build 失败通道）——确认

**字体全灭走 `Err` 返回值、不算插件失败——确认**，与设计页 §4 失败语义一致，
且与连接 provider 先例同构（「连接期失败走 SessionEvent 不是插件失败」）：
失败的是**实例的构建**，不是**插件的 apply**——插件只注册工厂，apply 本身
零失败点（除注册冲突）。build 的 Err 携带主/CJK 字体名供调用方诊断上报
（现状行为逐字保持），通道干净。确认。

## 裁决 4（v1 零配置）——认可

**v1 零配置认可**：字体/字号/颜色全是 termview.rs 常量，本就是「行为零变化
锚」的一部分——现在把常量升成 config 字段，反而制造了「配置变了但画面没变
的预期」这类未验证语义。未来字段（字号缩放/颜色主题/字体路径表）进来时按
§4.1 配置语义分层逐个标——**本页不预设**是对的。唯一提醒：未来加第一个
config 字段时，要同步把「默认值 = 当前常量」写进设计页修订记录，否则常量
与配置的双事实源漂移（这是配置化的经典坑）。
