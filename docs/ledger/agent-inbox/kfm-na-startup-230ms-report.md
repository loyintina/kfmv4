## 一、战果

冷启动（杀后台点开）进程内全程 **~230ms**（android_main → 提示符上屏可输入），
用户判卷「秒进、提示符跟画面一起出」。基线为 8-21 傍晚的 ~2.7s。

## 二、三刀手术（kfm-na master）

1. **exec 探针后台化**（`9c6ba54`）——分段探针实测：init 2382ms 的 96%
   是 exec_probe 结尾 report_sync 的阻塞 HTTP 三连重试；探针结果 v1 只
   上报不分支，挪后台线程。init → 129ms。
2. **首帧快路**（`7cd06bf`）——resumed 收尾主动 draw_frame，不等系统
   发 RedrawRequested。首帧 +2358ms → +143ms。
3. **主线程同步探针拔刺**（`6449537`）——本案真凶。8-13 查「黑屏不见字」
   埋的三根探针（首 output / 像素统计 / RTT）全是 report_sync（阻塞
   HTTP，连 2s+读 3s×3 重试），在主线程 output 抽干路径上堵 ~2.1s +
   帧内再堵 ~340ms。四处主线程 report_sync（含会话死亡登记）全改异步。

## 三、一桩乌龙（值得各线镜鉴）

拔刺前我们追了五轮假病灶：「系统扣住首笔 RedrawRequested 2.5s」——
Poll 硬轮询、blackout 补画、唤醒锤（proxy user event 50ms）全部无效，
最后靠 ue/atw 心跳测绘 + 前 3 帧分段探针实锤：循环没睡、锤有效、
buffer_mut 仅 3ms——**主线程是被自家同步探针按在 HTTP 上摩擦**，Redraw
只是排队等我们腾手。刺一拔，「系统扣牌」假象自动消失（首笔 Redraw
+211ms 即到，与脏帧同圈）。

教训两条（已成纪律）：
- **主线程上永远用异步 report**；sync 直报只留进程将死/出生第一格。
- **探针完工要拆**。这批刺是 8-13 埋的，留到 8-21 反咬——观察者烧掉了
  被观察系统。当前留存的分段/测绘探针（init 五段、字体三段、帧三段、
  ue/atw 心跳）待启动性能验收稳定后应开一案拆除。

## 四、副产品

- 诊断通道加固（`0e10318`）：report 三通道全落 logcat（HTTP 队列随进程
  死全丢的事故出了两次；logcat 环形缓冲在系统侧。注：termux 侧无权读
  他户 logcat，此道供 app 自读/未来接 bugreport）。
- 唤醒锤 + blackout 补画保留作冗余：首笔 Redraw 前的脏帧由 about_to_wait
  直画，无害且对慢机器有兜底价值。
