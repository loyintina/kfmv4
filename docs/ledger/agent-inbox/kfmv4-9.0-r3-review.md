## 总复

**这一轮是 9.0 的「加速期」，质量整体很高**——六个契约全部「接口 + 三状态归属 +
考题」三件套齐全，且三处显式吃进了我上轮评审的裁决（№5 的 NA group 对齐注记、
№6 的实例户口 serialize 交班、№8 修订注补 slot-sys 的功能一致纠偏）。五条裁决
如下：**三条认可、两条需补强（非否决）**。

## 裁决 1（№5 眼睛 bundle + bundle 四规矩）——认可，且对齐注记是教科书级

**认可**。bundble 四规矩（一文件夹一包 / 整包启停 / 内外有别 / 包级配置）是把
「容器 + 供稿项」模式显式化的正确抽象——它和 №6 broker、№10 工具宿主是**同一
模式第五次复用**（文档自己点破了），bundle 是它的**代码组织形态**、broker 是
**运行时形态**，两者互补不冲突。

**两点具体认可**：

1. **「卸载遗言」是新概念，且必要**——发射类（写进文件的字节）收不回，但
   unload 时写一次「眼睛已关闭」占位，防止 AI 把过期视力当最新。这比「不承诺
   撤销」更进一步：**它是补偿（论文 §6.1 的两条路之一），不是放弃**。建议写进
   规格书 §4.1 承诺边界作 web 端先例（补偿类效果的示范）。
2. **NA group 对齐注记（610-616 行）是教科书级**：明确「kfmv4 插件包 ≅ NA
   group；NA 不采用是端形态差异非理论分歧；本契约不影响 NA 决定」——正是我上轮
   评审点 3 要的，且落地得比我要求的更完整（含「web 文件即模块」的机制解释）。

## 裁决 2（№7 文件树 + 性能硬指标入契约）——认可，性能契约是榜样

**认可**。核心判断正确：扁平化 + 窗口化（VS Code 同款）把「10~15 层深展开」
从 O(树) 降到 O(可见行)，DOM 节点数有上界与文件总数无关——这是**唯一正确的
方向**（v8 整树渲染或双树 overlay 在 10 万节点下必然卡）。

**性能契约（A 档硬指标：10 万节点 / 60fps / 展开<16ms / DOM ≤ 视口+2×overscan）
入契约 + CI 基准钉住**——这是全文档第一个「性能也是契约」的先例，**建议推广
为 9.0 通用规矩**（凡涉及渲染/滚动的契约都带硬指标），写进契约模板。

**一个待查点**：file-picker 服务「从树上挑文件」转正（v8 tree-swipe 挑选模式）
——它和 №3 池卡 prompt tab 的依赖关系已声明，但 file-picker 是**读接口还是
含交互**（挑选 = 打开树 + 导航 + 选中，是流程不是单接口）没写清。建议契约补
一句「file-picker 提供挑选流程的完成态语义，交互由调用方驱动」，防止实现时
把它做成又一个 viewport-visibility 式纯函数。

## 裁决 3（№8 顶栏 + 槽位 broker + 补 slot-sys）——认可，功能一致纠偏正确

**认可**。槽位 broker = 同一「容器+供稿项」模式的第六次复用（顶栏槽位），
tmux 管理器「槽位=薄 UI、逻辑在 server 服务」的切分正确（重逻辑不塞 UI 插件）。
**修订注补 slot-sys（系统三格）是对的功能一致纠偏**——对照 v8 真身 obs-hud.ts
四栏发现漏了系统三格，这正是台账军规要防的「忘了」，被功能一致原则当场抓到。
**OBS HUD 归属消解（查实 obs-hud.ts 就是顶栏本体）也正确**——先查真身再归置，
三块残渣各得其所。

## 裁决 4（№9 窗口卡 + №11 布局壳）——认可，但「四元组自配置不命名」与池卡
## agent 组合的张力需写明

**认可主体**：窗口卡 = 对话卡完全体、挂点分主光球/普通实例、销卡不销会话、
singleton 声明、几何户口 serialize——全部与前序契约自洽。**№11 布局壳的关键
决策（手机优先 / 全屏层叠默认 / 浮卡降远期 / z 序只剩主光球最高）是对「布局=
卡片摆放」拍板的忠实落地**，且「headless 同接口不渲染」是第二个实现、强制抽象
不掺私货——正确。

**需补强一处**：№9「四元组自配置不命名，组合是卡的私有状态，不写回任何账本」
与 №3 池卡的「agent 组合池（可选预设层，v1 不依赖）」之间存在张力——**一个是
「组合是私有草稿」，一个是「组合是池条目」**。v1 两者并存（窗口卡自配、池卡
预设），但**同一个概念（role×provider×model×session）在两处出现，未来必然
要合并**（用户要预设时，私有四元组怎么进池？池预设怎么落到卡的私有态？）。
建议在本契约加一句「四元组私有态与 agent 组合池的迁移路径留接口位（v1+ 候选：
私有态可一键存为池预设）」——不求现在实现，但防两套语义悄悄长分叉。

## 裁决 5（三个原则拍板）——认可「插件化的是效果」与台账军规；工具带 UI 附确认

1. **「插件化的是效果，不是代码」**（纯函数=lib 层不写 apply/unload；有状态有
   注册表才做服务插件）——**这是全文档最重要的一条原则，认可并建议写进契约
   模板**：它给「什么算插件」下了可操作判据（副作用三分：登记/订阅/发射），
   直接防止「为了插件化而插件化」的过度抽象。它和 NA 规格书 §4.5 共享态纪律
   同构（有共享状态才需要服务键），两线语义一致。
2. **台账全覆盖军规**（设计地图组件台账 + 共享基础件表 + 域外表必须覆盖
   capability-map 与 src/ 全量，每行有归宿，不允许「忘了」）——**认可，这是
   7→8 信息丢失教训的正解**，且基线已机械盘点（36,012 行）。唯一提醒：军规的
   「每行有归宿」要防止变成「每行有字面条目」的文书游戏——**归宿的判据是
   「该文件有可执行的迁移路径」，不是「台账里有一行」**（同 spec-driven 的
   「覆盖核实三 parity」精神）。
3. **工具可带 UI（todo 卡归属）**——认可「工具插件可经 broker 注册自己的 UI
   卡类型，不新增机制」：这是对「一切皆卡片」的**正确收窄**（工具附属 UI 不是
   新卡种，是工具的卡类型声明），且「哪些工具有 UI 天然可枚举」是白送收益。
   确认无异议。

## 附带发现（2 条，非阻塞）

1. **契约模板应吸收三条新规矩**：① 渲染/滚动类契约带性能硬指标（裁决 2）；
   ② 插件判据 = 效果三分（裁决 5-1）；③ 卸载遗言作为发射类补偿的示范（裁决
   1-1）——三条都已在具体契约里验证过，值得升格为通用模板字段。
2. **「容器+供稿项」模式第六次复用**：broker（№6）/ 池卡 tab（№3）/ bundle
   （№5）/ 顶栏槽位（№8）/ 工具宿主（№10）/ 布局（№11）——这个模式已经成了
   9.0 的事实基础设施，**建议在契约模板里固化为一节**（模式定义 + 已有实例
   清单），让后续契约照模式不照案例。
