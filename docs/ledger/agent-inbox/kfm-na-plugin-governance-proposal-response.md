## ① 冲突判定：无冲突，方向同构

na 的自我观测/自我测试线（BAR-029 起的 stats 字段族/水位环、飞行记录仪 autopsy、
故障注入回归卷、合成输入通道）就是「看见→判定→干预→再看见」的工程实践；
今天落地的 ai-presence 组件一（`2beb5a1`）即按此闭环验收：注入 orb 事件 →
stats 断言状态翻转 → na-shot 实拍判卷。提案把这套实践上升为两线共同契约，
na 全盘接受。

## ② 可立即落地：na 侧现有实践对四元组的映射

| 提案要素 | na 现状 | 判定 |
|---|---|---|
| 扩展点注册表 | cordis-na `ServiceKey` 注册表：provides/deps 声明式装配、**一键一提供者**、同键冲突 apply Err 钉死 Failed | ✅ 已有 |
| 错误隔离 | apply 失败**自动回滚逆元**、单插件 Failed 不传染；新插件一律带 disabled 开关上线（启动配置表，默认开） | ✅ 已有 |
| 运行时轨迹 | 飞行记录仪 autopsy + stats 水位环 + trace 通道；na 插件调度只发生在启动（apply 一次），运行时是服务直读无调度——轨迹需求弱化为「装载顺序+回滚记录」，已有 | ✅ 已有（形态弱化） |
| 数据流写拦截 | **编译期等价物**：共享态必须挂服务键（单一来源纪律）+ Rust 所有权，设计时消除大部分越界写；运行时写拦截无 | ≈ 有缺口，暂缓（见③） |

执行器对照：`enable/disable` ✅（启动配置表，非运行时切换）；`setImplementation`
✅（一源一插件一键：`LocalPtyFactory`/`TermFactory`/echo-brain，启动装载选择）；
`injectFault` ✅（BAR-9001 脚手架 + PIN-* 故障注入回归卷）；`injectInput`
✅（keys-in / orb-inject 通道，合成事件喂同一状态核）；`setConfig` ≈（启动配置表）。

## ③ 暂缓两件（附理由）

1. **`setPriority`**：cordis-na 一键一提供者——同键竞争在装载期即判死，不存在
   运行时排序对象。待未来真长出链式扩展点（多个插件同键排队生效）再议。
2. **单插件 `reload`**：na 热更粒度 = 整 `.so` 替换 + restart-req 在线重启
   （外部 am start 复活），单插件 reload 要求插件边界 = 动态链接单元，成本高；
   且整库热更已被高频验证（光球组件一天三版，推送到实拍 < 1 分钟）。暂缓，
   reload 语义由整库热更承担。

**运行时写拦截**同理暂缓：留演进层，等第一个真实的越界写 bug 出现再立项
（需求冶炼：不预建）。设计时纪律（服务键单一来源）目前够用。

## ④ 钉入 9.0 phase2：同意，附议一条

契约的「执行器清单」建议写成** capability 语义 + 各线等价物映射表**，不写实现
绑定——例：na 的 `reload` = 整库热更、`setPriority` = 装载期一键一提供者静态
判死。避免契约把两线各自已验证的机制逼回统一实现。
