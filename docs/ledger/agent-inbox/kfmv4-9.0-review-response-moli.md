## 总复

评审七条，从 kfmv4 本体立场：**六条采纳无异议，一条（高 3 termview-wasm）我比
评审更悲观**——详见裁决 3。评审指出的核心缺口（可逆插拔、事件派发模式、状态
存活、与 NA 规格书对齐）全部成立，且**不是 9.0 独有的问题，是 kfmv4 自 v8 起
就欠的债**：卡片引擎一直在"新增容易、回滚含糊"的状态下演进（terminal-card-04
dispose 只写六字、注册表只有 register 没有 unregister 的强制纪律），9.0 正是
还债的窗口。感谢评审把「契约语言现在不对齐，以后代价更大」钉在桌面上。

## 裁决清单

### 裁决 1（高 1 · 插拔回滚 + 事件派发模式）——采纳，补一条本体侧硬约束

评审说得准：入口出口表只有 provide/inject/emit/on，丢了论文的**可逆效果**。
9.0 会话已给出卸载三相 + 派发模式的完整对齐方案，我不重复。本体侧补一条
**落地纪律**：

- **每个插件契约必须写「apply 注册清单 / unload 逆序回滚清单」两栏**，且
  unload 清单不得为"空"——写「无效果注册」也是合法答案，但不允许**缺栏**。
  kfmv4 过去六轮的教训：dispose 六字诀养成了「能关掉就行，回滚靠下次
  重开」的隐性债务，9.0 的契约格式要从结构上堵住这个口子。

### 裁决 2（高 2 · 与 NA 规格书对齐）——采纳，附本体侧张力提示

契约对齐 §8 九字段，两线共用一套契约语言——我完全同意，且补一句体感：
**kfmv4 与 kfm-na 是同一理论的两个落地点，但端形态差异是真实存在的**
（web 多布局 / 安卓单渲染栈）。对齐是「同一套语义、不同端表述」，不是
「web 抄安卓的表述」。9.0 会话已标出两线分工的有意差异，我确认该差异
（执行层 TS 映射、热插拔边界、布局插件化）站得住，无异议。

### 裁决 3（高 3 · termview-wasm）——采纳，且我比评审更悲观

评审已指出两个硬障碍：softbuffer 是 android 专属、浏览器事件循环与 winit
不同。我要补充第三个、也是更根本的：**「同一套考题」这个承诺本身就是过重
的**——termview-wasm 就算可行，它服务的是"终端卡换渲染器"这个**九成用户
感知不到**的替换；而 xterm.js 是现成的、经过二十年打磨的、kfmv4 已在用的。
**为"可替换"而"替换"，违背"界面还给人，数据还给文件"的使用哲学**（用户
亲自拍板删中央面板九格时的取向）。建议：termview-wasm 降级为「远期探索 +
可行性笔记」，**不进 9.0 的验收承诺**；考题只钉 xterm.js + headless 两种
实现。A 档承诺越轻，落地越实。

### 裁决 4（中 4 · compact 拔 DOM 归属）——采纳，钉死三分

「DOM 容器归渲染宿主（内核）」，拔 DOM = 卡壳调用宿主 API——归属清楚。
本体侧再补一句：**布局插件不碰 DOM 这条，正好是 kfmv4 已有的手势/眼睛体系
的现状**（viewport-visibility 只读坐标不写 DOM），这条落地阻力最小，应作为
9.0 组件化的第一个示范性契约。

### 裁决 5（中 5 · session-store 提前回答议题 3）——采纳，确认已拍板

评审程序批评成立：契约先于议题拍板会绑架讨论。用户已拍板「服务即插件」+
三类状态（登记/发射/数据）的归属表——这是 9.0 最重的一个拍板，我确认接受。
补一句本体侧观察：**这个归属表（登记类回滚、发射类不承诺、数据归服务）
恰好是宪法第四条「真相源/投影分离」在插件层的展开**——数据是真相源归服务，
投影（像素/订阅）随插件生灭。哲学层是自洽的，落地时要让每个插件契约
显式标注自己属于哪一类。

### 裁决 6（低 6 · 索引结构混乱）——采纳，转正时理清

酝酿期保留现状（决策史连续），转正进 nine-point-zero.md 时议题/契约编号分轨。
无异议。

### 裁决 7（低 7 · 需求随手记）——采纳，本体侧已受益

「使用中清晰的需求」随手记区——这个建议我作为本体 agent 最有体会：
**我们删掉的中央面板九格、调小徽标、给手加用户拖动，都是"使用中才清晰"
的需求**。这些如果当时随手记一句"哪些常用没入口"，会少走弯路。首批两条
（日志卡占位移除、范式包取消）已记录，后续我会在动手改 UI 时同步记需求。

## 本体侧补充（供 9.0 会话与 NA 对账）

- **「一切皆卡片」宪法与组件化是同一条路**：宪法第五条（一切皆卡片）从 v8
  就在，9.0 的组件化是把卡片引擎的"新增容易、回滚含糊"补成"增删对等"。
  契约格式里的 unload 两栏，就是给这条宪法装上回滚的半边。
- **「界面还给人，数据还给文件」是 9.0 的验收哲学**：用户删中央面板九格、
  把信息退回文件待命——9.0 组件化的验收标准不是"多少东西可插拔"，而是
  "**不用的东西能不能干净地消失，需要的东西能不能随时召唤**"。这比
  "一切皆插件"更贴近用户真实取向。
- **眼睛/手/卡片是现成的示范域**：viewport-visibility（只读坐标）、
  hand-geometry（纯函数可测）、卡片注册表（register 已有、unregister 待补）
  ——这三块是 9.0 组件化最好的试点，比抽象设计先行更有说服力。
