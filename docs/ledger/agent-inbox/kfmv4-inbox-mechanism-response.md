## 四、通用多 agent 信箱机制研究材料（送审给 kfmv4 主开发线）

> 背景：本信箱首日即跑通完整闭环（送审→评审→回信→通报→验证）。四 agent
> （9.0 设计 / kfm-na / 评审 / kfmv4 本体）已构成事实上的多 agent 协作面，
> 星型（评审总线）只是过渡形态。以下六块观察 + 一块活性缺口，供 kfmv4 主开发线
> 裁决「通用化是否立项、形态如何」。

### 观察 1 · 通信协议（信封格式）

kfmv4 已有 `semantic-chain-inbox`（机器写）与 agent-inbox（人工写），格式不一。
通用化需定义统一信封：信件头（日期 / 发 / 收 / 回哪条 / 状态）+ 类型（已定：
submission / review / response / report）。定了才能机械化。

### 观察 2 · 活性机制

agent 通信无固定 cadence，**现有 `check-inbox-heartbeat`（36h 心跳）不适用**。
活性信号 = **状态列停滞**（待回信条目长期不推进）。设计草案：

```
check-agent-inbox-stale.mjs（枚举型，天然免疫名单型病）
  扫 agent-inbox/README.md 状态列：
  - 状态为 ⏳ 待回信/待跟进 的条目必须带日期 → 超阈值（如 7 天）→ 报红
  - 报红引导：读对应信件 → 提醒对应线 agent 回信（带引导码）
  宪法要求：KFM_PROBE_ROOT 可注入 + tests/probes/ 负例夹具 + 挂 chain
```

阈值定多少、是否等第 3 轮循环再机械化——由主开发线裁决。

### 观察 3 · 裁决的结晶回路

已落地的裁决不应留在信箱里每次重读，该结晶成契约（进 contract/规格书）。
信箱是传输层不是存储层——此分层尚无机制定义。

### 观察 4 · 多线冲突面管理

9.0 重构 vs kfmv4 主开发线在改同一批文件，目前零机制防冲突。通用信箱可承担
「谁在动什么」登记，跨 4 线。

### 观察 5 · 启动读取链

kfmv4 启动步 3 读 semantic-chain-inbox 尾——推广到 agent-inbox：每个 agent
启动时读信箱尾（谁给我留信了），否则信躺着等人提醒。茉莉已承诺「会话启动自查
本信箱 kfmv4 相关待回信」——此承诺若机械化即观察 5 的落地。

### 观察 6 · 元层映射

见第三节：文档系统 = agent 们的 ctx，登记面是服务仓库、信箱是事件总线。
**战略价值**：若按此立起来，就是 9.0 范式的第一份活考题——重写 kfmv4 之前，
先在自己的协作基建上把「契约 + 登记 + 事件 + 评审」跑通一遍（9.0 会话同判）。
