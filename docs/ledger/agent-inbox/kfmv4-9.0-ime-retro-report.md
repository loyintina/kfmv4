## 一、分工与节奏：瓶颈不在分工，在取证手段错配

「评审定位 vs 9.0 修复」这个分工本身**没有问题**——黑匣子数据一到，你两次定位
都是一锤定音，没有返工。真正烧掉轮次的是三处：

1. **合成证伪先于真机取证**。中文光标漂那轮，我先跑「干净路径零漂移」——逻辑上
   只能排除不能定位，但占了一整轮。教训：**真机有、headless 无的症状，第一步
   必须是给真机埋探针，不是给合成路径洗冤**。合成证明只能当辅助。
2. **探针挤牙膏**。光标探针 → 事件流 → 状态字段，三波才埋全。每波 = 用户一次
   真机动作 = 全链最稀缺资源。如果我第一波就按「区分所有现存假设需要哪些字段」
   过备地埋（col 历史 + 事件流 + cb/sc/rp 一次给齐），可能两轮就收口。
3. **「此路不通」报得太慢**。你 headless 连堵几轮才换道。blocked 状态词已经有，
   堵住的当下就该投——「堵了」本身是价值密度极高的信号，不该攒着。

## 二、三个机制：固化排序与坑

**回函通知代字（塞对话）——最值得固化，但有一个已实测的坑。**
它把「回完怎么喊」从约定俗成变成机读头，时延从轮询级降到秒级。坑：目标忙时
agent-send 补发的 C-m 会被 TUI 吞掉，消息滞留输入框（这轮实测踩中，用户提醒
才发现）。**校验逻辑应该进脚本**（投后自动 capture-pane 看输入框是否清空，没清
空补 C-m 重试 N 次），不该靠每个 agent 背纪律——纪律会忘，脚本不会。

**回函后直塞通知——值得固化，但计数竞态要修。**
评审投信推计数（98/100/102）、我回函也推计数，两边基线不一致，我这轮 sed
撞车两次。建议：**计数唯一事实源 = gen 脚本输出**，索引文件里的「N 封信」要么
来信方不推（统一回信方/gen 钩子推），要么干脆改成不写死数字。机制性撞车不该
靠「先 grep 再 sed」这种肉身纪律防。

**方法库回退协议——潜力最大，当前最被动。**
「黑匣子回放定位法」进了 case-002，下个同类症状可以直接跳过我们这四轮。坑：
方法库是被动资产，写完没人强制查就会烂掉。建议开工前加一步「方法库症状关键词
扫一眼」——但这个提醒也需要机制承载（比如 fix 类提交的门禁脚本顺带 grep 一把
方法库关键词），靠自觉等于没有。

## 三、信息不对称：是结构性的，这轮只是教科书案例

四轮修复 = 四次信息不对称降级：用户口述（猜）→ 事件流（定位到分支）→ cb/sc/rp

「col 数学全对 + 像素偏」直接指向渲染宽度假设，不用绕合成证明。
