### 讨论结论：文档系统即插件系统（2026-08-15 用户动议，9.0 会话整理）

用户动议：kfmv4 文档系统本身具有代码库级复杂度，cordis「一切皆插件」的类比
成立；信箱或许是文档系统的 ctx。讨论后的精确映射（对「信箱=ctx」的修正）：

| cordis | 文档系统 | 现状 |
|--------|----------|------|
| ctx 服务仓库 | **登记面**（index.md 产物登记面 / 信箱信件清单） | 已有雏形 |
| 事件总线 | **信箱**（信件已类型化：送审/评审/回信/通报，各带派发契约） | 已有 |
| provide/inject | 文档头的「提供什么/依赖什么」 | 半有（散文版） |
| 可逆效果/修订 | 修订记录 + 修订注纪律 | 已有 |
| relied 守卫 | 被依赖文档禁止静默改（改动走修订记录） | 已有 |
| 契约测试/变异抽检 | 评审（事实核查 = 变异抽检） | 已有 |
| 状态存活 | 宪法级文档 vs 会话速记 | 隐含未分级 |

**关键修正：插件不是文档，是 agent。** 文档是共享状态 Σ（论文「Σ 涵盖一切
共享可变状态」→「一切跨线共享知识必须登记在册」，防孤儿登记面已在执行）；
四个 agent（9.0 设计 / kfm-na / 评审 / kfmv4 本体）才是跑在这个基座上的
插件——各自 provide 能力、inject 依赖、靠信箱事件协调、互不直接耦合。
文档系统整体 = agent 们的 ctx，登记面是服务仓库、信箱是事件总线。

**缺口只有三块**（收敛，不大兴土木）：

1. 文档契约头形式化：四字段机读——provides / depends / status（草案|定稿|
   append-only）/ 修订规则（§8 模板的文档版，只要四字段）；
2. 一个钩子脚本：机械验两件——每份文档登记在某个登记面（防孤儿）、契约头
   depends 路径活着（防死链）——执行层分工「能钩子强制的不靠文档」；
3. 信件类型钉死四五个，各写明回执契约（谁必须回、回什么格式）。

**明确不做**：重 schema、文档生命周期状态机、「文档热插拔」——cordis 的精髓
是契约薄而硬，不是契约多。

**战略价值**：文档系统若按此立起来，就是 9.0 范式的第一份活考题——重写
kfmv4 之前，先在自己的协作基建上把「契约 + 登记 + 事件 + 评审」跑通一遍。
且本信箱首日闭环（送审→评审→回信→通报）已是实证。

——9.0 会话（Kimi Code）· 2026-08-15
