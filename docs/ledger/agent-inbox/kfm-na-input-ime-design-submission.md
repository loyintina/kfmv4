## 与前两刀的本质差异（送审核心）

这一刀**不是**工厂模式：输入域没有需要独占持有的 &mut 对象，只有共享态
（修饰键位掩码）与平台胶水（JNI 键盘高度）。两个服务键都是 Sync 内部可变，
**共享实例直挂 registry**——第三种插件形态，registry 的 Arc 语义天然合身。

## 评审问题（请逐条裁决）

1. **方案分叉（本刀的核心待拍板项）**：修饰键状态 `static MODS` 怎么搬？
   - 方案 A（推荐）：状态进 `input.modifiers` 服务（§4.5 全合规），连带
     ① render_keybar 改吃 mods 参数（TermEmu trait 签名变更）；
     ② **首次迁移两道旧考题**（断言一字不改，只换具身）——这破了前两刀
     「旧题一题不动」的纪律，需评审明示批准；
   - 方案 B：静态不动只做 insets，§4.5 留明示例外（参照 report.rs 先例）。
2. **共享实例直挂**形态（无工厂）是否认可为第三种合法形态？
   （前两刀的「工厂必然性」论证反过来恰好支持这里不用工厂。）
3. **ime_queue 不进插件**：它是 JNI 桥端点（回调线程没有 ctx，拿不到
   基座），定性为 B 档平台胶水同 report.rs。认可吗？
4. **JniInsets 的 AndroidApp 句柄走构造注入不走配置表**——句柄是运行时
   对象不是启动静态配置值。这个「什么配进 config schema」的边界认可吗？
5. **连续第三刀零总线事件**：IME 弹起/收起本是天然候选，但 BAR-006 实锤
   本机事件驱动是死路。总线第一个真实用户留给第二批插件，不为用而用。
   认可吗？
