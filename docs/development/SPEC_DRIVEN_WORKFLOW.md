# KFM v4 — 规范驱动工作流（Spec-Driven Workflow）

> **面向要做一次「带文档的大改动」的 agent。**
> 这不是某个功能的设计文档，是**做设计文档这件事本身的方法论**——从设计、到分阶段
> 执行、到追加约束、到判断归档。KFM 一直在用（测试基础设施、回归体系都走过这条路），
> 本文把它显式写下来，让后来者照着做，而不是每次重新发明。

## 关联文档

- `docs/AGENTS.md` — 文档分层与维护规则（本工作流产出的文档要遵守它）。
- `docs/KFM_V4_INVARIANTS.md` — 心法原则（执行阶段的行为约束）。
- **已跑通的范本**：
  - `docs/archive/design/REGRESSION_TESTING_SYSTEM.md` — **任务型**，8 阶段建成后归档。
  - `docs/design/AI_CHAT_RUNTIME.md` — **参考型**，实现完仍保持 active（长期契约参考）。

---

## §1 何时用这套流程

**用**：改动满足以下任一条——
- 跨 3+ 文件，或跨客户端/服务端。
- 分多个阶段、无法一次做完。
- 引入或依赖**隐式契约**（跨文件的时序/协作约定，破坏后症状隐蔽）。
- 用户明确要求先出方案再实施。

**不用**（直接干）：单文件改动、bug 小修、能在几次工具调用内完成的事。给这类改动写设计
文档是过度工程。

**判断标准**：如果你说不清「这个改动分几步、每步验收什么」，就该先写文档理清；如果一句话
能说清怎么做，就别写。

## §2 四个环节

```
① 设计（draft/active 文档）
    ↓  §现状 → §方案 → §分阶段实施表 → §开放问题
② 执行（边做边更新状态表）
    ↓  每阶段做完翻状态；发现新决策先更文档再改代码
③ 追加约束（把纪律沉淀成一等公民）
    ↓  一次性纪律→心法 / 实时闸门→AI 规则 / 速查→HANDBOOK / 账本→独立追踪表
④ 判断去向（任务型归档 / 参考型保持活跃）
```

### ① 设计

在 `docs/design/` 新建文档，frontmatter：`status: draft`、`version`、`last_updated`、`maintainer`。
结构（照抄范本）：

```
§0 为什么存在（问题陈述 + 核心洞察）
§1 现状分析（当前覆盖/缺陷，带表格）
§2 方案（总体策略 + 关键设计要点）
§3 实施步骤（每步：目标 / 改动范围 / 设计要点 / 验收标准）
§4 实施计划（阶段划分表，含「状态」列：⬜待开始 / 🔄进行中 / ✅已完成）
§5 可复制模板（首个阶段跑通后回填，供后续阶段套用）
§6 开放问题（决策待定项，实施中逐个消解为「结论」）
```

**结尾必写**：`> 本文档与代码同步。实现中发现设计漏洞或新决策，先更新本文再改代码。`

### ② 执行

- **每阶段做完立刻更新 §4 状态表**（⬜→🔄→✅），附一句产出摘要 + 关键 commit。
- **文档先行**：实施中冒出的新决策/踩的坑，先写进文档（§5/§6），再改代码。文档滞后于代码 =
  下一个 agent 踩你踩过的坑。
- **验收先于推进**：每个阶段的「验收标准」逐条勾掉才进下一阶段（心法 23 增量验证）。
- **每个可测点走 revert 验证**：见 INVARIANTS 心法 24——回退修复必须让测试变红，否则测试是假的。
- **提交纪律**：每个可独立运行的改动立即 commit（心法 14）；`check-uncommitted` 会在 >3 文件时
  拦截，别攒。

### ③ 追加约束（关键，最易漏）

改动做完不等于结束——把这次学到的纪律沉淀到对应载体，否则下次还会犯：

| 约束类型 | 沉淀去向 | 例 |
|---|---|---|
| 长期行为纪律 | INVARIANTS 心法（编号追加/升级） | 心法 24 回归测试纪律 |
| 改特定代码时的实时提醒 | AI 规则（`src/server/ai/rules/` 下的 md，`condition` 触发） | `kfmv4-regression-discipline` |
| 隐式契约（破坏出隐蔽 bug） | `DIAGNOSTICS.md` §一 | §1.12 AI 运行时时序 |
| 日常速查 | `HANDBOOK.md` 对应节 | §五 回归测试分层 |
| 持续追踪的账本 | 独立追踪表（保持活跃） | `BUG_REGRESSION_REGISTRY.md` |

### ④ 判断去向

文档做完后，按**它是什么**决定命运，而非「实现完没完」：

```
这份文档是「一次性任务的计划」吗？
├─ 是 → 任务型：status: completed + archived_at，MV 到 docs/archive/design/，
│        更新 CLAUDE.md 文档树 + HANDBOOK 引用 + 依赖它的 doc 链接改指归档路径。
│        （范本：REGRESSION_TESTING_SYSTEM）
└─ 否，是「长期要查的契约/架构参考」→ 参考型：保持 status: active 留在 docs/design/
         或提升为根层文档。实现完也不归档。
         （范本：AI_CHAT_RUNTIME —— 改流式对话时仍要查它的 §4 隐式契约）
```

**常见错误**：把参考型文档因为「实现完了」就归档 → 后来者改相关代码时找不到契约参考。
**判据**：问「这份文档实现完之后，还有人需要回来查它吗？」需要 → 参考型 → 不归档。

## §3 收尾检查清单

一次规范驱动的改动，结束前逐条确认：

- [ ] §4 状态表全部 ✅，每阶段有产出摘要。
- [ ] §5 可复制模板已回填（真实跑通的做法，不是占位）。
- [ ] §6 开放问题全部消解为「结论」。
- [ ] 学到的纪律已按 §2③ 表沉淀到对应载体。
- [ ] 文档去向已判定（归档 or 保持活跃），CLAUDE/HANDBOOK 引用同步。
- [ ] `npm run check` 绿灯（含 check-docs 引用有效性、check-versions、check-handbook-sync）。
- [ ] 涉及测试的：`npm test` 全量绿 + 关键钉子过 revert 验证。
