# KFM v4 — 回归测试体系建设设计规范

> **版本**：v1.0
> **状态**：设计阶段（draft）
>
> 本文档定义 KFM v4 从「零散手动验证」迁移到「分层自动化回归体系」的方法论、
> 分层策略、实施步骤与验收标准。实施完成后归档到 `docs/archive/design/`。

## 关联文档

- `docs/archive/design/TEST_INFRASTRUCTURE_SPEC.md` — 前一轮测试基础设施改进（GSAP/DOM/Canvas mock，已完成归档）。本文是它的后继：那一轮解决「测试能不能跑」，本轮解决「测试测什么、怎么不爆炸」。

## §0 为什么做这件事

### 0.1 问题陈述

git 历史 1388 个提交、**687 个 `fix`**。这是一部海量、真实、已被人手动发现过的
bug 目录，却几乎没有沉淀成自动化哨兵。当前 214 个测试集中在**最稳定的部分**
（引擎纯函数），而历史上反复出 bug 的**集成边界**（run-manager 时序、着色链路、
z-index、光标/滚动、WS 重连）几乎零覆盖。

单个文件树功能当年就有几十个手动验证点（光标位置、展开、渲染、手势、滚动、
字符动画……），验证繁琐且痛苦。根因不是「该写的测试多」，而是**逻辑与渲染焊死**，
逼人用眼睛当断言器。

### 0.2 核心洞察（决定整个方法论）

> **不要给每个历史 fix 补一个测试。** 687 个 fix 里绝大多数属于以下三类之一，
> 不该逐条自动化：

| 类别 | 特征 | 处置 |
|------|------|------|
| **视觉/观感（V）** | 颜色/光晕/间距/动画节奏，无「对错」只有「好不好看」 | 不写自动化，冒烟层兜底 |
| **叠加微调（S）** | 同一处参数反复横跳（如滚动光标步进 7 连修） | 只测**最终形态**，中间态不测 |
| **死代码（D）** | 涉及已删除/已重写的模块 | 跳过 |

真正值得钉住的只有：

| 类别 | 特征 | 处置 |
|------|------|------|
| **逻辑（L）** | 有明确对错、纯函数可测（光标落点/滚动过滤/消息计数） | 回归钉子 |
| **集成（I）** | 跨模块时序/协作（run-manager/重连/着色链路） | 集成测试 |

**结论**：目标不是「全面覆盖 687 fix」，而是「把有明确对错、会复发、可测的那批
变成永久哨兵，并顺手把它们背后的逻辑从渲染里剥离」。

### 0.3 反爆炸原则

对「组合太多测不全」的恐惧，解药不是穷举用例，是换武器：

- **不变量测试**：一条「任意展开/折叠序列后，渲染树总高 == 可见行高之和」+ 随机
  操作序列跑几百次，覆盖几十个手动用例都盖不全的组合空间。
- **回归钉子**：每类真实出过的 bug 配一个哨兵，不追求覆盖率数字。
- **浏览器测试克制**：始终个位到二十几条。**膨胀 = 逻辑没抽出来的信号**，回去拆
  纯函数，而不是加浏览器用例。

## §1 现状分析

### 1.1 当前覆盖（214 测试）

| 层 | 覆盖 | 状态 |
|----|------|------|
| 引擎纯逻辑 | Box、flex、text-layout、StyleConfig | ✅ 扎实 |
| 模块状态机 | orb-state、floating-state、renderer-lifecycle | ✅ 扎实 |
| 注册中心 | gesture-registry、card-registry、style-registry、animation-registry | ✅ 较扎实 |
| 基础工具 | click-queue、logger、debug-assert、interaction-constants、dom-refs | ✅ 扎实 |
| **服务端** | 无 | ❌ 零覆盖 |
| **AI 运行时** | 无 | ❌ 零覆盖（run-manager/chat/重连） |
| **WS 心跳/重连** | 无 | ❌ 零覆盖 |
| **集成路径** | 无 | ❌ 零覆盖（右滑→建卡→着色→层级） |
| **Canvas 渲染像素** | 无 | ❌ 冒烟层兜底 |

### 1.2 基础设施缺陷

- `runner.ts`（54 行）：线性顺序执行，**测试间共享全局模块状态**（`KFMState`/
  `cardRegistry`/gesture 注册表），存在隐式先决条件。规模扩大到几百个会雪崩。
- 无分类标签：无法单独跑 `unit`/`integration`/`regression`/`smoke`。
- 无回归钉子命名约定：测试挂了看不出对应哪个历史 bug。

## §2 目标体系

### 2.1 四层金字塔

```
     ┌─────────────────────────────┐
     │   L4 冒烟（smoke）            │  12-20 条,真实浏览器+服务端,慢,CI 定期
     ├─────────────────────────────┤
     │   L3 集成（integration）      │  多模块协作,轻量 stub,Node 内跑
     ├─────────────────────────────┤
     │   L2 单元（unit）            │  单模块/纯函数,当前主力
     ├─────────────────────────────┤
     │   L1 不变量（invariant）      │  随机输入验证不变量,压组合爆炸
     └─────────────────────────────┘
```

**价值最高的补充是 L3（集成）与 L1（不变量），不是继续堆 L2。** 因为历史 bug 全在
集成边界。

### 2.2 测什么 / 不测什么

```
测：输入→输出、不变量、边界值、错误路径、跨模块时序
不测：内部变量名、实现步骤、mock 调用次数、视觉观感
```

判据：**重构实现后测试还应是绿的**。测试与实现一一对应 = 重构会连带改测试 =
失去安全网。

## §3 实施步骤

> 每一步都是纯新增或纯重构，**不改产品行为**。本轮不开发新功能。

### 步骤 0：测试基础设施升级（前置，不碰产品代码）

**目标**：让 runner 能承载几百个测试而不雪崩。

**改动范围**：`tests/runner.ts`（改造）+ 新增隔离工具 `harness.ts`（隔离工具，置于 tests/）。

**设计要点**：
- **测试隔离**：提供 `beforeEach` 钩子，每个测试前重置共享模块状态（`KFMState`
  reset、`cardRegistry` 清实例、gesture 注册表清空）。
- **分类标签**：`test(name, fn, { tag: 'unit'|'integration'|'regression'|'smoke' })`；
  支持 `TEST_TAG=integration npm test` 只跑一类。
- **回归钉子命名**：`regression('BAR-008: 液体粒子跟随回弹', 'd4f658a', fn)` —— 显式
  绑定 B.A.R. 编号 + 修复 commit。挂了一眼定位复发的历史 bug。

**验收标准**：
- [ ] 现有 214 测试不因升级失败。
- [ ] 可用 `TEST_TAG=xxx` 单独跑一类。
- [ ] 提供状态重置钩子，两个互相污染的测试改用隔离后各自独立通过。

### 步骤 1：Bug 回归登记表（把 git 历史蒸馏成地图）

**目标**：把 687 个 fix 分类，产出可执行的「该测什么」清单。**这是最耗人力但最关键
的一步——把无穷多的 bug 变成有限、分好类、知道该干嘛的清单。**

**改动范围**：新增 `docs/BUG_REGRESSION_REGISTRY.md`（复用 B.A.R. 编号体系）。

**设计要点**：
- 过一遍 fix 历史，每个打标：`L`(逻辑) / `I`(集成) / `V`(视觉) / `S`(叠加) / `D`(死)。
- 只有 `L`/`I` 进入「待钉」队列；`V` 记为「冒烟兜底」；`S` 合并为「最终形态一条」；
  `D` 标注跳过原因。
- 表结构：`| BAR编号 | commit | 一句话症状 | 类别 | 状态(待钉/已钉/兜底/跳过) | 测试位置 |`
- **分批滚动填充**，不要求一次填满 687 条——按实施批次填。

**验收标准**：
- [ ] 登记表建立，含分类图例 + 与 DIAGNOSTICS/旧 B.A.R. 的关系说明。
- [ ] 第一批（run-manager 相关）fix 已完整登记。

### 步骤 2：垂直切片样板 —— run-manager 时序（阶段 A）

**目标**：完整走通一个子系统的回归建设闭环，产出可复制的模板。选 run-manager 因为：
最近出过 bug、有 `AI_CHAT_RUNTIME.md` 做规格、纯 Node 可测、极易复发。

**改动范围**：新增 `run-manager.test.ts`（置于 tests/）。

**设计要点**（对应 `AI_CHAT_RUNTIME.md` §4.1 时序契约）：
- 用 mock 生成器驱动 `startRun`，`attachRun` 订阅，断言 `onDone` 触发时机。
- 覆盖三个场景（每个都是一次真实修复的规格）：
  1. 生成器正常结束 → 实时订阅者收到 `onDone`（`a5bf0c4`：finally 显式收尾）。
  2. 断连后 run 已 done → `attachRun` 补齐后立即 `onDone`（`d4a60f7`：重连续读）。
  3. `startRun` 取代旧 run（非复用）→ 新消息不接旧上下文（`d4a60f7`：supersede）。

**微循环（每个钉子都走）**：
```
1. git show <commit> 读懂当时错在哪、怎么修的（心法 9/10：不凭记忆）
2. 判断正确行为能否用不看屏幕的断言表达 → 能则写，不能则先抽纯函数
3. 写一个"会因该 bug 复现而失败"的测试
4. 【灵魂】git revert 该 fix（或临时改回旧逻辑）→ 跑测试 → 必须挂
   否则测试是假的,根本没在测那个 bug
5. 恢复 fix → 测试转绿 → 提交
```

**验收标准**：
- [ ] run-manager 三场景测试通过。
- [ ] 每个测试经过 revert 验证（临时回退 fix → 测试变红）。
- [ ] 沉淀为其他批次可套用的模板（记录在本文 §5）。

### 步骤 3：第一批 —— 服务端 + 运行时逻辑（零重构成本）

**目标**：钉住纯 Node 可测、无需剥离的高价值区。

**改动范围**：新增 `server-routes.test.ts`、`chat-protocol.test.ts`（置于 tests/）。

**覆盖**：
- `src/server/ai/routes.ts` 参数校验：空 sessionId→400、空 messages→400（`f46a551`）。
- `path-utils` 路径逃逸守卫（安全关键）。
- `chat.ts` 工具块索引连续化：Claude 非零起始 index → 无 undefined 空洞（`7ac8f47`）。
- 事件协议：`message_stop`/`done`/`__end__` 序列正确。

**验收标准**：
- [ ] 每条经 revert 验证。
- [ ] 覆盖至少 4 个已登记的 `L`/`I` 类 fix。

### 步骤 4：第二批 —— 客户端逻辑（已是/易剥离为纯函数）

**改动范围**：新增/扩充对应测试文件。

**覆盖**：
- 滚动约束过滤折叠节点（光标 fix 串的最终形态）。
- `tree-model` 展开/嵌套边界。
- 会话消息计数只算有正文的消息（`b8dec96` 类）。
- mode-system 着色回调注入（本次 `427c960`）。

### 步骤 5：第三批 —— 逻辑与渲染焊死的模块（有重构成本）

**目标**：先把计算抽成纯函数，再钉。**重构让代码更好，不是纯为测试付的税。**

**覆盖**：
- `canvas-cursor` 光标位置计算 → 抽纯函数 → 钉本次液体粒子（`d4f658a`）。
- `canvas-scroll` 偏移数学。

### 步骤 6：不变量层（压组合爆炸）

**改动范围**：新增 `invariants.test.ts`（置于 tests/）+ 轻量随机序列生成器。

**候选不变量**：
- 任意展开/折叠操作序列后，渲染树总高 == 可见行高之和。
- 光标永远落在可见（非折叠）节点上。
- 任意 scrollY 下，光标屏幕坐标 == box 树坐标 − scrollY。
- 回弹动画中任意时刻，液体粒子原点 x ∈ [cursorBox.x, cursorBox.x + 8]。

### 步骤 7：冒烟层（最后，最少）

**改动范围**：新增 `tests/smoke/`（Playwright）+ package.json 脚本（独立于 `npm test`）。

**覆盖（12-20 条封顶）**：页面起来、光球开合、右滑出卡且 z-index>4000、切模式卡片
变色、文件树展开有内容。**只验证「活着、大致对」，不验证逻辑。**

## §5 可复制模板（阶段 A 已跑通）

阶段 A（run-manager）已验证下面这套「子系统从零到钉住」的标准动作，后续批次照套。

### 5.1 让被测逻辑可离线运行 —— 依赖注入优先于 mock hack

run-manager 原本直接 `import { streamChat }`，无法离线测（会打 provider + 网络）。
**给 `startRun` 加一个可选参数** `streamFn: StreamFn = streamChat`：默认值让所有生产
调用零改动，测试注入受控 mock 生成器。这是设计改进，不是测试 hack。

> 优先级：依赖注入（改一个默认参数）> ESM resolve hook mock（`gsap-hook.mjs` 那套，
> 只适合 bare specifier，相对路径导入（`./模块名`）很别扭）。

### 5.2 无墙钟等待 —— await 代码真正的信号（rule ts-no-test-timers）

禁止 `setTimeout` 猜时长。两个确定性等待模式：
- **有界微任务轮询**：`awaitRunDone(run)` 反复 `await Promise.resolve()` 直到
  `run.done`（它在 `finally` 翻转，独立于被测的 onDone 修复），有轮数上限。
- **关键：等待信号必须独立于被测对象**。BAR-101 测的就是「onDone 是否触发」，
  所以不能用 onDone 当等待信号（循环论证）——用独立的 `run.done` 轮询，让 bug
  以「断言失败」而非「挂死」暴露。

### 5.3 回归钉子的微循环（每个钉子都走）

```
1. git show <commit>            读懂当时错在哪、怎么修（心法 9/10：不凭记忆）
2. regression('BAR-xxx', commit, 名称, fn)   写测试，断言 = 修复的可执行规格
3. 【灵魂】临时回退该 fix（改一行 → void 0 / if(false)）→ 跑 → 必须变红
   若测试仍绿 = 假测试，它没在测那个 bug
4. 恢复 fix → 转绿
5. 更新 BUG_REGRESSION_REGISTRY 状态为 ✅ 已钉（revert 验证）
```

阶段 A 实证：禁用 `a5bf0c4` 的 finally onDone → BAR-101/101b 变红（`onDone 必须
被触发` 失败，不挂）；禁用 supersede abort → BAR-104c 变红（`旧 run 应被 abort`）。

### 5.4 分类与隔离

- 回归钉子用 `regression()`（默认 `tag='regression'` + `reset=true`）。
- 编排类多步测试用 `test(name, fn, { tag: 'integration' })`。
- 共享单例污染由 `reset-hooks.ts` 的 `beforeEach` 统一清（KFMState/cardRegistry/gestures）。

## §6 开放问题

### 6.1 revert 验证如何自动化？

手动 `git revert` → 跑 → 恢复很繁琐。是否需要一个脚本：给定 commit + 测试名，自动
临时回退、跑指定测试、断言其失败、再恢复？**建议**：阶段 A 手动做，若发现高频再脚本化。

### 6.2 冒烟层是否进 `npm run check` 主管线？

浏览器测试慢且需要环境。**建议**：独立脚本 `npm run smoke`，不进 `check`/`build` 主
管线；CI 单独定期跑。

### 6.3 登记表最终去向

`BUG_REGRESSION_REGISTRY.md` 是活跃追踪表。**建议**：全部批次完成后，作为「测试体系
建设成果」归档，并在 HANDBOOK 留一个「新 bug → 补钉子 → 登记」的常驻流程指引。
