# KFM v4 — 上下文拼接与 AI 工作空间设计

> **状态**：draft
> **版本**：v0.1
> **最后更新**：2026-07-07
>
> 本文记录 AI 对话的上下文来源、拼接管线、存储方案和相关卡片的讨论。
> 不是实现计划，是问题清单和方向整理。

---

## §1 问题

当前对话（orb 面板）发消息到 API 时没有注入任何系统上下文。AI 不知道：

- 自己在什么项目里
- 有什么规则要遵守
- 能调用什么工具
- 当前页面上有什么
- 对话历史在哪

结果是 AI 每次回复都是"通用 AI"，不是"这个项目的 AI"。

## §2 上下文来源

从讨论中梳理出的三类上下文：

### 2.1 静态预设（用户预先选好的）

用户（或项目预设）指定某些文件自动注入每次对话：

| 来源 | 示例 | 用途 |
|------|------|------|
| 心法文档 | `docs/KFM_V4_INVARIANTS.md` | 技术约束 |
| 角色卡 | `角色卡`（概念，如卡萝/空谷） | 人格设定（L1） |
| 项目手册 | `docs/HANDBOOK.md` | 项目知识 |
| 开发指南 | `docs/development/CARD_DEV_GUIDE.md` | 规范参考 |

**问题**：选中的文件应该存为路径列表。存哪？当前方案倾向 localStorage 或 `.kfmv4/` 工作区目录。

### 2.2 动态 pin（本次对话临时加入）

当前对话中手动 pin 的卡片或文件：

| 来源 | 示例 | 获取方式 |
|------|------|---------|
| 功能卡 | 日志卡当前输出 | 卡片实现 `ContextProvider` 接口 |
| 文件卡 | 打开的 .md 文件 | 文件内容 |
| 终端卡 | 当前屏幕内容 | 卡片实现 `ContextProvider` 接口 |

**问题**：需要 `ContextProvider` 接口定义。所有卡片可选实现。

### 2.3 项目状态（自动注入）

| 来源 | 示例 |
|------|------|
| 当前版本 | v7.0.0 |
| 当前焦点 | 文件树展开到哪、哪张卡 active |
| Registry snapshot | 页面上有什么交互元素 |

## §3 拼接管线

```
预设文件列表 ──┐
               ├─ 读取 → 拼合 → 裁剪 → 注入 system message
动态 pinned ───┘
项目状态 ──────┘
```

裁剪策略：
- 固定优先级：角色卡 > 心法 > 手册 > 其他
- Token 上限：context window - 预留回复空间
- 超长时从低优先级开始裁

## §4 存储方案（未定）

讨论中反复出现的问题是"数据存哪"。有两个方向：

### A. localStorage（当前设置卡的方案）

```
kfm-ai.apiUrl
kfm-ai.apiKey
kfm-providers       ← JSON
kfm-agent-config    ← JSON
kfm-preset-contexts ← 文件路径列表
```

**优点**：零额外工作，现有代码可用
**缺点**：AI 自己不能读写，非持久化，不适合大数据

### B. `.kfmv4/` 工作区文件（讨论中提出的方向）

```
.kfmv4/
├── providers.json      ← API 配置
├── sessions/           ← 对话历史
│   └── 2026-07-07.jsonl
├── tools/              ← 工具定义
│   └── file-read.json
├── contexts/           ← 预设上下文
│   └── pinned.json
└── identity.md         ← AI 基础认知（舰灵）
```

**优点**：AI 自己能读写，文件化持久，可 git 备份
**缺点**：需要额外搭建、双 git 问题未解决

**结论**：第一阶段用 localStorage，等需求明确再迁文件。

## §5 涉及的卡片

| 卡片 | 职责 | 阶段 |
|------|------|------|
| **对话卡**（现有 orb 面板） | 发消息、渲染回复、管理上下文池 | 立即做 |
| **API 配置卡**（现有 api.card） | 管理 Provider(url+key+模型列表) | 当前 |
| **Agent 设置卡**（待建） | 选当前用哪个模型、加载哪些预设上下文 | Phase II |
| **工具卡**（待建） | 展示 AI 可用工具集 | Phase II |
| **历史卡**（待建） | 浏览/搜索对话历史 | Phase III |
| **上下文管理卡**（讨论中否决） | ❌ 不单独建，由对话卡自身承载 | 已否决 |

关键决策：**不做单独的上下文管理卡**，对话卡本身就是上下文管理器。

## §6 实现顺序（当前认知）

```
第一阶段（现在做）
  1. 对话卡接 API（读 localStorage 配置，发消息，渲染回复）
  2. 注入最简 system prompt（"你在 KFM 项目中..."）

第二阶段（下一轮）
  3. ContextProvider 接口定义 + 预设上下文选择
  4. 文件卡上下文注入（pin .md 文件）
  5. 功能卡上下文注入（pin 日志/终端）

第三阶段（未来）
  6. Agent 设置卡（模型选择 + 上下文预设管理）
  7. 工具卡（可用工具展示）
  8. 对话历史持久化
```

## §8 已放弃的方案

| 方案 | 放弃原因 |
|------|---------|
| 单独的上下文管理卡 | 对话卡本身就是上下文管理器，不需要多一张卡 |
| 一次性建完所有存储卡片 | 应该从对话卡接 API 开始，逐步迭代 |
| 用 OMP/Claude Code 作为 Agent 后端 | 走直接 Chat API 路线，不依赖 CLI 工具 |
